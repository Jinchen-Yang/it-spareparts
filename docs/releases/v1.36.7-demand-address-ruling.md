# v1.36.7 需求单候选支持输 PN + 唯一匹配自动关联（领用地址=需求单联系地址）

日期：2026-10-13（上海）。决策：0004「2026-10-13 修订」。

## 背景与裁定

用户查看项目 `c5baa3c0…?tab=site` 发现领用地址全部「未填写」，随后裁定业务口径：
**领用地址就是维保需求单的联系（收货）地址**，推翻 D-26「两者语义不同」的前提。
实测数据支持「跟单走」规则：全库 2531 张已确认领用单地址全空；67% 项目存在多地址
（最多 235 个），地址是「单」级属性——跟随本单/本行关联的那张需求单即可消歧。

## 改动

1. **候选搜索 q 扩展**（`demand_candidates`，两入口共用）：q 匹配「单号 或 单内任一
   活跃明细行的 pn_std/pn_raw 文本」，仍用 EXISTS 不 join，count/分页口径不变。在
   需求单候选框里直接打 PN 即可搜出单（用户原话「输入 pn 自行匹配维保订单」的字面
   落地）。
2. **人工登记领用唯一候选自动关联**：行内选 PN 后候选恰好一张且未关联任何单时自动
   选上，地址链路（预填+来源标注+可改+换单跟随）随之打通；多张候选仍需人工挑。
3. **登记返还需求单下拉改服务端搜索**：filterOption=false + 300ms 防抖 onSearch，
   清空搜索词回全量；「含此 PN」分组逻辑不变。
4. 版本号 1.36.7 + 更新日志（补记昨日漏更的 1.36.6）。

## 存量回填（待明确指令后执行，不在本 PR 内）

规则：已确认/已更正领用单中 `site_location` 为空者，按行级 `demand_order_no`
（空则按单号对应）锚定同项目已生效需求单，取其 `receiver_address` 回填，version+1
并逐条留 operation audit。干跑（2026-10-13 生产实测）：2531 张空地址中 2166 张
可无歧义回填、0 张锚定冲突，其余 365 张锚定单无地址。执行脚本另附，需所有者
明确授权后在停写窗口运行。
