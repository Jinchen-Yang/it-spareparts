# v1.19.0 DEV-15 生产发布增量 Runbook

本文是 [DEV-14 Runbook](./v1.19-dev14-release-runbook.md) 的强制增量，适用于固定 13% 双口径、维保报销贡献毛利、三个月成本瀑布和往返工作簿。两份文档冲突时以本文为准；DEV-14 的精确 SHA 构建、停写、备份恢复演练、闭门切流、观察和证据归档步骤继续适用。

目标数据库 head：

```text
f1c8e4a7b2d9
```

迁移链：

```text
c9d4e7f2a6b1
→ d4e8f1a2b3c4
→ e5f9a2b3c4d5
→ f1c8e4a7b2d9
```

## 1. 放行前置条件

必须同时满足：

1. [DEV-15 规格](../maintenance/dev15-roundtrip-and-tax-policy-spec.md) 与甲方 12 条确认一致；
2. 目标 40 位 SHA 已合并进 `origin/main`，生产不部署功能分支；
3. 目标 SHA 的后端全量测试、前端全量测试与构建全部通过；
4. 迁移从生产旧 head 升级到 `f1c8e4a7b2d9`，再降级回旧 head，并再次升级到新 head 的演练通过；
5. 40,000 行维保成本重算在目标镜像中通过，第二次重算结果逐行一致；
6. 往返工作簿的结构、视觉、权限、签名、幂等、版本冲突、失败零写入和范围完整性测试通过；
7. 已在生产快照的隔离恢复库上演练本文和 DEV-14 Runbook；
8. 发布、数据库、回滚负责人及观察窗口已确认，维护窗口内没有进行中的导入或工作簿回填。
9. 旧 head 的 `f_project_expense` 为零；若不为零，必须先停止发布并完成原始归档税口径
   审计与重放，迁移本身会失败关闭。

任一项失败即停止。合并成功、镜像构建成功和生产可发布是三种不同结论。

进入 DEV-14 的受控发布 shell 后，确认两份 Runbook 使用同一新 head：

```bash
git show "${TARGET_COMMIT}:frontend/src/version.ts" \

```

从 `git archive "$TARGET_COMMIT"` 构建 app/frontend，不得从生产脏工作区构建。归档目标 SHA、源码 tar checksum、镜像 ID 和 Compose 配置摘要。

## 3. 历史报销税口径门禁与迁移断言

不能根据旧库单一 `amount` 猜测历史工作簿写的是含税还是未税。2026-07-29 的生产只读
预检证据为：

```text
alembic_version=c9d4e7f2a6b1
f_project_expense=0
成功 expense 导入批次=0
成功 expense 原始归档=0
```

这只是当时快照，不替代切流时复核。停止入口并确认没有运行中导入后、执行迁移前，在
旧 head 和隔离恢复库分别运行：

```sql
SELECT count(*) AS legacy_expense_rows
FROM f_project_expense;

SELECT
  count(*) FILTER (
    WHERE b.file_type = 'expense' AND b.status = 'success'
  ) AS successful_expense_archives
FROM sys_raw_file AS r
JOIN sys_import_batch AS b ON b.id = r.batch_id;
```

两项都必须为 `0`。任一非零立即停止发布：逐本校验 `sys_raw_file` 的 checksum 和归档
工作簿，按同行显式“金额口径/含税金额/未税金额”建立证据清单，再用 DEV-15 解析器在
隔离库重放并独立对账。没有口径字段的行才可默认未税。禁止直接修改迁移、设置环境开关
或用 SQL 把全部旧金额批量标成未税；迁移检测到任一旧报销事实会主动报错并保持旧 head。

在隔离恢复库升级后执行：

```sql
SELECT version_num
FROM alembic_version;

SELECT
  purchase_display_basis,
  sales_display_basis,
  maintenance_project_profit_default_basis,
  version
FROM sys_business_setting
WHERE id = 1;

SELECT column_name, is_nullable
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name = 'f_project_expense'
  AND column_name IN (
    'amount_ex_tax',
    'amount_inc_tax',
    'tax_basis',
    'tax_rate_used'
  )
ORDER BY column_name;

SELECT to_regclass('public.maintenance_manual_cost_override');
SELECT to_regclass('public.maintenance_contract_workbook_state');
SELECT to_regclass('public.maintenance_roundtrip_operation');
```

硬断言：

- `alembic_version = f1c8e4a7b2d9`；
- 采购默认 `both`、销售默认 `ex`、项目维保默认 `both`；
- 迁移前旧报销事实与成功报销原始归档均为零；
- 三张新表存在；
- `f_maintenance_line.cost_bucket` 能把 `cost_source='manual'` 识别为实际成本。

迁移后零历史误标断言：

```sql
SELECT count(*) AS expense_rows_after_schema_upgrade
FROM f_project_expense;
```

结果必须为 `0`。

## 4. 新口径独立对账

不要只调用应用函数后读取应用自己的结果。使用独立 SQL 或独立脚本抽取至少：

- 10 条原采购口径为含税的记录；
- 10 条原采购口径为未税的记录；
- 10 条未标注采购税口径的记录；
- 10 条销售记录；
- 10 条维保报销；
- 10 个存在重复销售单号的合同；
- 三个月边界内、边界外各一组成本参考；
- active 与 archived 互通池各一组。

逐项核对：

```text
采购 True：未税 = 原值 / 1.13，含税 = 原值
采购 False/NULL：未税 = 原值，含税 = 原值 × 1.13
销售：未税 = 原含税值 / 1.13，含税 = 原值
无报销税字段：未税 = 原值，含税 = 原值 × 1.13
贡献毛利 = 合同收入 - 备件成本 - 生效维保报销
```

同一 XSDD 的收入必须取“成功导入且已生效”记录中的最新版本；并列依次按导入时间、事实创建时间、批次 ID、事实 ID 打破。

## 5. 重算与幂等

DEV-14 中“旧五层结果不得变化”的断言不再适用。DEV-15 明确调整瀑布顺序，应改为：

```text
direct
→ window
→ month_avg
→ pool_purchase
→ pool_sales
→ purchase_history
→ sales_history
→ manual
→ none
```

所有历史参考都必须满足：

- 参考日期不晚于出库日；
- 参考日期不早于“出库日前三个自然月”的边界；
- 只有 active 池可用；
- 不限制 active 池来源；
- 同一 PN 落入多个 active 池时失败关闭；
- 人工成本只能接管自动瀑布仍为 `none` 的行。

目标镜像内连续执行两次重算。第一次前、第一次后、第二次后分别导出以下字段并比较：

```text
id
unit_cost_inc_tax
unit_cost_ex_tax
cost_amount_inc_tax
cost_amount_ex_tax
cost_source
reference_side
reference_pool_group_id
reference_pool_version
reference_from_date
reference_to_date
reference_latest_date
anomaly_flags
```

第一次允许按新规则变化；第一次后与第二次后必须逐字节一致。

## 6. 往返工作簿闭门验收

目标镜像至少完成以下自动化与人工验收：

1. 导出 `全部` 模板，确认 9 个 Sheet 的名称、顺序，以及五个数据页的固定 Table 名；
2. 导出自定义日期模板，确认订单、订单明细、报销均只含闭区间内容；
3. 原样导入为零业务变更；
4. 新增报销后未税值原样保存，含税由服务端生成；
5. 修改订单和订单明细后版本递增并留审计；
6. 新增人工成本后重算命中 `manual`；
7. `VOID` 只软作废，不物理删除；
8. 同一文件重复上传返回原批次，不重复写入；
9. 两份基于同一 revision 的模板依次导入，后一份返回 `409`；
10. 篡改元数据、行签名、Table、表头、隐藏结构、公式或重复 UUID，整本拒绝且业务表、成本、合同状态和审计零写入；
11. 带日期范围、空白模板或新引入但未在签名快照中的合同，`expense_snapshot_complete` 必须为 `false`；
12. 只有无日期的 snapshot 模板中已签名合同可以变为 `true`；
13. 无成本或无利润权限账号不能下载或导入往返工作簿；
14. 工作簿用 Excel 或 LibreOffice 打开，冻结、筛选、列宽、日期、金额、颜色、必填提示和中文说明可用。

资源与复杂度门禁同样是硬验收：

- 每个可编辑 Table 最多 10,000 行，10,001 行必须在 ORM 全量物化和 openpyxl 构建前返回 `413`；
- XLSX 解压总量不超过 64 MiB，压缩炸弹必须在 openpyxl 解析前拒绝；
- 同一 app 进程同一时刻只构建一份往返模板；
- 100 行和 1,000 行导入的查询数不能随行数线性增长；
- 1,000 条订单明细 UPDATE 全流程不超过 20 次 SELECT、50 条总 SQL；
- 1,000 条人工成本 CREATE 全流程不超过 22 次 SELECT、50 条总 SQL；
- 精确文件重放固定为 2 次 SELECT、0 次 commit、0 次重算。

生产闭门检查只做只读导出，不向真实合同导入测试数据。需要验证写入时必须在隔离恢复库或专用验收合同执行。

## 7. 生产切流前检查

按 DEV-14 Runbook 备份、校验 checksum、查看 TOC，并在隔离数据库完成恢复。随后停止生产入口和 app，确认没有运行中的导入：

```sql
SELECT id, filename, file_type, uploaded_at
FROM sys_import_batch
WHERE status = 'processing'
ORDER BY uploaded_at;
```

必须为零行。升级数据库后：

```bash
sudo docker compose run --rm --no-deps app alembic upgrade f1c8e4a7b2d9
```

先在闭门 app 完成：

- `/health`、`/health/db`；
- 管理员读取三个展示口径；
- 普通账号可读取但不能修改；
- 项目页在线请求不携带导出日期；
- 订单 Excel、单本、批量 ZIP、往返模板四类下载；
- 贡献毛利在没有完整水位的合同上继续失败关闭；
- 日志无 5xx、迁移错误、重复键、连接泄漏或内存异常。

闭门验收通过后才恢复 frontend。

## 8. 观察窗口

开放后至少观察 30 分钟，并在 0、5、15、30 分钟记录：

- 三个容器状态与精确镜像 ID；
- `/health`、`/health/db`；
- 5xx、409、413、429 数量；
- 数据库连接、锁等待、CPU、内存、磁盘；
- 导出临时文件是否回收；
- `maint_roundtrip` 批次成功/失败数；
- 成本来源计数与 `none` 数是否异常跳变；
- 贡献毛利完整合同数是否只随合法全量回填增加。

观察期间任一 P0/P1 数据错误、越权、部分写入或不可恢复导入出现，立即断流。

### 8.1 原始归档孤儿文件巡检

数据库事务与文件系统不能原子提交。导入会先发布按 SHA-256 命名的原始文件，再提交
`sys_raw_file`；如果数据库提交明确失败或提交结果未知，磁盘上可能留下无数据库引用的
文件。不得在请求异常路径直接删除，因为“提交成功但客户端丢失 ACK”时数据库引用可能
已经存在。

发布完成后先执行默认 dry-run：

```bash
EVIDENCE_DIR="$PWD/backups/v1.19-dev15-evidence-${TARGET_COMMIT}"
mkdir "$EVIDENCE_DIR" \
  || fatal "DEV-15 证据目录已存在或无法创建，禁止覆盖：$EVIDENCE_DIR"
chmod 700 "$EVIDENCE_DIR"
save_state EVIDENCE_DIR "$EVIDENCE_DIR"

sudo docker compose exec -T app \
  python -m scripts.raw_archive_gc --grace-days 7 \
  | tee "$EVIDENCE_DIR/raw-archive-gc-dry-run.json"
```

命令只扫描严格早于 7 天、名称为 64 位小写十六进制 SHA-256 加 `.xlsx` 的普通文件。
它在与导入相同的 `DATA_CHANGE_ADVISORY_LOCK_KEY` 下，用独立只读数据库事务确认
`sys_raw_file.file_hash` 和 `storage_path` 在所有导入类型中均无引用。符号链接、非普通
文件、摘要不符、文件变化、数据库或 I/O 状态不确定时一律保留。
CLI 和服务层都把 7 天作为不可放宽的最小安全窗口；`--grace-days` 小于 7 或大于
3650 会在读取数据库和扫描目录前失败关闭并返回非零退出码。禁止为追求清理速度缩短该窗口。

dry-run 证据必须包含以下字段：

```text
dry_run
scanned
candidates
referenced
deleted
deleted_bytes
skipped
errors
```

硬断言：`dry_run=true`、`deleted=0`、`deleted_bytes=0`、`errors=0`。若
`candidates>0`，先核对生产备份、数据库引用和磁盘水位；确认后才允许显式执行：

```bash
sudo docker compose exec -T app \
  python -m scripts.raw_archive_gc --execute --grace-days 7 \
  | tee "$EVIDENCE_DIR/raw-archive-gc-execute.json"
```

执行结果必须满足 `dry_run=false`、`errors=0`，并归档 `deleted` 与
`deleted_bytes`。退出码非零或 `errors>0` 时不得重试放宽条件、不得手工 `rm`；保留文件
并排查数据库/磁盘状态。

上线稳定后由运维调度器在低峰期每周执行一次相同的 `--execute --grace-days 7` 命令，
每次保存完整 JSON、目标镜像 ID、开始/结束时间和退出码。每月人工复核一次最近四份记录；
若连续两次 `errors>0`、孤儿数量突增或删除字节异常，暂停定时执行并按导入故障处理。

## 9. 回滚边界

### 尚无 DEV-15 写入

如果仅完成迁移/重算，尚未发生往返工作簿写入、人工成本或新报销写入，可按 DEV-14 的停写回滚流程降级到旧 head。降级前仍须制作事故后备份。

### 已有 DEV-15 写入

一旦存在以下任一事实，禁止直接 `alembic downgrade`：

- `maint_roundtrip` 成功批次；
- 人工成本记录；
- 双税报销新增或更新；
- 合同完整水位 revision 变化；
- 管理员三域展示策略变化。

这些数据在旧 schema 中没有等价表示。优先顺序：

1. 保持数据库在 `f1c8e4a7b2d9`，断流后前向修复；
2. 若旧应用已验证可在新 schema 上只读运行，可临时回退应用镜像但冻结所有导入、重算和工作簿功能；
3. 只有在导出新表、新列、设置和审计的完整私密快照，并由数据库负责人批准可重放方案后，才允许 schema 降级。

禁止为了快速回滚恢复发布前备份覆盖已发生的业务写入。
