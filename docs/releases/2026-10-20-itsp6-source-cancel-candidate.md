# ITSP-6 已取消影响：候选验收与回退

决策: D-34

本文件为发布准备，不代表合并或部署。基线为 PR #425 的 `0ff4ffe`（含 main `32ab2a6`），候选分支 `feat/cancel-cascade-confirm`。开发验证见 [实施计划](../plans/itsp6-cancel-cascade.md)。本轮无生产访问、无推送或 PR。

## 一、能力与边界

项目面板“备件与需求单”新增独立“已取消影响”。来源状态仅“已取消”可执行；草稿、进行中、空值没有取消候选，其他未知非生效文字只告警。每次确认一张明确选择的单头，需求行和精确关联领用在同一事务中软作废；不能按 PN、数量或单号猜关联。

成功 upsert 后保存不可变单头状态证据。旧历史没有新证据时不可执行；skip 批次不生成可执行候选，也不覆盖此前合法 upsert 形成的当前单头证据。部署不处理历史 76 张已取消单，不新增自动任务、不回填、不打开 cutover。

确认要求 D-12 作废动作权、实名账号、项目范围、非空原因和最新影响摘要；锁内重新鉴权和核对。409 要求重新查看；网络未知保留同一请求重试。回放显示原确认结果，不宣称数据现在仍处于该状态，也不再次处理新增或恢复行。

## 二、候选构建验收

用户使用前后端同一候选 SHA 的独立验收环境，按 [测试场景](../plans/itsp6-cancel-cascade.md#公共-seam-与验收场景) 实际点按：

1. 上载合成已生效需求及领用/返还，随后以 upsert 上传已取消；确认前领用保持有效。
2. 项目卡片查看具体需求、可读领用单号、精确关联依据和无法关联项，填写原因确认；仅精确集合软作废，返还和库存原数保留。
3. 切换草稿、进行中、空值、未知“已作废”和无证据旧记录，均不能执行，未知文字有明确人工提示；skip 批次不生成可执行候选。
4. 两人同时编辑/确认，旧摘要得到409；无权/越项目403。断网后重试沿用原请求，不重复作废。
5. 通过合法 upsert 将来源单头重新上传为已生效：未确认需求恢复可见；经人工确认的软作废行与墓碑不复活。实名恢复/更正仍走既有权限路径，墓碑恢复不会自行重建归属或恢复子行。
6. 320px/390px 核对长PN、详情横向滚动、原因输入、按钮、失败恢复和账号切换。

代理浏览器只提供开发调试证据，不替代用户点按验收。

本地前端完整链已通过（1563项）；后端相关回归109项、提交前定向75项通过，详细日志见实施计划。按后续 lane 新规则，后端全量交 CI，本地全量在1044通过、2跳过、0失败时由执行方中止；不得以此宣称后端全量通过。

## 三、迁移与兼容

无新增表或 Alembic revision，head 仍为 `c9d4f2a6b8e1`。状态证据和追加式确认回执分别保存在 `sys_import_batch.report_json` 的私有键 `_wbdd_source_status_snapshot` / `_source_cancel_confirmations`；公开上传历史过滤私有键。原件归档、旧身份快照、成本证据不改写。

确认会留下现有需求软作废字段、领用版本/事件/审计、需求墓碑和停用归属；真实返还、库存、采购、报销和回款不删除不冲减。账本审计与回执必须随正常数据库备份保留。

## 四、发布与回退

main 合并仍须 @Jinchen-Yang 对精确候选 SHA 的人工 APPROVED review，用户另行明确“开始部署”后才能进入生产流程。届时按仓库部署 runbook 完成可读备份、前后端同 SHA、`alembic upgrade head` 后启镜像、`release-` 标签与回读；不得运行任何历史取消转换脚本。

应用回退使用上一已批准版本的同 SHA 前后端；无 schema downgrade。先停止使用新确认入口，保留新证据、回执与已执行的软作废事实，不清 JSONB、不删墓碑、不批量重开 `is_active`。若业务要撤销已经人工确认的作废，按既有管理员实名恢复/更正逐项处理；应用版本回退不等于业务状态回滚。

停止条件：范围越权、非已取消可执行、任一实收/库存/成本证据被删除或冲减、漂移发生部分写入、同请求重复执行。出现上述现象停止确认入口并保留审计，准备具体修复候选，不自动恢复数据库或更改生产状态。
