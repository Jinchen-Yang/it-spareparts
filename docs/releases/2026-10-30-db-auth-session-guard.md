# 2026-10-30 鉴权短会话与数据库探针修复

决策: 无（技术故障防护，不改变既有业务口径或权限）

## 事故与修复边界

生产 r142 曾出现 30 个 idle in transaction 连接，业务请求返回 503，
但 `/health/db` 仍错误返回 HTTP 200。现场既有长时间停在 sys_user 的连接，
也有仍执行后续 SQL 的长请求；这不足以证明所有连接都由同一泄漏点导致。

请求入口鉴权现在用同一连接池中的独立短 Session，完成实名停用、token_version、
权限校验并生成普通字典后立即关闭，不持有事务等待业务处理或流式响应。
`verify_token_db(token, db)` 保留，供业务事务内部写前复核使用；撤销级联的写前复核
继续使用本次业务事务，不被入口鉴权清理动作提交或回滚。

仅鉴权事务设置 `SET LOCAL idle_in_transaction_session_timeout = '60000ms'`，
并保留既有 30 秒单条 SQL 限额。事务退出后设置自动恢复；没有数据库/角色级配置变更，
没有修改后台导入、工作簿或业务事务的超时策略，没有自动重试业务写入。
鉴权 SQL 超时返回 504，池满、连接故障或空闲事务被 PostgreSQL 终止返回 503；
SQLSTATE 25P03 的连接失效后不再复用。数据库故障不能被降级为 guest 权限。
数据库探针失败保留安全响应体并返回 HTTP 503，存活探针 `/health` 不变。

这是可验证的连接占用防护，不声称已证明或消除所有长请求的根因。

## 发布与验收

1. 仅在 jinchen-dev/CI 验证；运行 `test_auth_session_lifetime.py`、
   `test_request_db_timeout.py` 及鉴权、权限、撤销级联回归。
2. 跨模型复审、必需 CI 通过后按正常发布流程集成；本修复无需新数据库迁移。
   前后端仍需同一发布提交，备份与当前发布迁移门禁不省略。
3. 生产只读核查探针、业务请求 503/504、连接池等待及 pg_stat_activity 的事务年龄。
   不能只看 `/health`；持续排查仍有 SQL 活动的长事务和慢业务请求。
4. 本修复没有持久化数据库配置变更，回滚按该次发布 runbook 的精确镜像和 schema
   兼容边界执行；回退后鉴权长时间占用连接的风险也随之恢复。

## 契约证据

- 真实 PostgreSQL、pool_size=1/max_overflow=0：业务处理/流式响应仍等待时，
  其他请求已能完成鉴权和业务查询；取消响应时不残留鉴权连接。
- 鉴权成功、拒绝、异常、取消均归还连接；身份权限完全物化，停用及版本变更立即生效。
- 真实 25P03（下条 SQL 或关闭时首次读到）返回 503 并更换连接；
  SET LOCAL 不污染复用连接，不回滚业务未提交内容。
- 原版本以上并发等待/取消及探针契约为红；修复后结果由发布回执记录。
