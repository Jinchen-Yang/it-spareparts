# v1.37 客户需求 Round1（销售/采购分析）发布 runbook——迁移闸门

日期：2026-10-18（上海）。决策：D-39 / D-40 / D-41。来源：#401 复审 S3。

## 范围

prod 当前 alembic 版本 `a40c9e1d7b52`（2026-10-18 只读确认），本轮升级到 head `c9d4f2a6b8e1`，链路：

`a40c9e1d7b52 → baff4b809f12 → 7f73424a7f65 → b8f2d6c4a1e9 → e3a5c7d9b1f4 → a5e8c3f7b2d9 → c9d4f2a6b8e1`

本 runbook 只规定迁移闸门，重点是 `c9d4f2a6b8e1`（快照→订单 FK 显式 `ON DELETE SET NULL` + 补索引、`f_sales_order` business_type 筛选索引 `ix_so_status_btype`）。已对账回填和 06-30 前销售单重导的 dry-run 另行由金臣过目并说「开始部署」后才执行，不在此列。

## 为什么要闸门

`c9d4f2a6b8e1` 在升级事务内用普通 `CREATE INDEX`（非 CONCURRENTLY）建索引，并重建、校验 FK。这些操作都在一个事务里完成，事务结束前一直持锁：
- 建 `ix_so_status_btype` 期间，`f_sales_order` 写入被阻塞；
- FK 校验要扫描 `f_sales_reconciliation_snapshot`，并锁住两表。

迁移自带 `SET LOCAL lock_timeout = '5s'`：拿不到锁就失败回滚，不会无限排队，但升级会中断，需要重试。


基线（2026-10-18）：`f_sales_order` **110,572 行 / 37 MB**；`f_sales_reconciliation_snapshot` **不存在**，由同一次升级中的 `b8f2d6c4a1e9` 新建（`7f73424a7f65` 只是 dim_part 复合索引），因此 `c9d4f2a6b8e1` 执行时它还是空表，FK 校验瞬间完成。在此规模下，`ix_so_status_btype` 预计亚秒级完成，普通升级可接受。

**判定**：
- `f_sales_order` 不超过约 50 万行 / 200 MB，且快照表为空或不存在：按原迁移执行。
- 超出上述规模，或快照表已有大量行（例如环境已部分升级、回填已跑过）：不要直接升级，走闸门 2。

## 闸门 2：大表时拆分（仅当闸门 1 判定需要）

不改已发布的迁移文件语义，改为新增或调整迁移，并经评审：
1. **FK**：`ALTER TABLE f_sales_reconciliation_snapshot ADD CONSTRAINT fk_sales_recon_snapshot_sales_order FOREIGN KEY (sales_order_id) REFERENCES f_sales_order(id) ON DELETE SET NULL NOT VALID;` 在升级事务内完成，只需短锁。之后在单独的事务里执行 `ALTER TABLE f_sales_reconciliation_snapshot VALIDATE CONSTRAINT fk_sales_recon_snapshot_sales_order`；该步只取 SHARE UPDATE EXCLUSIVE，不阻塞读写。
2. **索引**：`CREATE INDEX CONCURRENTLY ix_so_status_btype ...` 和快照表的 `sales_order_id` 索引，都要在 alembic 事务**之外**执行（alembic 中用 `autocommit_block()`），完成后检查 `pg_index.indisvalid`；若无效，`DROP INDEX CONCURRENTLY` 后重建。
3. 拆分后的迁移仍须保持 alembic 单头，并在 staging 恢复库上演练一次。

## 闸门 3：会话超时设置

升级前确认 prod 的会话级超时不会掐断长事务（只读）：

```sql
SELECT name, setting, unit FROM pg_settings
WHERE name IN ('idle_session_timeout','idle_in_transaction_session_timeout','lock_timeout','statement_timeout');
```

基线（2026-10-18，只读）：`idle_session_timeout = 0`（关闭）；`idle_in_transaction_session_timeout = 0`；`lock_timeout = 0`（迁移内用 `SET LOCAL` 改为 5s）。`statement_timeout` 的服务器默认值以发布时查询为准：只读探针会话自己设了 30s，所以本次读到的 30000ms 不是服务器默认值。

若发布时发现 `idle_session_timeout` 或 `idle_in_transaction_session_timeout` 非 0 且短于预计升级时长，在执行 alembic 的会话里用 `SET` 放宽，或按闸门 2 拆分。若 `statement_timeout` 非 0，确认它大于建索引的预计时长。
