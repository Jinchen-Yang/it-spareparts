# 主数据库人工编辑事务修订运行手册（PR #372）

日期：2026-10-15（上海）。决策: D-36。范围：P5-1 旧人工事务核心及本次审查修订。

本文是候选发布、验收与回滚方案，未执行部署，也不表示用户已点按验收。候选分支为
`feat/req00001-master-edit-tx`，本次修订起点为 `f79cb75`；交付时记录最终候选精确 SHA。
本包不新增 Alembic 迁移，不开放商城跨系统写命令、目录发布或图库能力。

## 背景与范围

人工建档和编辑将主数据库字段、品牌/品类字典绑定、规格及审计放在同一事务中。
编辑以稳定 `part_id` 和原始字段快照识别并发修改。字段快照不是持久单调版本，
不能作为未来目录发布水位；`edit-history` 仅展示人工审计，不代表全部写入口历史，
也不提供一键历史恢复。

人工命令与全量 `master_data.refresh` 在父 PN、字典和规格写锁之前取得同一个事务级
advisory lock，串行协调这两类写者。其他治理与 ETL 写入口的完整锁序收敛属于后续
适配；不能据此宣称所有主数据库写路径均已无死锁。人工接口遇到 40P01 时应回滚并
返回可恢复的并发冲突，不能部分提交。

## 破坏性接口变更与调用方兼容

### PATCH `/api/parts/master`

旧的仅传 `pn_std` 与改动字段的请求不再有效。每次编辑必须先通过
`GET /api/parts/master/{part_id}/edit-state` 取得完整快照，然后提交：

```javascript
// snapshot 是打开编辑器时取得的 edit-state 响应对象。
const body = {
  part_id: snapshot.part_id,
  pn_std: snapshot.pn_std,
  base_snapshot: snapshot,
  description: "人工确认的新描述",
};
```

保留 `version_mode`、`identity`、`fields`、`specs` 等原始基线，不从表单默认值重建，
也不能使用提交时现查的值冒充用户打开编辑器时的基线。仅提交用户选定的变更；
字段未传表示不修改，显式 `null` 表示清空。缺少 `part_id` 或 `base_snapshot`、
包含不支持字段时返回 422，不提供绕过基线的兼容入口。

两级品类作为一组：修改大类或小类时，比较两者基线，并同时保护两者；保存后的
文本、字典 ID 和人工来源应一致。不同独立字段可以合并；同字段当前值已等于
本次拟写值时允许成功。真正的字段冲突返回 409，整次修改不生效。

前端在字段冲突后提供“以当前值为新基线并保留我的草稿”操作。用户先核对当前值与
草稿，更新基线后再手动保存；更新基线本身不写资料。若期间又有修改，仍可能再次
409。改名或合并造成的身份冲突必须重新打开对应型号，不能靠刷新字段基线绕过。

### POST `/api/parts/master`（`PartCreate`）

`PartCreate` 使用 `extra="forbid"`。只接受 `pn_std`、`description`、`brand`、
`category_major`、`category_minor`、`machine_or_part`、`unit`、`force`；旧请求中
曾被忽略的其他字段现在会导致 422。尤其不能把编辑用的 `part_id`、
`base_snapshot`、`spec_updates` 或外部操作人的自报字段直接放进创建请求。
创建请求无需编辑基线；硬重名仍不能用 `force` 绕过，近似候选需人工确认独立型号。

### 登录与已知受影响调用方

POST 与 PATCH 都要求有效、非共享回退的实名系统账号，并保留现有主数据库页面
权限检查；没有有效凭据或账号已停用返回 401，没有权限或不满足实名要求（如共享回退身份）返回 403。审计操作人
必须为真实用户名，不能以 `admin` 等角色回填身份。`edit-state` 与 `edit-history`
也受登录与主数据库页面权限控制。

| 调用方 | 影响 | 发布前必须取得的结果 |
|---|---|---|
| 备件主数据页、型号查询内联编辑、`frontend/src/api.ts` 的 `masterEdit` | 编辑请求必须携带稳定 ID 和原始快照；冲突需保留草稿；编辑会话 token 仍绑定原账号 | 使用本候选前后端联合验证，两处编辑入口均覆盖正常保存、冲突与恢复 |
| 私有仓库 `itdata-dsh` 的 `plugins/itdata/lib/operations.js` 中 `part.master_edit` | 已知调用旧 PATCH 契约；需处理 `part_id`、原始基线和实名身份 | **金臣已定不处理 itdata-dsh**（不在本次范围）；本候选不对其做适配 |
| 同文件 `part.master_create` | 需核对请求白名单以及实名身份；附加字段将由 `PartCreate` 拒绝 | **金臣已定不处理 itdata-dsh**（不在本次范围） |
| 其他脚本、保留旧页面的浏览器会话 | 旧编辑请求会 422，共享回退写请求会 403 | 盘点并验证请求形状和身份；通知重载页面、重新打开编辑器，未适配写入口须暂停 |

金臣已定不处理 itdata-dsh；其旧调用在本候选上线后将被拒绝（422/403），不阻塞本候选发布。
尤其不能通过移除基线、放宽未知字段或接受服务/角色身份来恢复旧 AI 写调用。
AI 不得写采购、销售、库存、项目、维保、申请或审批业务状态的红线继续生效。


本地相关测试不能代替发布前的 CI 必需检查、构建或用户验收。验收环境运行精确候选
构建，不要求先合入远期 `test` 分支。由用户安排以下实际点按并登记结论：

1. 有权限的实名账号，在主数据库页面修改描述、品牌、品类（及整机/部件、单位），在型号
   查询内联编辑修改描述与品类（内联编辑不提供品牌；两处页面均不提供参数编辑）；保存后
   回读一致，人工审计记录真实用户名，描述重抽不丢已有参数。
2. 两人同时打开同一 PN，一人只改大类、另一人只改小类；旧基线提交应冲突，不出现
   交叉品类，也不丢失任一人的草稿。只改一个品类字段后，重导不覆盖其配对字段。
3. 两人改同一字段为相同值可以成功；改为不同值时显示三方差异。选择以当前值为
   新基线后草稿仍在，再次手动保存可成功；身份已变化时要求重新打开型号。
4. 编辑与主数据库刷新并发时，不出现未处理 500 或部分字段生效；遇到并发 409
   保留草稿、提示重新核对，不自动盲重放。读取 `edit-state` 不阻塞另一人的保存。
5. 无登录、无主数据库页面权限以及共享回退身份分别验证 401/403；`edit-history`
   不越权。编辑中切换账号，旧请求不覆盖新会话、不清除新账号 token。
6. 用候选合成 PN 验证新建、近似阻挡及确认独立后新建；旧 PATCH 以及创建未知字段
   均明确拒绝。`itdata-dsh` 按金臣决定不处理，不纳入验收。

## 发布顺序（另获“开始部署”授权后执行）

1. 盘点 `itdata-dsh` 以外的旧调用方并确认适配/暂停（金臣已定不处理 itdata-dsh），归档测试与用户点按证据。
   核对 D-36 文档前置、当前 main 基线及最终候选 SHA；两个必需 CI 检查通过，
   取得 @Jinchen-Yang 对该 SHA 的人工 GitHub APPROVED review 后按保护规则合入 main。
2. 用批准的 main 精确提交构建 app/frontend 两镜像，记录 SHA、镜像摘要与上一个
   已验证的成对回退镜像。前后端必须来自同一提交，禁止功能分支直接部署生产。
3. 备份数据库及运行配置，校验备份可恢复，保存切换前快照。安排短停写窗口，暂停
   未适配旧调用方；通知用户结束旧编辑会话，保留必要草稿后重载候选页面。
4. 在停写窗口内先完成候选要求的 `alembic upgrade head`，再启用 app/frontend
   两镜像并恢复流量。本修订未新增 revision/down_revision；以当次批准 main 的
   唯一迁移头为准，不把本手册中的历史基线当作生产 schema 事实。
5. 检查 `/health`、数据库健康、登录、两处编辑、审计和刷新并发；观察
   `field_conflict`、`identity_conflict`、422、401/403、40P01 等错误及用户反馈。
   受影响调用方逐个按已验证方案恢复，记录发布回执并按仓库规则打 `release-` 标签。
   只有真实环境验证后才能登记“已部署”，不能由本地测试推出该结论。

## 回滚与故障恢复

1. 发生异常先停止人工编辑流量和受影响外部写调用，保留失败请求的脱敏信息、
   草稿和审计，不把超时当作已回滚。先查询当前资料及人工历史，确认上一笔是否生效。
2. 将 app/frontend 一起切回事先验证的同提交镜像，旧浏览器会话一并重载。新后端
   配旧前端会拒绝旧请求；旧后端配新前端可能忽略并发基线，均不能作为正常回退组合。
3. 本修订无数据库迁移，不执行 schema downgrade，不删除字段锁、字典、人工规格
   或审计。已提交资料不会随镜像回退撤销；错误资料须由有权限人员核对当前值后，
   通过适用人工入口再次更正并留痕，不能恢复旧整库覆盖切换后发生的业务事实。
4. 原镜像虽可恢复旧调用契约，但同时失去本候选的并发与事务保护；只有暂停未验证
   写调用、明确接受临时限制并完成回退验证后才恢复。优先保留读能力与草稿，前向修复
   后重跑相关契约、构建和用户验收。任何数据库恢复另按明确授权及恢复方案执行。

用户验收人及结果、切换时间、观察结果、回退镜像及是否实际回退；本次均为待执行项。
