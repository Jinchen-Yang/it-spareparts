# v1.20 生产发布 Runbook

本 Runbook 只用于 v1.20 的项目数据、下载中心、日期范围导出、批量工作簿和固定回填
模板增量。生产 checkout 固定保留在 HTTPS 控制面基线
`ab42005b5b94bf98b3db0e4bff87e5df9da2f7ca`；发布脚本从目标 `main` SHA 构建
业务镜像，但不把生产工作树 checkout 到新版本。

## 1. 安全模型

发布控制面必须同时维持以下不变量：

1. 只从已合并、CI 通过的 40 位 `main` SHA 构建。
2. DB、Caddy、edge 配置、ingress 和 loopback 8080 在切流中不可变。
3. `/var/lib/it-spareparts-release-control/v120-state.state` 是唯一状态权威；
   应用目录同名 state 只是可修复镜像。
4. state 是严格 `key=value` ASCII 数据，永远不能 `source`、`.` 或 `eval`。
5. `ROLLBACK_POLICY` 只能从 `old_allowed` 单向变成 `forward_only`。进入
   `opening` 的同一次状态提交完成该锁存；之后不得再启动旧业务镜像。
6. `failed_closed` 只能在 `compose stop` 成功并再次确认 app/frontend 均未运行后
   落盘。无法确认物理停服时保留原阶段并报警，不能伪报已关站。
7. root 控制件和完整 `source.tar` 只来自可信控制机生成、操作员传输的哈希寻址
   包。生产主机禁止从应用账号控制的 `.git/objects`、工作树或 Git ref 生成、
   补全或验证发布源。
8. build、release、observe、rollback 和 root control install 共用 root 创建的
   `/run/lock/it-spareparts-v120` 目录锁；Edge/HSTS 随后再获取持久的
   `/etc/it-spareparts/shared-caddy.lock`，所有共享 Caddy writer 必须保持这一锁序。
9. 每个控制包只安装到
   `/var/lib/it-spareparts-release-control/versions/<manifest SHA>`；
   已存在版本只校验、绝不覆盖。`current` 只通过同目录 symlink rename 原子切换，
   所有 root 入口先重验 manifest 中的全部文件和 `source.tar`。

root authority 首次创建前，操作员必须显式提供与目标 manifest、commit 精确绑定的
一次性 bootstrap authorization；installer 永远不能自行签发。首次 state 落盘时
会同时创建独立的
`/etc/it-spareparts/v120-authority.marker`。marker 存在而 active state 丢失时，
sync helper 必须拒绝新的 generation 0；marker、state、control 三者任一不完整都
必须 fail closed，不得通过删除文件“重新初始化”。

## 2. 上线门禁

开始前必须全部满足：

- 目标 PR 已合并，exact-head CI 与合并后 `main` CI 均通过。
- 后端全量、前端 build/Vitest、发布行为测试、`bash -n`、ShellCheck 均通过。
- 至少两条独立审核均无 P0/P1。
- `https://hbzgc.icu/` 返回 200；HTTP 同路径和查询参数 308 到 HTTPS。
- 当前应用发布阶段仍须保持旧公网 `118.25.94.90:8080` 关闭；宿主机只允许应用
  `127.0.0.1:8080`，不得出现 `10.0.0.11:8080`、通配地址或公网/NAT 监听。
  Issue #178 已单独批准的 redirect-only 最终契约不是应用发布前置条件，只能在应用
  release 与 0/5/15/30 分钟 observer 全部通过后，由 Edge scoped control 建立。
- DB、Caddy、app、frontend 正常且 restart count 无异常；无 `processing` 导入。
- 备份目录为 `700`，dump/checksum 为 `600` 且 checksum、TOC 可验证。
- `docker-compose.yml` 是固定 checkout 的精确内容，`.env` 为应用账号 `600`。

任一门禁失败即停止，不允许“先发再看”。

## 3. 在可信控制机生成并传输 root 控制包

以下步骤在已审核的本地工作树执行，不在生产应用目录执行：

```bash
TARGET_COMMIT='<合并后 main 的 40 位 SHA>'
test "$(git rev-parse origin/main)" = "$TARGET_COMMIT"
git fsck --strict --no-reflogs "$TARGET_COMMIT"

PACKAGE_PARENT=$(mktemp -d)
.deploy/package_v120_control.sh "$TARGET_COMMIT" "$PACKAGE_PARENT"
PACKAGE_DIR=$(find "$PACKAGE_PARENT" -mindepth 1 -maxdepth 1 \
  -type d -name 'it-spareparts-control-*' -print -quit)
MANIFEST_HASH=$(sha256sum "$PACKAGE_DIR/manifest.txt" | cut -d' ' -f1)
INSTALLER_HASH=$(sed -n 's/^INSTALLER_SHA256=//p' "$PACKAGE_DIR/manifest.txt")
SOURCE_TAR_HASH=$(sed -n 's/^SOURCE_TAR_SHA256=//p' \
  "$PACKAGE_DIR/manifest.txt")
test "${#MANIFEST_HASH}" = 64
test "${#INSTALLER_HASH}" = 64
test "${#SOURCE_TAR_HASH}" = 64
test "$(sha256sum "$PACKAGE_DIR/source.tar" | cut -d' ' -f1)" \
  = "$SOURCE_TAR_HASH"
test "$(git get-tar-commit-id < "$PACKAGE_DIR/source.tar")" \
  = "$TARGET_COMMIT"

scp -r "$PACKAGE_DIR" it-spareparts-prod:/var/tmp/
```

仅在三项权威证据从未创建的首次 bootstrap，已认证 SSH 操作员显式签发一次性
authorization。生产当前可能还保留 HTTPS 上线阶段的单文件 control 目录；以下命令
只接受“完全不存在”或经文件数、owner/mode、hardlink 数和 SHA-256 精确确认的
`rollback-now.sh`，并把后者原子归档。任何 state、marker、authorization 或其他
control 内容都必须失败，先人工恢复权威证据，禁止删掉后重跑：

```bash
ssh it-spareparts-prod sudo bash -s -- \
  "$MANIFEST_HASH" "$TARGET_COMMIT" <<'ROOT'
set -Eeuo pipefail
umask 077

authorization_created=0

trap 'exit 129' HUP

test ! -e "$marker" && test ! -L "$marker"
test ! -e "$authorization" && test ! -L "$authorization"

  test "$(sha256sum "$legacy" | cut -d' ' -f1)" = "$legacy_hash"
  mv -T -- "$control" "$legacy_archive"
  legacy_moved=1
  sync -d /var/lib

  printf 'AUTHORIZATION_FORMAT=v120-bootstrap-1\n'

chmod 600 "$temporary"
```

命令成功后，旧 HTTPS rollback helper 只保留在上述固定 archive 路径。本段
bootstrap 失败且 shell trap 可执行时会自动移回原位；后续 installer 是独立 SSH，
失败时保持 fail-closed，不会触发本段 trap。如确需回退 HTTPS，必须从固定 archive
路径直接执行已验明的
`sudo /var/lib/it-spareparts-release-control.https-legacy-1d377dea5058/rollback-now.sh`，
不能假设旧 control 路径仍存在。
SIGKILL/掉电发生在原子 rename 之间时，业务容器不受影响，但必须按两个固定路径的
实际存在情况人工恢复，不能继续初始化。

随后把 installer 复制到 root 私有临时文件，并按可信控制机记录的精确 hash 校验。
不要直接 `sudo` 执行 `/var/tmp` 中的应用账号文件。升级已有 authority 时跳过上面的
authorization 签发，但仍执行同一安装流程：

```bash
ssh it-spareparts-prod sudo bash -s -- \
  "$MANIFEST_HASH" "$INSTALLER_HASH" <<'ROOT'
set -Eeuo pipefail
umask 077
manifest_hash=$1
installer_hash=$2
[[ "$manifest_hash" =~ ^[0-9a-f]{64}$ ]]
[[ "$installer_hash" =~ ^[0-9a-f]{64}$ ]]

test -f "$source_file"
test ! -L "$source_file"
test "$(stat -c '%h' "$source_file")" = 1
trusted_copy=$(mktemp /root/install-v120-control.XXXXXX)
cleanup() {
  status=$?
  trap - EXIT HUP INT TERM
  rm -f -- "$trusted_copy"
  exit "$status"
}
trap cleanup EXIT
trap 'exit 129' HUP
trap 'exit 130' INT
trap 'exit 143' TERM
timeout 10 dd if="$source_file" of="$trusted_copy" \
  iflag=nofollow,fullblock bs=262145 count=1 status=none
test "$(stat -c '%s' "$trusted_copy")" -le 262144
test "$(sha256sum "$trusted_copy" | cut -d' ' -f1)" = "$installer_hash"

bash -n "$trusted_copy"
"$trusted_copy" install "$manifest_hash"

```

installer 会先用原子 `mkdir` 创建共享目录锁；若路径已存在，只验证其为
`750 root:ubuntu` 的真实目录，绝不通过 `install -d`、`chown` 或 `chmod` 修复
symlink。上传包会先复制进 root 私有 staging，再校验 manifest、九个固定控制件和完整 `source.tar`，
持久化到不可变的 `versions/<manifest SHA>` 后，最后一次原子
rename 更新 `current`。掉电发生在 rename 前仍指向完整旧版本，发生在 rename 后只
可能指向完整新版本；下次使用仍会重验整个 manifest。

## 4. 一次性迁移 cron

root 控制包安装不会自动发布 cron，避免与现有 user crontab 形成重复窗口。生产当前
旧 crontab 必须精确等于以下两行；若还有其他任务，停止并人工合并，不能整表覆盖：

```text
0 3 * * * /home/ubuntu/apps/it-spareparts/backup.sh >> /home/ubuntu/apps/it-spareparts/backup.log 2>&1
*/5 * * * * /home/ubuntu/apps/it-spareparts/.deploy/monitor.sh
```

在明确无其他人编辑 crontab 的维护窗口执行：

```bash
ssh it-spareparts-prod sudo bash -s -- "$MANIFEST_HASH" <<'ROOT'
set -Eeuo pipefail
umask 077
manifest_hash=$1
control=/var/lib/it-spareparts-release-control
test ! -e /etc/cron.d/it-spareparts
test ! -L /etc/cron.d/it-spareparts
expected=$(mktemp)
archive=
archive=$(
  mktemp "$control/archive/legacy-crontab-$(date +%Y%m%d%H%M%S).XXXXXX.txt"
) || {
  result=$?
  rm -f -- "$expected" || result=97
  exit "$result"
}
archive_captured=0
cleanup() {
  status=$?
  result=$status
  trap - EXIT HUP INT TERM
  if [ -n "$expected" ] && ! rm -f -- "$expected"; then
    result=97
  fi
  if [ "$status" -ne 0 ]; then
    if ! rm -f -- /etc/cron.d/it-spareparts; then
      result=97
    fi
    if [ "$archive_captured" = 1 ]; then
      if ! crontab -u ubuntu "$archive"; then
        result=97
      fi
    elif ! rm -f -- "$archive"; then
      result=97
    fi
    if ! systemctl start cron; then
      result=97
    fi
    if [ "$archive_captured" = 1 ]; then
      if ! crontab -u ubuntu -l | cmp -s - "$archive"; then
        result=97
      fi
    fi
    if ! systemctl is-active --quiet cron; then
      result=97
    fi
  fi
  exit "$result"
}
trap cleanup EXIT
trap 'exit 129' HUP
trap 'exit 130' INT
trap 'exit 143' TERM
cat > "$expected" <<'CRON'
0 3 * * * /home/ubuntu/apps/it-spareparts/backup.sh >> /home/ubuntu/apps/it-spareparts/backup.log 2>&1
*/5 * * * * /home/ubuntu/apps/it-spareparts/.deploy/monitor.sh
CRON
systemctl stop cron
crontab -u ubuntu -l > "$archive"
chmod 600 "$archive"
test "$(stat -c '%U:%G' "$archive")" = root:root
cmp -s "$archive" "$expected"
crontab -u ubuntu -l | cmp -s - "$archive"
sync -f "$archive"
sync -d "$control/archive"
archive_captured=1
crontab -u ubuntu -r
if crontab -u ubuntu -l >/dev/null 2>&1; then
  exit 1
fi
"$control/current/install-v120-control.sh" install-cron "$manifest_hash"
systemctl start cron
test "$(systemctl is-active cron)" = active
"$control/current/install-v120-control.sh" verify-cron "$manifest_hash"
rm -f -- "$expected"
expected=
trap - EXIT HUP INT TERM
ROOT
```

迁移后全系统只能有一份 backup 和 monitor 定时任务。installer 会同时扫描
`/etc/cron.*`、`/etc/anacrontab`、全部用户 crontab、system/user unit 目录，以及
当前 system/user manager 已加载的 timer 和其触发 unit；任何其他入口引用项目
backup/monitor 都会阻断。若脚本失败，会删除尚未确认的 cron.d 文件、恢复已核验的
旧 crontab 并重启 cron。cleanup 中每个恢复动作都在受控条件语句内执行；某一步
失败只会把最终状态提升为 `97`，不会跳过后续恢复和服务启动。任何非零退出后仍须
从第二个 root 会话核验 cron.d 文件、ubuntu crontab 和 cron active 状态，不能盲目
重跑迁移。只有已与预期内容和二次读取逐字节核对，并完成文件与父目录 fsync 的
durable archive 才能用于自动恢复和后续删除旧 crontab；捕获失败、未验证或未持久化
的临时 archive 会被删除，不能回写部分输出。

## 5. 从可信 root source tar 构建候选镜像

生产应用账号不得读取 Git 对象来生成 source tar，也不得从生产 checkout 解出工具。
root 先重验当前完整控制版本，再从 root-owned `source.tar` 解出只读工具到 `/run`，
随后降权给应用账号，通过已核验的绝对路径 `/usr/bin/bash` 解释执行。生产 `/run`
允许挂载 `noexec`，不能把其中的脚本作为可执行文件直接启动：

```bash
TARGET_COMMIT='<同一个 40 位 SHA>'
[[ "$TARGET_COMMIT" =~ ^[0-9a-f]{40}$ ]] || exit 1
[[ "$MANIFEST_HASH" =~ ^[0-9a-f]{64}$ ]] || exit 1
ssh it-spareparts-prod sudo bash -s -- \
  "$MANIFEST_HASH" "$TARGET_COMMIT" <<'ROOT'
set -Eeuo pipefail
umask 077
manifest_hash=$1
target_commit=$2
control=/var/lib/it-spareparts-release-control/current
"$control/install-v120-control.sh" verify "$manifest_hash"
test "$(sed -n 's/^TARGET_COMMIT=//p' "$control/manifest.txt")" \
  = "$target_commit"
tools=$(mktemp -d /run/itdata-build-v120.XXXXXX)
cleanup() {
  status=$?
  trap - EXIT HUP INT TERM
  rm -rf -- "$tools"
  exit "$status"
}
trap cleanup EXIT
trap 'exit 129' HUP
trap 'exit 130' INT
trap 'exit 143' TERM
mkdir -m 755 "$tools/.deploy"
for name in build_v120.sh v120_state.sh; do
  tar -xOf "$control/source.tar" ".deploy/$name" \
    > "$tools/.deploy/$name"
  chown root:root "$tools/.deploy/$name"
  chmod 555 "$tools/.deploy/$name"
  bash -n "$tools/.deploy/$name"
done
# 先完整解出依赖，再从可信根目录解析 `# shellcheck source=.deploy/...`。
cd "$tools"
for name in build_v120.sh v120_state.sh; do
  shellcheck -x "$tools/.deploy/$name"
done
chmod 755 "$tools"
sudo -u ubuntu /usr/bin/bash "$tools/.deploy/build_v120.sh" "$target_commit"
ROOT
```

记录输出中的绝对 `STATE`，禁止用“最新文件”、通配符或目录扫描代替。build 不改变
canonical image ref，也不重建在线容器；它只固化 root source tar/checksum 证据，
从 root-owned 只读 context 构建 candidate images，并生成 generation 0 built
state。built state 通过同目录 `renameat2(RENAME_NOREPLACE)` 语义发布，最终文件
始终只有一个 hard link；并发创建同名 state 时保留原文件并失败，不再使用
“先 hardlink、后 unlink”的崩溃窗口。

已有 root authority 后，每次补丁都必须显式链接父 release。合法父状态仅为
`observed`、`failed_closed` 或 `rolled_back`：

把上述最后一行改成：

```bash
sudo -u ubuntu /usr/bin/bash "$tools/.deploy/build_v120.sh" \
  "$target_commit" --supersedes '<父 RELEASE_ID>'
```

`observed` 后继把父 target 与父 candidate image 作为旧业务 rollback base，并重置
为 `old_allowed`；build 必须证明当前运行 CID 的镜像与父 authority 一致。
`failed_closed` 后继继承 `forward_only`，要求 app/frontend 和 8080 均保持关闭；
`rolled_back` 后继使用父旧业务 source/image 并继续 `old_allowed`。父 state 的精确
SHA-256 和 attempt 序号写入新 state，root sync 只接受相邻 attempt，并把旧 authority
归档后再切换。`prepared`、`backup_verified`、`opening`、`switched` 一律拒绝。

严格顺序是：应用 release → 应用 0/5/15/30 分钟 observer（公网 8080 仍关闭）→
Edge scoped drill/final → HSTS scoped drill/final → 最终 Edge/HSTS 0/5/15/30
分钟观察。Edge 建立后才允许 `10.0.0.11:8080` redirect-only 监听；HSTS 从 300
提升到 31536000 必须最后按
[`edge-v120-scoped-runbook.md`](edge-v120-scoped-runbook.md) 执行。

## 6. 解出发布工具并切流

```bash

[[ "$TARGET_COMMIT" =~ ^[0-9a-f]{40}$ ]] || exit 1
[[ "$MANIFEST_HASH" =~ ^[0-9a-f]{64}$ ]] || exit 1
[[ "$STATE" =~ ^/home/ubuntu/apps/it-spareparts/backups/v120-[0-9a-f]{12}-[0-9]{14}\.state$ ]] \
  || exit 1

# STATE 和 source artifacts 位于生产主机；这段必须通过 SSH 远程校验，
# 不能在可信控制机上把生产绝对路径当成本地路径检查。
ssh it-spareparts-prod sudo bash -s -- \
  "$STATE" "$TARGET_COMMIT" <<'ROOT'
set -Eeuo pipefail
state=$1
target_commit=$2
[[ "$target_commit" =~ ^[0-9a-f]{40}$ ]]

sudo -n journalctl -u cron --since "1 minute ago" --no-pager -n 1 >/dev/null
sudo -n journalctl -u cron --since "1 minute ago" --no-pager >/dev/null'

  "$MANIFEST_HASH" "$STATE" <<'ROOT'
set -Eeuo pipefail
umask 077
manifest_hash=$1
```

上述 root session 在切流成功后立即进入 30 分钟 observer，并在 observer 结束后才清理
root-owned 只读工具目录。第 7 节的只读业务验收应在观察窗口内从另一终端并行执行。

release 持有共享锁并按以下顺序执行：

1. 验证 state、source、root control manifest、candidate/rollback image ID。
2. 验证固定 Compose 身份、DB/Caddy、edge checksum、ingress 与 8080 边界。
3. 在重建 release evidence 前验证 root authority：同 release 必须仍与 generation-0
   built state 逐字节相同；不同 release 必须满足正式 supersession 规则。
4. evidence 使用绑定 `RELEASE_ID`、目标 commit 和 built state SHA-256 的私有 marker。
   如果进程在 root `built` 提交前后被 SIGKILL 或掉电，重跑同一个精确 state 会先
   校验 marker，再只清理该 release 的证据 staging 并重新生成；未标记目录、symlink、
   mount point 或身份不匹配目录一律拒绝，不能触碰业务文件。
5. 私有保存新旧镜像 bundle；分组安装 backup/monitor。
6. 把 built proposal 提交为 root authority，并同步应用镜像。
7. 进入 `prepared`，停止 app/frontend；DB/Caddy 不停止、不重建。
8. 新建 hardened backup，校验 checksum/TOC，并在 `--network none` 的受限容器中
   完整恢复，对比 Alembic head 与核心表计数。
9. 进入 `backup_verified`，只启动 candidate app，验证 `/health` 和 `/health/db`。
10. root state 先原子进入 `opening`，同时把 policy 锁为 `forward_only`，然后才启动
   frontend。
11. 验证 HTTPS、loopback 8080、ingress、DB/Caddy 不变；monitor 通过后再次验证
   全系统 backup/monitor 唯一，再进入 `switched`。

`old_allowed` 的 `prepared`/`backup_verified` 失败会在同一锁内恢复旧业务。
`forward_only` 的任一失败只会物理停服并进入 `failed_closed`。root authority
丢失或损坏一律停止自动恢复，不能启动旧后端。

state codec 与可重试 evidence staging 生命周期中的 rename、文件 fsync 和父目录
fsync 都显式检查返回值，即使函数由 `if !` 或 `||` 调用，也不得依赖 Bash
`errexit` 隐式传播。任一持久化失败必须返回非零，禁止输出完成标记。

## 7. 只读业务验收

禁止调用上传、回填和重算接口，尤其禁止：

- `POST /api/maintenance/roundtrip-import`
- `POST /api/maintenance/recompute`

稳定项目目录搜索必须把搜索词放在 JSON body，不得再把 `q` 放进 URL：

- 无搜索词的目录兼容入口仍为
  `GET /api/maintenance/projects/stable` 和
  `GET /api/maintenance/projects/stable/operations`。
- 有搜索词时只调用 `POST /api/maintenance/projects/stable/search` 或
  `POST /api/maintenance/projects/stable/operations/search`；旧 GET 入口一旦出现
  `q`（包括空值）必须返回通用 422，且不得产生稳定项目目录应用审计记录。
- 合法 `reminder` 仅限已声明的类型、规则枚举，以及
  `manager_update:YYYY-MM` 受控语法；未知值返回通用 422，不回显原值，也不写
  应用审计。旧 `/maintenance/reminders` 跳转和合法 reminder 深链必须继续可用。

发布候选的日志隐私口径必须逐层验证：

- frontend Nginx 使用 `safe_path` access format，只记录 method、`$uri`、status、
  bytes、request/upstream timing；格式中不得出现 `$request`、`$request_uri`、
  `$args`、`$query_string` 或 Referer。`nginx -t` 必须通过。
- `/api` location 的 Nginx `error_log` 必须写入 `/dev/null`：该日志格式不可定制，
  上游断连/超时时可能带入含 query 的完整 request line。502/504 状态与耗时仍由
  `safe_path` access log 保留，业务行为由后端审计与监控覆盖。故障门禁必须实际让
  后端不可达，以唯一敏感哨兵请求旧 GET，并确认容器日志只有无 query 的路径和状态。
- backend Uvicorn 以 `--no-access-log` 启动，禁止默认 access logger 把完整 query
  string 写到容器日志；业务行为仍由结构化应用审计覆盖。
- backend SQLAlchemy engine 必须启用 `hide_parameters=True`；PostgreSQL 必须保持
  `log_parameter_max_length=0`、`log_parameter_max_length_on_error=0` 和
  `log_statement=none`。允许保留 `log_min_duration_statement=1000` 的慢查询结构与
  时长，但普通、慢查询和错误日志都不得展开 bind 参数。
- `stable_project_directory` 与 `stable_project_operations` 审计只记录
  `searched: true/false` 和非敏感请求范围，不记录 `q` 原文、哈希、十六进制等
  可反推值，也不记录搜索结果 `total`、`returned` 或其他命中数。
- 仓库提供的 Caddy 站点模板不启用 access log。若生产共享 Caddy 在站点外层另有
  全局日志，切流前必须确认正常搜索已经走 POST body，且该日志不会采集请求 body；
  未核实不得宣告日志隐私门禁通过。

用授权下载账号验证：

- `GET /api/maintenance/as-of`
- `GET /api/maintenance/orders/export`
- `GET /api/maintenance/export-workbooks`
- `GET /api/maintenance/export-workbook?contract=...`

订单 XLSX 与批量工作簿 ZIP 覆盖全部、今天、近 7/14/21/30 天、本月、自定义八档。
检查 MIME、`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`、中文

## 8. 0/5/15/30 分钟观察

第 6 节命令已经直接启动 observer，不要从应用账号可写目录重新解包或再次启动。

## 9. 手工恢复边界

手工命令不接受 state 路径，只读取固定 root authority：

```bash
sudo /var/lib/it-spareparts-release-control/current/rollback-v120.sh
```

- `old_allowed + prepared/backup_verified`：可恢复并验证旧 app/frontend，提交
  `rolled_back`。
- `forward_only`、`opening`、`switched`：只停服并确认，提交 `failed_closed`；
  绝不恢复旧镜像。
- `failed_closed`：重复确认停服并修复应用 state 镜像。
- `observed`：明确拒绝回滚且保持健康服务在线。
- `rolled_back`：幂等返回，不重复重建容器。
