# P1-1 品类筛选与需求单原始数量摘要（方案 A 候选）

决策: D-31

按金臣 2026-10-15 本轮裁定，本轮只交付品类筛选、原始下单量 N、实收 R 和数量差额。
**本轮不发布返还状态，不从 N/R 剔除任何免返件，不发布依赖状态的 P4 待返结论。**
完整免返优化留后续，不能根据下单和实收数量推断哪些预购件已经使用或无需返还。
本文件不表示用户已验收、已合入 main 或已部署。

## 范围与数量口径

- 领用、返还列表使用主数据库当前 `DimPart.category_major/category_minor`，在数据库分页前筛选。
  行先按 `part_id = DimPart.id` 关联备件身份，再按两级品类**文本精确匹配**，不按
  `DimPart.category_id`（关联 `ProductCategory.id`）匹配；筛选值沿用 `/parts/categories` 的当前文本选项。
  这是既有列表读侧的展示分类契约，可覆盖尚无标准分类 id 的历史主数据；标准 id 的返还规则
  与冻结义务是独立契约，不能把相同文字当成相同规则，也不为筛选猜测或补写分类 id。
  `category_state=unclassified` 表示已关联主数据但任一级品类为空；`unlinked` 表示未关联主数据。
  不根据 PN 文本猜品类，不改变既有返还要求或冻结义务。
- 领用仍按单头分页，`total` 是匹配单数，返回明细只含命中有效行；
  `total_line_count` 表示整单有效行数。原有整单作废仍影响整单。
  返还收货按行分页，列表与总数使用同一组筛选条件；更换筛选清理选择，刷新保留已执行条件。
- N 是整张有效需求单全部有效明细 `qty` 之和；**NULL 需求数量按 0 计入 N**。
  不扣退货，不取单头自报量、需求净量或领用量。
- R 是精确关联稳定 `source_order_id` 的全部 active 收货，包含全部 PN、来源和件况。
  作废收货不计；未关联收货独立保留，不按项目或 PN 分摊到需求单。
- `line_no_return`、`project_default_no_return`、`category_disk` 三种免返来源均不调整 N/R。
  同型号明细混有应返和免返时仍按整单原始数量核对，不产生免返归属歧义，也不逐行分配收货。
  项目文本提醒、当前标准品类及领用行覆盖均不参与本次数量计算。
- 当前有效且数据完整、N>0 时，差额为 `max(N-R,0)`；
  兼容字段 `pending_qty` 和 `remaining_qty` 只承载此数量差额，不表示待返义务或写入许可。
  纯数量 `over_received_qty=max(R-N,0)` 可保留，R 不封顶，超收不抵其他单的差额。
- 负量、非有限下单数量、无有效明细等情况下 N 为 null；总量为 0（含全部 NULL 按 0 合计）
  保留 `zero_demand_qty/incomplete` 的完整性约定，差额和超收为 null。
  单头、项目失效或无有效归属时不发布确定差额、超收；归属冲突还遮蔽 R 和无日期实收数量，
  不泄露旧项目数量。日期缺失的有效收货计入当前累计，并提示 `undated_receipts`。
- 删除 `return_status`，不产出“收齐／未收齐／已返／未返／无需核对”等新状态；
  删除 `excluded_exempt_disk_*`、`ambiguous_disk_receipt_basis`、`all_exempt_disk`、`not_required`。
  `basis_state` 只表达数据完整性（complete/incomplete/inactive/ownership_conflict），不形成返还结论。

## 接线、消费与契约

需求单列表、详情和项目内需求单列表共享数量摘要，界面只显示“已收 R／下单 N、差额”，
必要时补充超收数量和数据不全原因；只读用户也能查看详情摘要，不扩大写权限。
摘要不进入删除 snapshot/version_digest 或明细 OCC digest，不改变原列表集合、排序、分页或 cutover。
汇总始终检查未恢复墓碑；cutover 关闭时旧列表可能仍有该单，摘要会说明失效。

项目内 `boss_board.project_orders`、需求单搜索与详情对授权后的当前页/单据批量富化
（列表每页最多 200 单，小于汇总上限 500）。摘要读取放在连接级 savepoint 内，
真实数据库查询失败也只回滚该 savepoint，不 flush 草稿或回滚调用方整个事务。
汇总抛出 `ReturnSummaryError` 时记录异常日志，保留 HTTP 200、单据列表、总数及其他列，
各行 `return_summary=null` 且附 `return_summary_error=summary_unavailable`；
详情在响应顶层附同样标记。前端显示“摘要暂不可用”，隐藏不可用数量，不伪造零量。
成功后省略错误标记；无错误的空摘要仍显示待核对。主体读取和权限错误不纳入此降级。
有效墓碑另外附 `tombstoned_order`，与源单头未生效区分；恢复墓碑后该原因消失。

按单汇总每批仍只有一条 SELECT，需求与实收分别聚合后合并；不再读取免返规则或领用覆盖证据。
内部使用 Decimal，响应数量为三位十进制字符串或 null；只读且不 autoflush、加锁或提交。
内部快照保留调用方只读 REPEATABLE READ 保护，汇总数量改名 `known_difference_qty`，
不再输出 `known_pending_qty`。未知数、失效数分列，未知不当零。
由于删除状态与剔除字段等不兼容变化，快照候选标记为 `v2.0-draft`。
本轮遵循金臣方案 A 与修订后的 D-31；集成契约的版本、JSON 示例和快照字段
仍需文档 owner 与当前候选同步，本分支不重复创建决策文件。

已检查 P4 分析服务、页面和 boss_board：P4 尚未接入本次汇总，没有可发布的新待返页签或状态结论。
既有源表自报“已返／待返”列、旧 boss_board 待返关注项不依赖本次 `return_status`，保持各自原标识与口径。
卡墙及 PN 分析仍用同期实际返还／同期实际领用；`receipt_summary` 仍是全部有效实收事实，
旧领用行要求及冻结义务继续独立存在。不能宣称本轮已经统一这些既有指标。

本轮不实施容量守卫、满额候选、领用页内更正、批量应返／免返、导出排序、项目自定义描述或完整免返优化。

## 验证与待用户点按验收

测试使用本机合成数据和 conftest 随机隔离 PostgreSQL 库。共享 :5433 不稳定时使用本会话
`--pull never` 创建的临时 postgres:15 实例；结束按记录的 CID 清理，不修改共享实例。
实际命令、退出码、全量结果和干净 origin/main 对照见 `R/logs/S-A-370A.report.md`。
不得用旧报告通过数替代本轮验证。

待用户在候选构建点按：

1. 在多页领用、返还列表选择大类、小类、未分类、未关联，核对总数、分页、清空和刷新条件。
2. N=5、R 从 2 增至 5：三处均显示原始 N、R 和差额从 3 变为 0，不出现返还状态。
3. 分别有三种来源免返硬盘的单据均保留原始 N/R；同型号应返／免返混合的 N=10/R=9 显示差额 1。
   预购未用件不被免返标记整体剔除；完整免返处理后续另做。
4. NULL+3 显示 N=3；全部 NULL 显示 N=0 和数量完整性提示；负量、无行、失效、归属冲突不伪造差额。
5. A 单 N=2/R=3 保留超收 1，B 单 N=4/R=0 保留差额 4；切项目或筛选后不串数据，其他事实保存后正常读回。
6. 项目列表、需求列表和详情汇总暂不可用时仍能查看主体数据，摘要显示“摘要暂不可用”；
   刷新恢复后重新显示数量，不能把不可用读成 R=0。
