# v1.35.0 开支按项目 / 销售主档口径 / 项目墙筛选 URL 化

> 状态：方案定稿（2026-09-17），实现与验证见后续章节。

## 一、需求背景（甲方原话）

> 「还有个小问题 能看到具体是那个项目的开支吗」
> 「销售名称有点bug 比如联通 销售我已经改成王俊凯了 但是统计的时候还是王小环」
> 「搜索维保订单后进入具体项目 回退的时候能不能还是回到搜索后的界面 比如我按照算力运维搜索 退回去去以后还是算力运维，返回项目墙的时候能不能按照筛选以后的返还呢」

## 二、现状与根因（定位）

| # | 现象 | 根因 |
|---|---|---|
| N1 | 开支统计看不到「哪个项目」花了多少 | `spend_trend` 只按业务类型/销售分组，无项目维度 |
| N2 | 项目销售改成王俊凯，统计仍是王小环 | 统计的销售口径用**订单源列** `f_maintenance_order.salesperson`（导入时的快照）；客户在项目面板改的「销售」落在**项目主档** `maintenance_project.salesperson`（catalog 更新会置 `salesperson_override_active=True`，回填不再覆盖），订单源列不回写 |
| N3 | 进项目再返回，项目墙筛选丢失 | 项目墙全部筛选是组件 `useState`（路由切换即卸载重置）；面板「← 返回项目墙」是固定 `/maintenance` 链接，不带筛选 |

## 三、目标（达成后是什么样）

1. 开支统计新增**按项目汇总**表：项目（可点入项目面板）/ 业务类型 / 含税与未税金额 / 有效数量 / 单数 / 占比；未归属单列一行；与既有合计恒等。
2. 分析页（两个页签）的**销售口径统一改为「有效销售」**：有项目 → 项目主档销售（人工改过即权威，清空即未标注）；无项目 → 订单源销售。`按销售汇总`分组与`销售`筛选（spend-trend 与 pn-ranking）都按此口径。
3. 项目墙筛选（期限 / 业务类型 / 状态 / 排序 / 关键词）写入 URL；浏览器后退、面板「返回项目墙」都回到**筛选后的墙**。

## 四、验收指标

| # | 指标 | 判定 |
|---|---|---|
| A1 | 项目维度 | 按项目汇总之和 == 合计；项目筛选/业务类型/销售/时间等全部筛选同样收窄该表；行可点入项目面板 |
| A2 | 销售口径 | 项目主档=王俊凯、订单源=王小环 → 汇总与筛选只认王俊凯（sp=王小环 查不到）；主档被清空（override）→ 未标注，不回退旧名；主档为空且未人工改过 → 回退订单源值；无项目 → 订单源值；spend-trend 与 pn-ranking 口径一致 |
| A3 | 范围与权限 | 行键范围只收不放；无成本权限金额 restricted、占比 —；排序不泄露成本序 |
| A4 | 墙 URL 化 | `?lifecycle=&business_type=&status=&sort=&q=` 全入 URL；URL 直开恢复筛选；改筛选更新 URL；默认行为与现在完全一致（默认六档全选等） |
| A5 | 返回 | 墙（筛选 算力运维）→ 项目面板 → 浏览器后退 / 「返回项目墙」→ 墙仍按算力运维筛选；直达面板无历史时返回退化为默认墙 |
| A6 | 回归 | 后端相关回归、前端全量、构建、CI 通过；v1.34 开支统计与 PN 排名既有行为不回退 |
| A7 | 上线 | 生产迁移头一致、健康、`hbzgc.icu` 版本号 v1.35.0 |

## 五、约束

1. 无数据库迁移；只读聚合与前端状态管理改造。
2. 销售口径变更必须**同时**改 by_salesperson 分组与 `sp` 筛选、同时覆盖 spend-trend 与 pn-ranking，禁止两页签口径分叉。
3. `salesperson_override_active` 是权威标记：人工改过（含清空）后统计不得回退订单源旧值——这正是 N2 的教训。
4. 墙 URL 化不得改变默认行为与既有测试语义；分页/滚动位置不入 URL（甲方要的是筛选保持）。
5. 成本三态信封、行键范围、审计布尔口径沿用 v1.33/v1.34，不放松。
6. 图表与表格规范沿用 charts/README 与既有 statMoney/qtyFmt。

## 六、实现方案

### 6.1 后端（`maintenance_analytics.py`）

1. **有效销售表达式**（两查询共用）：
   `有活跃挂靠 → (override_active ? nullif(btrim(project.salesperson),'') : coalesce(同左, nullif(btrim(order.salesperson),'')))；无挂靠 → nullif(btrim(order.salesperson),'')`。
2. `spend_trend`：
   - `by_salesperson` 分组改用有效销售；
   - `sp` 筛选改对该表达式 icontains；
   - 新增 `by_project` 分组查询（assignment.project_id 分组，join 项目主档取名与业务类型档；未挂靠归 `project_id=null` 行「未归属（无项目）」）；按成本降序（受限时数量序）、上限 200。
3. `pn_ranking`：`sp` 筛选同口径（主聚合 outerjoin 项目主档；既有 business_type EXISTS 显式 `correlate(assignment)` 防止项目被并入子查询）。
4. 响应新增 `by_project`；其余键不变（向后兼容）。

### 6.2 前端

1. `maintenanceAnalytics.ts`：`SpendProjectRow` + `by_project`。
2. 分析页「开支统计」：在按业务类型后新增**按项目汇总**表（项目名 Link 到项目面板；业务类型/金额/数量/占比；客户端分页 20）。
3. `MaintenanceHomePage`：lifecycle/business_type/status/sort/q 改为 `useSearchParams` 派生 + `setSearchParams(..., {replace:true})` 写入；默认值与空选=全选语义不变；关键词草稿本地态、提交入 URL。
4. `MaintenanceProjectPanelPage`：「← 返回项目墙」改为有历史则 `navigate(-1)`，否则回 `/maintenance`（React Router `history.state.idx` 判定）。

### 6.3 同类需求记录（后期）

追加到 issue #328：需求单与数据同步页搜索状态 URL 化（同 N3）；开支统计更多维度（客户/仓库）；老板板与池分析的返回保持。
