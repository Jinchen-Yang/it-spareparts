### 结论

- **无任何破坏性操作**：全链 0 处 `drop_table` / `drop_column`，0 处删除或改写业务事实行；
- 全部 4 处 `drop_constraint`/`alter_column` 均为**约束放宽后重建**（允许新枚举值 / 放宽 nullable），
  旧应用的写入集合是新约束的子集；
- 全部 `execute` 回填分三类：①权限键回填（值 false）②本迁移新列的自身回填
  ③冻结功能表回填（生产为空表）；
- 因此「回滚 = 关 flag，不做 downgrade」的前提成立：**升级后的 schema 对旧应用向前兼容**
  （M5-4 演练第 3 步以生产镜像连升级后灰度库实测验证）。
- 第 15 条（验收补丁 P2）追加在链尾、未改动前 14 条，M0-E 已签署的「整链发布」口径不受影响；
  发布工件的 `DB_TO` 与演练/发布脚本的 `TO_REV` 已同步到 `d6e1f4a8c3b5`——**这一步不能漏**：
  ORM 已映射 `remark`，若生产停在 `c5d9e3f7a2b4`，任何一次报销行查询都会因缺列失败。

### 列槽位上限（`b4c8d2e6f1a3` 专项核查）

Postgres 的「单表最多 1600 列」上限**把已 drop 的列一起算**：`DROP COLUMN` 只把
`pg_attribute` 行标成 `attisdropped`，槽位到表被重建为止都不释放。本迁移一次给
`f_maintenance_order` 加 34 列、`f_maintenance_line` 加 28 列，因此需分别核查：

| 对象 | 迁移前列数 | 迁移后列数 | 距 1600 |
| --- | --- | --- | --- |
| `f_maintenance_order` | 18 | 52 | 1548 |
| `f_maintenance_line` | 34 | 62 | 1538 |

- **生产**：升级只执行一次，无 drop/re-add 循环，余量充裕，**无风险**；
- **测试库**：迁移测试家族每跑一次 `downgrade→upgrade` 就把途经迁移的列加一遍、
  drop 一遍，槽位单调累积。本迁移落在链尾，几乎所有迁移测试都会途经它，整套跑下来
  约 45 轮即触顶，随后某个 `add_column` 报 `TooManyColumns`，该测试的 `upgrade head`
  半途失败、库停在降级态，其后**每个**用例都在 `TRUNCATE` 上炸 `UndefinedTable`
  （实测一次性 366 个 error，把真实失败全埋了）。
  已在 `backend/tests/conftest.py` 的 `db` 夹具加槽位守卫：逼近上限时重建 schema
  并重跑 `upgrade head`（用例间本就 TRUNCATE 全表，重建无损）。这是测试基座的
  无界增长假设，不是本迁移的缺陷，但下一个往热表加列的人同样会踩，故按基座修复。

## 1b. 复审提出但判定「不改」的两项（附理由，便于复核推翻）

| 项 | 复审意见 | 判定 | 理由 |
| --- | --- | --- | --- |
| `supply_deadline` 用 `cleaner.parse_date` 而非 `date_loose` | 建议改用宽松解析器 | **不改** | 同一份氚云 WBDD 导出里，承重的 `order_date` 一直走 `cleaner.parse_date`；`date_loose` 的文档定位是**手填台账工作簿**的容差解析。给同一个文件里的两个日期列配两套方言，比偶尔解析不出更容易出错。解析不出的值记 `rows_display_issue` 并留 `None`，不猜值。 |
| `/api/import/upload` 是第二条不受 flag 约束的 WBDD 写路径 | 建议一并纳入总闸 | **不改** | 该端点是发布前既有的稳定能力（`page_import` 把关），把它纳入新 flag 等于「关 flag 会打断既有导入」——那才真的违反发布契约里的「稳定能力零影响」（`test_maintenance_boss_release_gate.py` 正在看守）。新增的 34+28 列全部 additive-nullable：flag 关闭时它们被写入但无人读取，用户可见行为不变；flag 打开时数据已经就位。真正需要收回的是**本次新增的**写端点（WBDD 专用上传、relink），二者均已在闸内。 |

## 4. 发布工件与执行顺序（plan v1.3 M5-3/M5-4）

| 工件 | 作用 |
|---|---|
| `.deploy/v123_maintenance_boss_manifest.py` | 构建/校验发布包：绑定每个工件 sha256、迁移区间、TARGET_SHA/PARENT_PROD_SHA、四个冻结闸门名 |
| `.deploy/v123_maintenance_boss_rehearse.sh` | 隔离网络演练：恢复冻结备份 → 迁移（总闸强制 false）→ **父生产镜像连新 schema 冒烟** → 总闸关闭时端点整组不可达 |
| `.deploy/v123_maintenance_boss_release.sh` | 阶段闸状态机：preflight → backup → migrate → deploy → canary → observe → commit-release；rollback 只关 flag |
| `.deploy/v123_maintenance_boss_static_test.py` | 无生产访问的静态自检（语法/常量/不变量） |
| `backend/tests/test_v123_maintenance_boss_release_control.py` | 用 stub docker 真实驱动上述脚本，锁死三条不可协商规则 |

执行顺序：

```bash
# 0) 静态自检（任意机器）
python3 .deploy/v123_maintenance_boss_static_test.py

# 1) 打包并校验（TARGET_SHA=本次发布提交，PARENT_PROD_SHA=当前生产提交）
python3 .deploy/v123_maintenance_boss_manifest.py build \
  --source-dir .deploy --target-sha <TARGET_SHA> --parent-sha <PARENT_PROD_SHA> \
  --out /tmp/v123-package
python3 .deploy/v123_maintenance_boss_manifest.py verify --package-dir /tmp/v123-package

# 2) 演练（冻结备份 + 当前发布镜像 + 父生产镜像）
.deploy/v123_maintenance_boss_rehearse.sh <DB_DUMP> <TARGET_SHA> <PARENT_PROD_SHA> \
  <APP_IMAGE_ID> <PARENT_APP_IMAGE_ID> /tmp/v123-rehearsal

# 3) 生产按阶段推进（每步都写状态文件，跳阶段/重复/回退一律拒绝）
.deploy/v123_maintenance_boss_release.sh preflight      /var/lib/v123.state /tmp/v123-package
.deploy/v123_maintenance_boss_release.sh backup         /var/lib/v123.state /var/backups/v123
.deploy/v123_maintenance_boss_release.sh migrate        /var/lib/v123.state
.deploy/v123_maintenance_boss_release.sh deploy         /var/lib/v123.state
.deploy/v123_maintenance_boss_release.sh canary         /var/lib/v123.state
.deploy/v123_maintenance_boss_release.sh observe        /var/lib/v123.state 60
.deploy/v123_maintenance_boss_release.sh commit-release /var/lib/v123.state

# 回滚（任何阶段之后均可执行；不做 downgrade）
.deploy/v123_maintenance_boss_release.sh rollback /var/lib/v123.state
```
