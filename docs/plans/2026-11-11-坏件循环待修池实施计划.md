## 2. 数量账本怎么才不用推倒重来

待修、已上电商、废品都是查询结果，不设可修改的余额列。

- 待修 = 合格坏返件数 − 有效扣数。
- 已上电商 = 有效结果的 `fixed_qty`（含还没送达的推送）。
- 废品 = 有效结果的 `scrap_qty`。
- 作废只把结果标成 `voided`。扣数行留着做审计，统计时排除。

以后加能力时只加旁边的表或视图项，不改这三列的含义，也不把扣数行改造成工位。

| 以后的能力 | 扩展点 | 不做什么 |
| --- | --- | --- |
| 委外、派工、维修中 | 另建占用表（PN、件数、原因、外部单号），视图里从待修再减去占用。扣数仍只在填写结果时发生 | 不把工位枚举加回结果表 |
| SN | 旁表 `(record_id, receipt_id, sn)`。本期请求 `extra=forbid`，多一个字段即 422 | 不把 SN 放进出站载荷。内部身份继续是结果 id + 返还行 id |
| 自动回冲商城 | 作废事务里可以再插一张回冲 outbox，键为 `delivery_id`。本期的函数边界是 `attest_manual_shop_reduction`：只检查勾选，不发 HTTP。以后的开关默认关闭，本计划不添加该设置 | 不在作废时改扣数行的 `qty`，也不在本期调用商城减库存 |
| 回公司 / 内部采购 | 走普通采购进入 itsp 库存，与本账本无关 | 不增加第三种结果数量 |
| 售出、未发货取消 | 以后的分配表只引用 `delivery_id` 和订单行，不更新 `fixed_qty`。已上电商表示「已经交出」，不表示「商城还剩多少」 | 本期 `mark-sold` 不写这张表 |
| 真实闲鱼发帖 | 仍在商城，四个开关维持默认关闭 | itsp 不编造闲管家参数 |

合格件数的判断集中在一个 SQL 函数里，网页改单、重新导入和触发器都调用它，避免视图和接口各写一套。

## 3. 锁、重试、失败

### 3.1 锁顺序

现有改单先拿共享 `DATA_CHANGE` 顾问锁，再锁返还行。新的维修顾问锁按 `part_id` 升序，插在行锁之前，避免「提交持有 PN 锁等待行、改单持有行等待 PN 锁」。

1. 共享 `lock_receipt_context()`。
2. 本次涉及的 `part_id` 升序独占顾问锁。改单若会换 `part_id`，旧值和新值都锁。提交只锁请求里的那一个。
3. 按 `rkd_line_id` 升序 `FOR UPDATE` 锁返还行。
4. 再锁这些行上的扣数行和对应意图行。
5. 检查不变量，然后写入。

`update_receipt` / `void_receipt` 今天在 `_load_receipt(..., lock=True)` 里先锁行。S1 要改成：先按主键读出 `part_id`（不加行锁），完成第 2 步，再锁行。锁行之后若 `part_id` 已经变了，补锁新的 `part_id` 并重新读行。不要在已经持有行锁之后再去等 PN 顾问锁。

提交分配的读取顺序是 `occurred_at NULLS LAST, rkd_line_id`。加锁顺序仍是 `rkd_line_id`，两者不要混用。

语句超时 5 秒、锁超时 1 秒，与出站领取一致。锁超时返回契约里的 409。

重新导入已经在 API 层调用了 `lock_receipt_context`。`apply()` 在改行之前补第 2–5 步。它自己会 `commit`，所以检查失败必须在 `commit` 之前抛 `ImportError`。

### 3.2 出站

继续用 `claim_one` / `acknowledge` / `SellIntentWorker`。事务在 HTTP 前结束，回执用租约 CAS。轮询 5 秒。开关或 URL 为空时不起网络循环。

相对 v1 的重试差异只在 [v2 增补第 4 节](../integrations/cycle-sell-intent-v2.md)：422 和 409 进入 `failed` 且不重试；401/403/404/5xx/超时仍退避重试。网络失败不写成 `blocked`。

### 3.3 商城不可用或返回错误时业务上发生什么

| 情况 | 待修 | 已上电商 | 商城库存 | 人要做什么 |
| --- | --- | --- | --- | --- |
| 开关关闭 | 已扣 | 已记 | 不变 | 不用处理。意图保持 `pending`，开关打开后才发 |
| 超时、5xx、404 | 已扣 | 已记 | 未知或未加 | 不用改结果。worker 重试同一个 `deliveryId` |
| `blocked` 且不是 `publish_disabled` | 已扣 | 已记 | 未加 | 等商城补条件，或主管作废（不用勾选） |
| `publish_disabled` 或 `applied` | 已扣 | 已记 | 已加 | 要作废必须先手工减商城库存并勾选 |
| 422、409、`conflict` | 已扣 | 已记 | 按商城契约不加 | 主管作废后重填。新结果用新的 `deliveryId` |
| 作废时租约未过期 | 不变 | 不变 | 不变 | 稍后重试作废 |

没有「同一条结果商城加了一半」的状态。商城要么加上全部修好数，要么不加。

晚到的回执若发现意图已经是 `failed`，CAS 影响 0 行。若这时商城其实已经加过库存，作废规则把 `attempts > 0` 视为可能已加库存，必须有勾选。

### 4.1 `maintenance_repair_record`

结果记录。`record_id` UUID 主键。`record_no` 唯一，给页面看，格式 `WX` 加 8 位序列（序列 `maintenance_repair_record_no_seq`）。接口身份用 `record_id`。

| 列 | 约束 |
| --- | --- |
| `part_id` | 非空，外键 `dim_part.id` |
| `pn` | 非空，写入时拷贝当时的 `pn_std`，最长 128 |
| `fixed_qty` / `scrap_qty` | 整数 0–1000，合计至少 1 |
| `operator` | 非空，账号名，最长 64 |
| `status` | `active` / `voided`，默认 `active` |

- 主键 `delivery_id` UUID。
- `record_id` UUID，非空，唯一，外键结果表。
- `part_id` 外键 `dim_part.id`。
- `qty` 整数，`CHECK (qty BETWEEN 1 AND 1000)`。

### 4.5 视图与函数

`v_repair_pool` 的列用英文：`part_id`、`pending_qty`、`shop_qty`、`scrap_qty`。不要用中文列名。

`repair_receipt_eligible_qty(line)` 返回整数：行有效、件况属于 `坏品`/`坏件`/`故障`、`part_id` 非空、数量是 ≥ 1 的整数时取该数量，否则 0。件况 `废品`、`成品`、空白和非整数都得到 0。这个函数不看 `dim_part.status`，避免档案被标成合并之后，已有扣数在没有人改返还行的情况下突然大于合格件数。

维修员池和采购三数只返回 `dim_part.status=active` 的型号。合并档案上残留的待修不会出现在这两个列表里，主管仍可按结果 id 打开原来的记录。本期不改型号合并写路径。

`assert_repair_deduction_within_receipt(receipt_id)`：有效扣数大于合格件数，或有效扣数大于 0 且 `part_id` 相对更新前发生了变化，则 `errcode 23514`。延迟约束触发器挂在扣数表和返还行的 `qty` / `line_status` / `test_result` / `part_id` 更新上。应用层先做可读的 409/422，触发器是漏调用时的底线。应用把 `23514` 映射成契约里的拒绝文案，并回滚。

视图只服务查询。写入以扣数行和结果状态为准。

## 8. 验收清单（业务语言）

- [ ] 坏件登记或导入之后，维修员按型号能看到待修件数。好件不出现。件况空着的不出现，补成坏件后出现。原来就是废品的仍是废品，不进待修，也不算进「废品件数」。
- [ ] 维修员只看到型号、描述和待修件数，看不到从哪个项目、哪个客户回来，也看不到别人填的结果。
- [ ] 填修好 2、废品 1，且池里至少有 3 件时，待修少 3，已上电商加 2，废品加 1。没填完的件数还在池里。
- [ ] 修好的数量会生成一条待发记录。出站开关保持关闭时，商城库存不变。
- [ ] 两个人同时填同一个型号，扣掉的总数不会超过坏返收货数。后提交的如果超出剩余，整笔失败，不会被系统改小。
- [ ] 填错的人当天可以作废并重填。过了当天要主管作废。作废后件数回到待修。
- [ ] 商城已经加上的数量，作废前必须有人确认商城库存已经手工减过。系统本期不会自己去商城减。
- [ ] 把返还行改小、作废或重新导入，若会少于已经扣掉的件数，整笔不生效。
- [ ] 采购只看到每个型号的三个数。销售不能在这个页面新建型号。
- [ ] 页面上没有派工、领取、维修中、委外、待处置、回公司。
- [ ] itsp 的主库存、前置库、采购、销售、氚云和变卖台账的行数不因这些操作变化。
- [ ] 发布开关仍是关的。本阶段不发闲鱼，不部署生产，不升级前端版本号。

## 9. 上线约束

功能切片合入 main 也不等于上线。生产只部署打了 `release-` 标签的提交，且需要单独授权。

- `SHOP_CYCLE_SELL_ENABLED` 默认 false，配置和测试夹具以外不把它写成 true。
- 五个页键默认 false。
- 不调用闲管家。
- 不改 `frontend/src/version.ts`。
- 不在生产库执行 `alembic upgrade`。
- 不合并 #520 / #521 / #522。

开发库若升级失败，因为里面已经有件行：在开发库单独清空这四类行之后再升级。清空脚本不要写进迁移，也不要拿去跑生产。

商城 v2 接收端未合入之前，即使有人打开出站开关，也只会得到 404/422 并按增补退避或失败。默认配置下 worker 不发请求。打开开关不在本计划的任一 PR 里。

S1 与 S2 之间，已经打开页键的开发账号会看到旧页面打到已删除的接口。这两支都合并之前不要打发布标签。
