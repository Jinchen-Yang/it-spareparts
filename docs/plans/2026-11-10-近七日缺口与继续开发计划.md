## 6. 接口协议：照抄与停笔

协议分三层。第一层已经在代码和 §10 里冻结，后续 PR 不得改字段。第二层是契约 §4 已经写明的商城表和状态，外加一条实现约束：改商城库存必须走现有 `stock_txn`，不能只改数量列。`kind` 和 `operator_id` 仍待确认，确认前不建表，也不给契约表加列。第三层没有规格，本计划不设计。

### 6.1 已冻结：itsp 出站与入站

出站 body 只有这六个字段，多一个就 422，itsp 自己也不发：

```json
{
  "schemaVersion": 1,
  "deliveryId": "<uuid>",
  "unitId": "<int>",
  "partId": "<int>",
  "conditionBucket": "good | bad",
  "qty": 1
}
```

`SHOP_CYCLE_SELL_URL` 必须整段就是 `https://主机/api/integrations/cycle/sell-intents`。校验要求路径恰好是这一段，不能带查询串、片段或用户信息。代码把该变量原样当作 POST 地址，不会再拼一次路径。生产必须用 HTTPS；开发环境只有回环地址可以是 HTTP。出站 token 不能与目录通知或图库 token 相同。客户端超时是 `httpx.Timeout(10, connect=3)`，不是契约正文里写的 15 秒；本计划不改这个超时。不跟随重定向，`trust_env=false`，响应不超过 4 KiB，`content-encoding` 必须是 identity。

回执 `status`：`applied` | `unchanged` | `blocked` | `conflict`。`unchanged` 只有在该意图持久的 `receipt_status` 已经是 `applied` 时才标成 `delivered`。以前只是 `blocked` 时，商城若回 `unchanged`，itsp 把它当成 `invalid_receipt`，回到 `pending` 做网络退避，不标 `delivered`。网络失败、非 200 同样回 `pending`，不写成 `blocked`。

`blocked` 只有 `blockCode` 属于下面这个集合时才进入 `blocked` 并按 5 分钟 / 15 分钟 / 1 小时 / 6 小时退避：`missing_formal_image`、`missing_category_mapping`、`missing_list_price`、`missing_catalog_identity`、`publish_api_missing_stock_update`、`publish_disabled`。集合外的 `blockCode` 与缺码一样，是无效回执，留在 `pending`。

itsp 入站不新增表、不新增列。凭据是 `CYCLE_SELL_CALLBACK_TOKEN_SHA256`（64 位小写十六进制）。空则三个 POST 一律 404 `not_enabled`。摘要不得等于出站 token 的 SHA-256。未知 JSON 字段 422。`Cache-Control: no-store`。

| 路径 | 成功时做什么 | 冲突 |
| --- | --- | --- |
| `POST /api/integrations/cycle/requeue` | body 只有 `deliveryId`。仅 `blocked` 把 `available_at` 调到现在 | 无此 id 为 404。其他状态 200 且不改行 |
| `POST /api/integrations/cycle/mark-sold` | `schemaVersion`、`deliveryId`、`shopOrderLineId`、`qty=1`。仅 `station=closed` 且 outcome 为 `to_shop`，并且意图不是 `delivering` 或 `failed` 时改为 `sold`。同事务里 `pending` / `blocked` 改为 `failed`，`last_error_code=unit_sold_by_callback`。`delivered` 保持 `delivered` | outcome 已是 `sold` 且最新 `mark_sold` 事件的行号相同：200，不写第二笔。行号不同、工位未结案、意图正在投递或已失败：409 `remote_conflict`，不覆盖 |
| `POST /api/integrations/cycle/revert-sold` | 只把 outcome 从 `sold` 改回 `to_shop`。代码不改工位；售出路径要求当时已是 `closed`，所以工位保持 `closed` | 最新售出行号不一致，或 outcome 不是可回退的 `sold`：409。已发货退货没有单独分支，误调用同样 409 |
| `GET /api/cycle/units/{id}/sell-intent` | 用户 JWT，仅 `page_cycle_manage`。响应等于 `read_status()` | 无权限 403，单位不可见 404 |

人工 `mark-sold` 的事件 payload 只有 `outcome`，没有 `shopOrderLineId`。此后商城回调对不上行号，返回 409，不会补写行号。人工售出只把 `pending` / `blocked` 改成 `failed` 并清空 `receipt_status`；`delivering` 返回 409；已经 `delivered` 的意图保持 `delivered`。它不调用商城。若之前某次 `publish_disabled` 已经加过商城库存，这件货的商城数量不会被这次人工售出扣回。

itsp 库表维持 #528 的三张，本计划不加列：

| 表 | 关键约束 |
| --- | --- |
| `maintenance_cycle_unit` | 工位 `pool/testing/repairing/outsource/ready/closed`。结案 `to_shop/to_company/scrap/sold`。一行一件 |
| `maintenance_cycle_event` | 售出幂等靠事件 payload 里的 `shopOrderLineId` |
| `maintenance_cycle_sell_intent` | 一单位一条。状态 `pending/delivering/delivered/blocked/failed`。`qty` 只能是 1 |

返还收货入池沿用现有 `HandoffInput`，不改形状：

| 字段 | 规则 |
| --- | --- |
| `receipt_id` | 1–36 字符。收货行须 `active`，`part_id` 指向 active 备件 |
| `qty` | 服务层校验 1–1000。越界 400。已入池未撤回件数加本次不得超过收货数量 |
| `expected_receipt_version` | 与收货行版本不一致则 409 |
| `serial_numbers` | 可空。请求体内重复、空白、与 `qty` 个数不等：400。入库时撞上同一收货行已有 SN 的唯一约束：409 |
| 权限 | `page_cycle_recycle` 或 `page_cycle_manage`。201，body `{items}` |
| 额外字段 | 422 |

页面可以不传 `serial_numbers`。工人序列化白名单没有 `serial_number`、`vendor_name`、`source_receipt_id`；待办摘要只有 `pn`、`part_id`、`station`、`unit_uid`。这些字段只出现在 `page_cycle_manage` 的单位响应里。交接不顺手改收货行的 `version`：版本检查只比较，不递增。行锁加上「已入池未撤回件数 + 本次 ≤ 收货数量」保证不超收。两条并发请求的件数之和不超过剩余数量时，两条都会成功。只有第二条会超收时，第二条 409。验收不能写成「任意两次并发只有一次成功」。
