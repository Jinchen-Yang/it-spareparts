# 06 领用工作簿锁后授权复验

日期：2026-10-23。决策：D-33、D-38。落实 2026-10-15 的 `docs/integrations/maintenance-site-issue-facts-v1.md` 调用者契约，不新增其他 sheet 的全系统在途取消规则。

## 问题与边界

独立调查在固定 main 和重构候选各复现 10 个实际 PostgreSQL 等待窗口：入口已经鉴权，等待全局 advisory/state 行锁期间被撤权，原请求仍提交。06 领用已有明确“入口校验并锁后复验”约定，因此单开行为修复；结构提取与行为修复分别审查。03/01 的观察不据此扩展为新的业务政策。

## 调用结构

HTTP → 现有入口权限/计划校验 → 单一授权回调 → coordinator 取得事实/合单锁 → 当前授权复验 → 同一事务写入各 sheet → 当前授权复验 → 唯一 commit。

HTTP 层持有服务端身份和原 token version，重读 SysUser 当前 active/version/权限，再复用原有页面、工作簿编辑、项目范围和本次涉及合同金额/项目备注及归属改派的全量项目范围资格。06 使用工作簿既有动作权，项目负责人/销售例外继续由既有函数决定。服务层只接受 Callable，不导入 API、Request 或 token 实现，不新增用户行锁，也不调整原锁顺序。

首次写路径先在 scope/merge 锁后检查，防止入口读到的资格在等待期失效。混合工作簿还可能在后面的 sheet 等锁，因此 commit 前再检查；失败由 HTTP 明确 rollback，之前 flush 的事实、版本、operation 和完成回执均不提交。锁内命中已有 operation 的早返回在原位置复验，不把重放挪到事实 CAS 之后。无锁提前回执查询沿用当前请求依赖和 D-38 必要金额权检查。

`reauthorize` 可选是为了保持既有可信内部 service 调用；实际 HTTP 06 修改/合单计划必须提供。HTTP 入口还在等待前执行同一函数验证实名。回调始终核对原 operated_by，不会换操作人生成另一份幂等身份。

这关闭被测试的锁等待撤权窗口，不是授权撤销与业务提交之间的严格线性化协议；最后一次读取之后到 commit 之间仍不是跨事务互斥。建立更强协议需要资格修改端共同参与锁设计，超出本修复范围。

| 变量 | 类型 | 用途 | 定义原因 |
| --- | --- | --- | --- |
| `ident` | dict | 已验签的原账户身份和 tv | 比较等待前后是否仍是同一有效登录 |
| `plan` | MasterV2Plan | 已校验的整本变更 | 决定 06 范围和混合字段所需原有资格 |
| `operated_by` | str | 原审计/幂等操作人 | 拒绝身份漂移而不是静默换人 |
| `current` | UserContext | 当前数据库权限构造的上下文 | 不复用等待前的权限快照 |
| `reauthorize` | Callable[[], UserContext] 或 None | HTTP 提供的同一授权边界 | coordinator 不依赖 HTTP 实现；内部兼容入口明确标注可信 |
