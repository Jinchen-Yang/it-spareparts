## 根因及最小修复

调用关系：`V1 / 全局补价 / V2 既有行 → _merge_manual_cost_to_line → _recompute_line_amounts`；
读取关系：`页面 / 工作簿 / SQL 汇总 → normalized_line_cost → normalized_tax_tier → source_tier`。

读质量层要求来源、有效税基和兼容金额均有可靠证据，随后才采用目标双税金额。
原 writer 把来源改成 `manual`，却只写双税字段，导致原先适用 `none` 的人工账本 fallback 也不再适用。
读层拒绝不完整证据是正确行为，不能通过放宽 `normalized_line_cost` 修复。

权威 `maintenance_cost.recompute` 的人工路径已经规定：人工未税价作为兼容 `unit_cost`，
`cost_tax_basis=ex`，兼容 `cost_amount` 等于未税金额。本次让显式补价遵循同一持久化契约。
后续只改数量时，仅对双税单价齐全的 `manual` 来源同步对应税基的兼容金额；已有 `inc` 税基保留原侧。
自动、估算和未知来源的数量重算行为原样保留。
开发期只读预审发现：缺单价侧可能带有历史残留金额，直接同步会把缺证据升级成已知成本。
因此显式要求两侧单价齐全，新增 `ex/inc` 税基 × 缺失 `ex/inc` 单价的 4 个反例；
历史不完整证据不会因只改数量而被本次代码补成可靠成本。

| 变量 | 类型 | 用途 | 定义理由 |
| --- | --- | --- | --- |
| `line` | `FMaintenanceLine` | 事务锁内的需求事实及成本证据 | 原有锁顺序和 Session 继续生效 |
| `refill` | `CostRefill` | 经现有入口校验的人工单价与原因 | 不新增读侧推断或另一套换税算法 |
| `cost_fields` | `tuple[str, ...]` | 界定本次同步的 8 个成本字段 | 同时覆盖双税与兼容证据 |
| `before_cost` | `tuple[object, ...]` | 写前字段快照 | 兼容字段单独修复也必须报告真实变化，避免漏掉 revision |

`changed` 比较实际写前／写后字段值：只有兼容字段缺失而价格相同，仍会推进外层既有 revision；
人工账本的价格、原因和 active 没变化时不伪增账本 version。完全相同的有效证据继续为 no-op。
V1 沿用原有账本／工作簿 revision 语义，V2 沿用原有行 UPDATE 审计及首次完整回执；不新建补偿历史。
