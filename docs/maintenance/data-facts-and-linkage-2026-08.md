## 1. 维保备件需求单 Excel 字段分析（两份真实导出）

### 1.1 两份导出的布局差异（关键）

| 版本 | 文件 | 列数 | 结构 |

| 历史版（2026-07-02 导出） | 维保备件需求单_2026-07-02-17-46-31-358.xlsx | 90 | 头段 [0..52]，明细段 [53..89]，系统列（ObjectId/CreatedBy…）在头段 |

- 两份都是 **双表头**：第 0 行字段码（F00* / D1074…），第 1 行业务名；
- 两份均**无精确重复的业务名列**（已程序化核验：Counter 精确相等项=0）——
  头级「需求数量」与明细级「需求明细.需求数量」名称不同，不构成重复；
- 列序完全不同 → 导入必须**按业务名定位**（并兼容 (必填)/(不可修改) 变体后缀），
  不能按位置写死。

## 2. 三文件交叉验证（真实样例，本机跑通）

### 2.1 发货单 ↔ 需求单（57MB 发货单，流式解析）

- 发货单 166 列；「维保供货」头 5,712；
- 其中带「维保需求单」号 4,928 种、**5,701 头（99.8%）命中需求单表的 WBDD 单号**；
- 发货单**没有项目名列**，只有需求单号 + 销售订单（维保供货行销售订单基本为空）
  → 发货单挂项目的唯一可靠路径 = WBDD 单号；
- 出库类别分布：销售出库 13,128 / 维保供货 5,712 / 采购退货 329 / 其他出库 403。

### 2.2 返库单 ↔ 需求单

| 文件 | 头行 | 带维保需求单 | 命中需求单表 | 带维保销售订单 |
|---|---|---|---|---|
| 宽版 4MB（120 列） | 7,104（其中 3,019 个单头、7,102 条明细） | 962 | 760（79%） | 2,721 |
| 窄版 18KB（49 列） | 27 | 10 | 10（100%） | 10 |

- 宽版测试结果分布：**成品 6,703 / 坏品 399**；
- 返库单**直接有项目名列**（如「预交付-平安银行20260401-20280331新华三整体维保」），
  不依赖需求单号也能挂项目。

### 2.3 结论

可靠事实链 = 需求单（申请）→ 发货单（实发，99.8% 可勾稽）→ 返库单（收回，成品/坏品，
有项目名）。需求单自身状态列不可靠（§1.3）。

## 4. 独立复审意见逐条核验结论（我逐条用代码/数据验过）

| 复审主张 | 核验结果 |
|---|---|
| 「91 列重复中文表头会在进 transform 前被通用 reader 整批拒绝」 | **部分成立**：reader.py:827 对被取用 sheet 的重复列名确实整批拒绝；但两份真实导出**都没有精确重复列名**（已程序化核验），当前文件不会触发。防御性建议（按位置分头/明细 + adapter 级放行）仍值得采纳 |
| 「transform 会丢失合法的有单头、无明细订单」 | **成立**：transform.py:217-220 每行必须同时有 维保单数据ID 和 明细数据ID，无明细的单头会被记为 error 行跳过，订单丢失 |
| 「M4：返库单坏品被跳过，坏件来自 rkd_inbound」 | **成立**：maintenance_doc_import.py 中 return_order 只对非坏品行 return_out，坏品跳过；坏件事实确实走 RKD |
| 「CKD/RKD 无需求明细行级键，只能项目+PN 聚合」 | **成立**：CKD 明细只有 数据ID/PN/数量，无 WBDD 行键；需求单重复 PN 无法行级分配 |
| 「M2：project_std 是名称不是稳定 ID，与 ADR-0002 冲突」 | **部分成立、有张力**：ADR-0002 针对「人工来源单归属」说名称只是线索；但业务已确认「台账项目名=身份」（Q8/§19），台账导入的项目 code 本身就是 Excel 里的项目名。稳妥做法：名称规则只出候选 + 人工确认 + 复用 maintenance_source_order_assignment，不新建第二套关系 |
| 「成本应改名『已知申请估算成本（含税）』并拆 actual/estimated/missing/coverage/quality」 | **成立**：88.7% 覆盖意味着 11.3% 缺价，混合展示会误导；缺价必须显式「不完整/已知下限」 |
| 「上传权限：/api/imports/upload 只校验 page_import 是全家桶」 | **成立**：该端点自动识别文件类型，给项目经理开放等于开放采购/销售/库存/报销全部导入；需 maintenance-only 专用端点 + 专用动作键 |
| 「M3 需服务端分页/异常队列/六种空值状态；y2026_ 写死年份；226 vs 415 口径不清」 | **成立**：全部采纳 |
| 「发布与回滚：分支比 main 多 23 提交/106 文件/1.96 万行，需最小发布链 + feature flag；不做 downgrade 回滚」 | **成立且最重要**：冻结功能不能随本次发布；回滚=关 flag+旧应用兼容新 schema |
| 文档内部计数错误（35/34、27/28）、「返库 7,104 头」与 3,019 头混淆 | **成立**：头级实列 34、明细实列 28；7,104 是宽版行数不是单头数。已修正 |

## 5. 给后续 plan 撰写者的建议要点（我的分析汇总）

1. **先 M0 后设计**：老板每周/月据此做什么决定、项目经理看本人还是全部、
   成本字段正式命名、事实粒度（建议项目＋PN 聚合）——四个口径拍板前不进 M3；
2. **导入层**：按业务名定位列（兼容变体后缀）+ 位置段分头/明细 + 保留无明细单头；
   状态列落库但只展示；
3. **事实源分离**：实发=CKD、未用件=return_order、坏件=rkd_inbound，
   各源带 as_of/readiness，未导入显示 not_imported 不显示 0；
4. **成本口径**：「已知申请估算成本（含税）」= actual/estimated/missing/coverage/quality；
5. **权限**：专用上传端点 + action_maintenance_wbdd_import；查看 page_maintenance_boss/
   page_maintenance；金额/成本两组数据权限独立；
6. **看板**：来源健康→本期变化→需关注→全项目分页→证据下钻；六种空值状态；
7. **发布**：最小迁移链（纯加法 nullable）+ 独立 feature flag；回滚=关 flag。
