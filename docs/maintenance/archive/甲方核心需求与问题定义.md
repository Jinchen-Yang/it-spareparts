# 维保备件展示板 — 甲方核心需求与问题定义

> 版本：2026-08-16 确认版（含当日业务纠偏后的最终口径）
> 本文是需求唯一事实源；开发计划（`docs/maintenance/plan-v1-boss-dashboard.md`）以本文为准。

---

## 1. 背景与定位

甲方有一套维保业务（备件/整体维保），数据散落在氚云系统导出的 Excel 里。
他们需要的是**给老板做决策用的「后事实展示板」**：

- 业务发生时数据已经在氚云/台账里，系统只做 **定期上传 → 归集 → 成本回填 → 展示**；
- **不做业务流程闭环**（不需要审批流、不代替业务员做操作）；
- 不是给操作人员用的工作台，是给**老板/管理层看数做决策**的。

一句话：**把每个维保项目里的「货」和「钱」透明化，老板每周/每月看一眼就能做决定。**

---

## 2. 谁在用、权限怎么给

- 使用者：**老板/管理层 + 项目经理**；他们公司管理层职能区分不清晰，本质是「给老板看决策」；
- 权限模型：**勾选名单制**——在权限中心勾选人员，**被勾选的人这一套维保系统全部可见**，
  不分细粒度、不做项目经理只见自己项目（待 M0-B 最终确认：项目经理看本人还是全部）；
- 金额敏感字段：利润/成本数据组沿用现有权限体系控制。

---

## 3. 核心需求（逐条，已确认）

### 3.1 数据上传：定期上传维保备件需求单

- 甲方**只需要定期上传「维保备件需求单」**（氚云导出，当前年度版 91 列、历史版 90 列，都要兼容）；
- 上传后系统自动**更新每个项目下的备件需求单**清单；
- 上传频率：每周或每月一次，当天最新即可；
- 事实链补强（已确认）：需求单（申请）→ **发货单（实发）** → **返库单/入库单（收回）**
  三份文件可按 WBDD 单号勾稽（真实样例验证：发货↔需求单 99.8% 命中）。

### 3.2 成本回填：需求单自动带出成本

- 每条需求单明细，用系统已有数据回填成本；
- 口径（甲方原话）：**「成本是采购价，如果没有采购就是销售价。距离当时订单时间越近越好。」**
  —— 即：采购价优先 → 无采购用销售价 → 时间就近；
- 已有取价引擎（五层瀑布：direct ±7天采购价 / month_avg / trace_avg / sales_ref / none），
  生产覆盖率 88.7%，**复用、不重写**；
- 缺价的部分：显示「无参照价/已知下限」，**不按 0 计**。

### 3.3 项目主数据维护

- 能修改补充项目的**名称、维保期限**；
- **「预交付」项目并入真实合同项目**展示（甲方原话：「维保里面有预交付和真实合同……
  不叫合并」）——预交付单归到真实合同下看总账，不是把两个项目合成一个。

### 3.4 需求单可更改

- 改行/改单、作废、补录、**改项目归属**（把单子挂到正确项目）；
- 本质定位（甲方原话）：「我们这个系统只是一个数据的展示板、后事实系统，
  当你看到这个系统后业务已经发生了。我们需要用已有数据来让老板看到数据」——
  即「更改」是**展示层面的数据修正**，不是业务流程编辑。

### 3.5 老板看板看什么

甲方勾选的五项（重要性不分先后）：
1. **项目成本/盈亏构成**——备件花了多少、报销花了多少、回款多少，赚不赚钱；
2. **现场库存/积压**——现场还有多少货没消耗，压了多少钱；
3. **备件消耗 vs 申请差异**——提了多少 vs 实际消耗多少，乱提/多提一眼看出；
4. **坏件回收/应返还**——坏件收回了多少、该还的还了多少；
5. **回款进度**——收到哪了、差多少。

甲方补充重点：**首先是项目成本和备件的申请**。

### 3.6 明确不做（冻结清单，甲方口径）

- 销售/采购模块与采购分析：**已经很完美，不动**；
- 之前做的重闭环功能（甲方原话「闭环得太大、远超他们的需求」）：
  AI 兜底列映射、补库购物车审批、回款凭证上传、坏件变卖登记、项目工作簿 v3 导出/回填、
  前置库账本界面、收回清单页、销售看板页、报销对账页 —— 代码保留、导航隐藏、不上线。

## 4. 要解决的问题（痛点清单）

1. **项目备件账不透明**：每个项目提了多少货、花了多少备件钱，老板看不到，只能靠 Excel 手工对；
2. **现场乱提备件/库存积压**：申请量与真实消耗对不上，货发到现场后去向不明；
3. **成本流失**：备件成本 + 人工报销成本没有归集到项目，项目赚不赚钱算不清；
4. **坏件回收失控**：该返还的坏件没人盯，返还了多少、还差多少没有数；
5. **需求单状态数据不可信**（甲方直觉，已用事实核验）：需求单上「已采/待供/待返/领用」
   等状态列是氚云里人工维护的，甲方认为氚云做不出这套可靠流转状态——
   结论：这些列**只原样展示、不参与计算、不标注**，实发/收回用发货单/返库单事实；
6. **生产数据缺口**：生产库里领用/返还/坏件/回款全是 0 行（从未跑过）；项目表只有名字、
   没有合同与期限（台账未导入生产）；
7. **预交付项目被拆开看**：预交付与真实合同分开，老板看到的不是完整项目账。
