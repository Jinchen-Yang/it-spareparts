# DEV-13A 编码前规格：维保需求号匹配归因报告

## 1. 目标

把现有维保成本引擎中“未命中专属采购直配”的全部行，按可解释、互斥、穷尽的原因分类，回答：

- 有多少行只是需求号书写格式不同；
- 有多少行需求号存在但 PN 对不上；
- 有多少行采购侧根本没有该需求号；
- 有多少行存在多个格式归一候选，不能安全判断；
- 剩余无法归入上述原因的行是什么。

本切片是只读数据诊断。它不修改需求号、不自动建立关联、不回填成本、不触发重算，也不改变维保项目成本、利润、库存或导入结果。

## 2. 唯一事实基线

“精确直配”的定义必须与 `maintenance_cost._purchase_pools()` / `recompute()` 当前 A0 层一致：

1. 维保母集：已生效维保单，且 `order_date >= MAINT_COST_START_DATE` 的全部明细行；
2. 采购候选：已生效采购单，`linked_maintenance_order_no` 非空，明细数量和单价均为正；
3. 打包占位 PN（`MAINT_POOL_EXCLUDE_PNS`）不构成候选；
4. 精确键为公共 helper `exact_match_key(需求号) + part_id`，成本引擎与报告共同调用；为保证母集完全一致，历史纯空白键会规整成 `''`，双方纯空白且同 part 时仍算现行 A0 命中；
5. 精确键存在至少一条合格采购候选即算已匹配，不进入归因母集。现有引擎允许同键多张采购单加权，因此这类不属于“重复候选未匹配”。

报告只分析上述母集中未精确匹配的行。它不是 `cost_source=none` 报告：未直配行仍可能被 ±7 天价、月均价、追溯价或销售参考价估算出成本。

## 3. 格式归一候选键

只用于分析，不写回、不替代成本引擎的精确键：

```text
loose_key = upper(trim(value)) 后删除所有非 A-Z / 0-9 字符
```

它只吸收大小写、首尾空白、内部空白和连接符差异；不纠正数字、不猜前缀、不做模糊相似匹配。例如 `wbdd 20260101 0001` 与 `WBDD-20260101-0001` 可归为同一候选，`0001` 与 `0010` 不能。

## 4. 六桶互斥优先级

所有未精确匹配行按下列顺序只进入第一个命中的桶：

| 顺序 | code | 人话标签 | 判定 |
|---:|---|---|---|
| 1 | `empty_request_no` | 单号为空 | 在现行 A0 未命中的母集中，维保需求号为空或只有空白（双方空白且同 part 的现行命中不在母集） |
| 2 | `normalizable_format` | 格式可规整 | loose_key + part_id 恰好对应 1 张合格采购单 |
| 3 | `duplicate_candidates` | 重复候选 | loose_key + part_id 对应 2 张及以上合格采购单；不能自动选 |
| 4 | `other` | 其他 | 采购侧存在 loose_key + 同 part_id，但候选因非正价、非正数量或占位 PN 等不满足现行直配条件 |
| 5 | `request_exists_pn_diff` | 单号存在但 PN 不同 | 采购侧存在同 loose_key，但没有同 part_id |
| 6 | `purchase_missing_request_no` | 采购侧无该需求号 | 采购侧完全不存在同 loose_key |

最后保留防御性 `other` 兜底。实现必须断言：六桶数量总和等于全部未匹配行；任何行不能重复计数。

“可修复率”只按 `normalizable_format / 全部未匹配行` 计算，名称为“技术上可规整候选率”。它不代表系统会自动修复，也不把重复候选、PN 不同或采购缺号包装成可自动处理。

## 5. API 契约

新增只读端点：

```text
GET /api/maintenance/match-audit?sample_limit=5
```

- 鉴权：硬登录 + `page_maintenance`；无页面权限返回 403。
- `sample_limit` 默认 5，范围 0~10。
- 固定返回六个桶，即使数量为 0，便于前后对照和长期跟踪。
- 无数据库迁移。

## 6. 样例脱敏与权限边界

每桶样例从 `maintenance_line.id` 升序确定性取前 N 条，重复运行顺序不漂移。样例只返回：

- 不可逆的短 `sample_ref`；
- 掩码后的维保需求号、PN；
- 掩码后的采购侧候选需求号、候选 PN（最多 3 个）；
- 候选张数与不含金额、不含人员的原因说明。

掩码规则固定为：长度不超过 4 的短值全遮；5~8 位最多保留首尾各 1 位；9 位及以上才保留首尾各 2 位；其余以 `*` 替代。任何响应都不得包含采购订单号、供应商、客户、采购员、销售员、价格、金额、成本来源或原始未掩码需求号。

该报告只陈述数据关联现状，不使用“错误员工”“违规”“自动修复”等措辞。

## 7. 实现边界与文件域

- 新建 `services/maintenance_match_keys.py` 作为正式精确键的单一真值源，成本引擎与审计共同调用并锁定历史边界语义。
- 新建 `services/maintenance_match_audit.py`，只执行固定次数的只读查询和内存归因；不得调用 `maintenance_cost.recompute()`。
- 新建独立 `api/maintenance_audit.py`，避免与后续维保主流程改造共享 `api/maintenance.py`。
- `main.py` 仅增加路由注册。
- 除把正式精确键抽到共享 `exact_match_key`（语义保持不变）外，不修改 `models`、迁移、ETL、成本引擎逻辑、前端、库存、利润或权限模板。
- 分类主路径固定 2 次查询；有样例时增加 1 次有界预览查询（最多 60 个 loose key、最多返回 180 行），总查询不超过 3 次且不随业务行数增长。采购明细先在 SQL 按采购单+part 聚合，Python 索引只保留分类所需订单集合和按 part 的合格订单计数。
- 每桶只保存整数计数和前 `sample_limit` 个待补样例；主索引不得构造候选预览。`sample_limit=0` 时不得构造任何样例/候选预览字典，也不得执行第三次预览查询。

## 8. TDD 验收 seam

公开 seam 为服务返回和 HTTP API：

1. 六类各有独立构造样本，分类互斥且桶和等于未匹配总数；
2. 精确 trim+upper 命中不进入未匹配；等价格式单候选进入格式可规整；多候选进入重复候选；
3. 同需求号不同 PN、采购缺需求号、同 PN 但候选无效分别进入正确桶；
4. 可修复率只取格式可规整桶；0 分母返回 0，不产生 NaN；
5. 样例顺序和 `sample_ref` 重复运行完全一致；所有原始标识均不出现在序列化响应；
6. page 权限 403、未登录 401；有权限账号可读且不出现供应商/客户/价格字段；
7. 调用报告前后，维保行全部成本字段逐行零变化；事务无新增/更新/删除；
8. 生产快照用独立 SQL 对账总行、精确命中、未匹配和六桶，100% 一致；
9. 后端全量 pytest 与 `alembic check` 全绿；双轴复审无阻塞项后才可建 PR。

## 9. 编码前快照剖面

在本机生产等价快照库 `spareparts_dev05_stage` 上，按 §2/§4 的独立 SQL 得到：

|---|---:|
| 维保作用域总行 | 29,046 |
| 精确直配 | 9,538 |
| 未精确直配 | 19,508 |
| 采购侧无该需求号 | 12,167 |
| 单号存在但 PN 不同 | 7,327 |
| 其他（同 PN 候选不满足直配条件） | 14 |

当前快照的技术上可规整候选率为 0%。因此 DEV-13A 的主要价值是量化“采购缺需求号”和“同需求号 PN 不一致”，不是承诺用字符串清洗大规模自动修复。
