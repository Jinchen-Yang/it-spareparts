# 同一 XSDD 被拆成多个维保项目

## 业务不变量

- [[XSDD 销售订单]] 是项目归并键：同一规范化 XSDD 必须指向同一个 canonical `project_id`。
- 一个项目允许挂多个不同 XSDD，不能反向加一对一约束。
- `project_raw`、`project_std`、台账项目名和人工改名前名称只作为 [[项目别名]]；页面在主名称下以灰字展示，搜索需命中别名。

## 生产证据（只读，2026-08-28 17:00–17:20 CST）

- 6 个 XSDD 被拆到 13 个项目，涉及 2,121 张当前活跃归属维保单。
- `XSDD-20251017-0036` 被拆到 3 个项目：`LEGACY-0361`、`LEGACY-0362`、`AUTO-00081`。
- `LEGACY-0361` 与 `LEGACY-0362` 各有一条 2026-06 累计回款 `82,325.40`，状态和收款单号相同；前者是 2026-08-28 上传时再次生成，后者是 2026-08-25 既有事实。
- 该 XSDD 的两个合同关系含税额分别为 `1,780,283.02` 与 `1,670,000.00`，因此历史归并不能自动搬行或求和。
- 原始精确 XSDD 与统一规范化口径扫描结果均为 6 组/13 项目，当前数据不会因规范化扩大冲突集合。
- 13 个项目当前没有报销归因、现场领用、返还、前置库或补库申请事实；冲突主要集中在合同、回款及一条回款计划。

## 根因模式

1. `maintenance_source_assignments.auto_assign_unassigned` 按 `project_std` 名称分组；同一 XSDD 出现多个名称时会创建多个项目。
2. `maintenance_project_contract` 允许同合同号跨项目，只在读模型标记 `contract_shared`，没有写侧唯一 owner。
3. 项目没有 alias 表；改名或来源名称差异只能通过创建新项目表达。
4. 项目总表上传回款会按当前项目补建 XSDD 合同，进一步把名称分裂升级为合同和回款分裂。

## KIMI K3 对抗审查结论

本地 `kimi-code/k3` 在代码编辑前完成只读对抗审查，verdict 为：

- 历史物理合并：当前不可实施。canonical 选举和重复回款裁决不足，直接搬外键有财务重复风险。
- 写侧闭环＋alias 展示：可编码但不可生产；必须有统一规范化、数据库唯一 owner、防并发测试和冲突 preview。

## 本次实现边界

- 新增 `maintenance_project_xsdd`：每个规范化 XSDD 唯一指向一个项目；迁移只回填证据唯一的 XSDD。
- 新增 `maintenance_project_alias`：保存主名、旧名和来源名。
- 合同和活跃来源单归属通过数据库 trigger 认领 XSDD；跨项目或历史多项目证据统一 fail closed。
- 自动挂靠改为 XSDD 优先分组；无 XSDD 才按名称兜底。
- 看板 API 返回 aliases，项目卡灰字展示，搜索命中 aliases。
- 历史 6 组只生成 preview，不在本变更中移动、归档或删除任何项目和事实。

## 验收标准

1. 同一规范化 XSDD、不同项目名的两张未归属单，自动挂到一个项目，只创建一个 canonical mapping。
2. 同一 XSDD 已归项目 A 后，项目 B 新建合同或活跃归属必须返回受控冲突，不能写入半截数据。
3. 同一项目挂两个不同 XSDD 正常通过。
4. 项目改名前后名称和来源名称均作为 aliases 返回；前端灰字展示并可搜索。
5. 历史冲突 preview 列出 canonical 候选、各事实表数量和逐条冲突；preview 前后数据库零写入。
6. 迁移只回填唯一证据；现有冲突不猜 owner，部署前后业务事实行数与金额合计不变。

## 发布结论

当前结论：**可编码但不可生产**。只有迁移演练、并发回归、生产只读 preview、6 组人工裁决和真实账号验收全部通过后，才可灰度；历史归并是后续独立变更。
