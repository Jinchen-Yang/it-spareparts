# 维保业务文档

这里是 IT_data 维保业务的文档入口。业务目标是把合同履约、备件流转、项目费用和项目经理待办串成可追溯闭环：项目经理发起需求，仓库发货，现场确认收货和领用，返还件经检测入库后恢复库存；项目当前成本汇总现场领用备件的已取价成本，以及审批完成且金额口径已确认的项目费用。

> **权威规则**：合并到 GitHub `main` 的[维保业务运行手册](./business-handbook.md)是正式业务口径。会议原始记录、聊天记录和字段分析只作为来源，不是另一份可编辑真相。任何口径变更都必须经 Issue 和 PR 审查后进入 `main`。

## 一屏业务主干

| 维度 | 说明 |
|---|---|
| 主要角色 | 项目经理、销售经理、现场人员、仓库、采购、财务、管理层；外部审核 Agent 回传补库逐条结论；坏件维修由独立维修子公司承接 |
| 库存范围 | 公司主库、地区共享库、项目客户现场前置库；其他项目前置库不作为日常可调资源 |
| 核心流转 | 维保备件需求 → 发货/出库 → 在途 → 项目收货确认 → 前置库 → 领用/消耗 → 返库 → 检测入库 |
| 成本原则 | `项目当前成本 = 现场领用备件的已取价成本 + 审批完成报销的已确认计入金额`；缺失成本留空，报销金额列未确认前失败关闭，需求、采购、入库、出库证据不重复相加 |
| 系统边界 | 本手册同时说明目标流程、当前能力与待确认项；目标流程不等于已经上线 |

下表是维保相关工作的统一总清单。`main`、集成候选和生产是三层不同事实；“代码已完成”不等于“已部署”，外部 HTTPS 可访问也不等于对应提交已经上线。

|---|---|---|---|
| 项目方块工作台与项目内四表导出（#200） | 在项目内查看合同、回款、实际消耗、报销、提醒和导出预览；缺字段仍展示 | 已在 `main` | 是否为现网 SHA 需发布时核对；不能只凭页面可访问判断 |

| 发货到领用候选桥接 | 只有已确认仓库发货、唯一需求关系、当前项目归属和精确 PN 才生成候选 | 集成候选已实现 | 候选不等于领用，不写库存或成本 |
| 成本/库存迁移核对（#210） | dry-run、逐项目证据、实名对账、职责分离审批和哈希绑定 manifest | 控制工作台已实现；独立审核仍有双真值、服务端工件、覆盖完整性和性能 P1 | 不纳入首批 Beta；迁移权限与生产切换总闸必须关闭，不得凭现有 manifest 激活 |
| 销售经理补库购物车 Beta | 搜索 PN、显示所属池与近半年采购/销售价量、购物车、逐条审核反馈、复提、版本留存和 Excel 导出 | 集成候选已实现；独立页面和权限，服务端总闸默认关闭 | 只允许白名单试用；不写库存、采购单或维保需求事实 |
| 审核 Agent | 接收精确版本并逐条返回通过/打回 | 不在本次开发范围 | 由外部 Agent 团队建设；系统只提供受控回传接口 |
| 真实项目映射、历史数据迁移与生产验收 | 把候选能力接到稳定真实数据并形成可追溯基线 | 尚未执行 | 必须在发布前完成备份恢复、生产快照演练、权限白名单和稳定/Beta 双路径验收 |

补库 Beta 与稳定版共用同一后端和数据库，但使用独立表、独立 API、独立页面、独立权限和独立服务端总闸。稳定版仍为默认入口；关闭 Beta 只拒绝 Beta 业务访问，不删除 Beta 历史，也不改变稳定版库存、成本或维保逻辑。首批只允许稳定版、只读维保 Beta 和经独立 canary 的补库 Beta；正式迁移与成本/库存切换明确排除。

## 同步与治理

1. 业务口径修改：先建或更新 GitHub Issue，再以文档 PR 修改本手册；未确认内容不得写成事实。
2. 实现规格：必须链接本手册的对应章节和 GitHub Issue，不能把聊天记录或旧会议纪要作为最终需求。
3. 图表维护：Mermaid 代码块是图的源文件，不并行维护手工 PNG；确需对外展示时再从 Mermaid 生成静态图。
4. 评审要求：业务一致性审查确认对象、状态和责任边界；文档工程审查确认链接、Markdown、隐私和可维护性。
5. 来源治理：原始记录可以留在受控资料区供追溯，但不得复制进仓库，也不得与 `main` 手册形成双份真相。
