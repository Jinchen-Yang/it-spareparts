## 1. 原始需求（原话逐字记录）

> ### 一、备件领用与返还功能优化
> #### 1. 备件类别筛选
> - **新增备件类别字段**：系统需增加备件类别字段，业务人员可通过筛选硬盘等特定类别，快速进行批量标记操作。
> #### 2. 返还状态反写与统计
> - **新增返还状态列**：系统需新增"返还情况"列，并在关联维保需求单后自动带出"已返"或"未返"状态。
> - **增加待返统计板块**：需在项目分析页面增加待返数量统计板块，方便业务人员直接查看未返还的单据明细。
> #### 3. 返还单录入限制
> - **限制最大返还数量**：系统需限制返还单的录入数量，最大数量不能超过下单数量，避免重复选单导致超额返还。
> #### 4. 导出表格排序规则
> - **调整导出表格为升序**：当前导出的维保明细表格为降序，增加了人工处理成本，需调整系统配置，确保导出时默认为升序。

相关待办（原文）：「调整导出表格的排序规则，将其修改为升序。 @杨金臣」（对应 R4）

## 2. 背景与动机

维保业务闭环（issue #128）中领用与返还是第 3/5 阶段（`docs/superpowers/plans/2026-08-12-maintenance-business-workbench.md:62-74`）。返还台账（D-17，2026-09-12）上线后，业务在实操中暴露四类摩擦：按类别（尤其硬盘免返）逐行处理太慢、需求单看不到返还进度、同一需求单可被重复选中超额登记、导出降序增加人工整理成本。

## 3. 现状事实（2026-10-14 六路只读调查；标注 ★ 的已由主 Agent 抽查复核原文）

### 3.1 领用与返还数据链路（R1/R2/R3 共同底座）

### 3.3 R2 返还状态列与待返统计

- 需求单列表（页面＋服务）**无任何返还情况列**——`frontend/src/pages/maintenance/MaintenanceDemandsPage.tsx:274-304`、`backend/app/services/maintenance_demands.py:189-228`
- ★ 需求单上的 `returned_qty/head_returned_qty` 是 WBDD（氚云）导入的**源表自报值，只展示、唯一写入方是 ETL**，不存在从返还台账反写需求单的代码——`backend/app/etl/mapping.py:133`
- ★ 台账侧**已有按需求单聚合**：`receipt_summary` 按 `source_order_id` 聚合 Σ(active 行).qty，返回 项目总量/未关联量/by_demand，且有不变式校验；前端"按需求单核对返还"表已展示每单已返量——`backend/app/services/maintenance_return_receipts.py:785-824`（主 Agent 已读原文复核）
- ★ **口径冲突（本需求最关键发现）**：D-17 拍板"实际返还数量**不按领用行分配**，按稳定项目和可选 WBDD 汇总""**不因项目收货而宣称某一领用行已返还**"（CONTEXT.md:169/175 原文已复核）——**行级"已返/未返"标记直接违反 D-17；需求单级汇总标记（台账 by_demand）与现行口径兼容**
- 待返统计：**任何页面都没有待返数量统计板块**；analytics 聚合 SQL 未聚合 `pending_return_qty`（最小改动＝在 pn-ranking select 加 `func.sum`）——`backend/app/services/maintenance_analytics.py:252-297`

- 代码库不存在名为"项目分析"的页面；候选：/maintenance/analytics（维保数据分析）、/maintenance 主页项目墙、项目面板"分析定位"tab、/boss 经营看板

### 3.4 R3 返还单录入数量限制

- ★ 台账手工登记校验只有：**正整数（0<qty<10^11）＋有 SN 时数量＝SN 个数**＋需求单归属校验——**完全不与下单数量比较、无同一需求单累计上限**——`backend/app/services/maintenance_return_receipts.py:259-273`（已读原文复核）
- 需求单候选端点返回全部有效 WBDD，**不排除已满返单、不返回已返/剩余量**；前端下拉全量可选、数量 min=1——同一需求单可被重复选中多次登记——`backend/app/services/maintenance_return_receipts.py:463-517`、`frontend/src/pages/maintenance/panel/ReturnReceiptsSection.tsx:826-875`
- **可借鉴的既有防超额实现**：坏件返还单创建时对义务 SELECT...FOR UPDATE 行锁＋Σ已登记校验（"返还数量超过当前剩余应返数量"）；领用侧对 delivery 行有"领用数量超过可用发货余额"校验——`backend/app/services/maintenance_bad_returns.py:405-448,1113-1193`、`backend/app/services/maintenance_project_operations.py:1370-1449`
- ★ 相关口径：D-17 允许"超过 100% 如实展示"（CONTEXT.md:171）——加硬上限属于**收紧既拍板口径**，需决策修订或明确例外

### 3.5 R4 导出升序

- ★ 现降序（`ORDER BY order_date.desc()`）是 **2026-08-21 客户反馈特意引入**，注释原文"order_date 倒序——最新日期排前面；行键/行级哈希与行序解耦，Excel 回传不受行序影响"——`backend/app/services/maintenance_project_master_workbook.py:471-493`（已读原文复核）
- 排序实现集中在唯一共用查询 `_assigned_lines`，四处消费同步变化：v1/v2 项目总表、主页全局行级表、网页行级接口；**改升序不破坏上传回传协议**（行序解耦）——同文件 :492,660,810-815,3085-3086
- 各导出现状不一致：项目总表 03 与 /lines/export CSV＝降序；逐单订单 XLSX 与 workbook v3 03 表＝升序——`backend/app/services/maintenance_cost.py:1593-1594`、`backend/app/services/maintenance_export.py:250-267`、`backend/app/services/maintenance_project_workbook_v3.py:157-176`

## 4. 需求描述（建议实现口径，待 §5 拍板后实施）

- **R1 类别筛选**：领用明细与返还台账列表增加品类筛选（复用主数据两级品类＋字典端点，后端 join 派生，不加行级类别列）；配套批量标记能力（具体标记对象待确认，若为"是否应返还"则与 [[需求00005]] 免返体系联动）。

- **R3 录入限制**：登记/修改返还台账行时，若关联需求单则校验 累计有效登记量＋本次 ≤ 上限（基准待拍板）；候选端点返回每单已返/剩余量，前端下拉展示剩余并可过滤已满返单；借鉴坏件返还单的 FOR UPDATE＋Σ已登记模式保证并发安全。
- **R4 导出升序**：将 `_assigned_lines`（及 /lines/export，如确认）排序改为升序（order_date 正向），四处消费同步生效；保留行序解耦不回传破坏的安全特性。
