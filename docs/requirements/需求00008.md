## 2. 背景与动机

- 业务在源系统（ERP）里对维保需求单（WBDD）做了删行、作废、改数量等修改，导出后重新上传，期望系统里的数据被「覆盖」成和原件一致；实际反馈仍未覆盖。
- 历史脉络：
  - 2026-09-02 「全量修改能力」事件调查——`docs/reports/2026-09/2026-09-02-全量修改能力-事件调查与需求差异报告.md`（针对的是**项目总表工作簿**的删行=作废/改值/加行，以及 v1.25 整本 CAS 带来的 409）；修复计划见 `docs/decisions/zcode-维修计划-全量编辑恢复.md`。
  - 2026-10-12 **D-27 维保原件同步与缺项差集**（`docs/decisions/0005-维保原件同步与缺项差集.md`），提交 `e715128`「按上传范围核对维保缺项并显式确认同步作废」，随 v1.36.5 发布（`docs/releases/v1.36.5-maintenance-analytics.md`）。这是**原件（WBDD）重传**的覆盖能力。
  - `be28543`（2026-10-13，PR #363 四项评审意见）只涉及需求单候选端点地址门禁、唯一候选自动关联仅限新建、搜索防抖、CONTEXT 地址口径；**与原件覆盖逻辑无直接关系**（唯一相关点：编辑既有领用单不再自动关联需求单）。

## 3. 现状事实（2026-10-15 只读代码排查）

「维保需求单」上传在系统里有两条通道：**A. 原件（WBDD 导出 Excel）上传**——「需求单与同步」页专用入口，或「数据中心→数据导入」通用入口；**B. 项目总表工作簿 03_备件明细**（系统导出、改后回传）。下面以 A 为主（原话最贴近），B 作对照。

### 3.1 改数值不覆盖：整行「人工保护」+ 通用入口默认跳过

1. **任何一次在项目总表里改过的行，以后重传原件都不再接受原件的值。** 原件 upsert 对需求明细的可编辑字段（PN、描述、需求数量、退货数量、SN 等）使用三态保护：字段被页面直改记入 `manual_override` 时保留现值；**行的 `edited_source != 'wbdd'` 时整行全部可编辑字段保留现值**——`backend/app/etl/loader.py:365-380`（说明）、`:446-458`（SQL `CASE WHEN edited_source != 'wbdd' THEN 现值`）、`:471-487`（审计同口径）。
2. 项目总表 03 回传只要改了该行**任一字段**（哪怕只改备注、人工成本或成本原因），就把整行标成 `edited_source = "workbook_manual"`——`backend/app/services/maintenance_project_master_workbook.py:6382`（解析侧只对有差异的行生成 UPDATE：`:3570-3582`）；页面新增/总表新增行也是 `page_manual`/`workbook_manual`——`backend/app/services/maintenance_demand_manual.py:550`、`maintenance_project_master_workbook.py:6287`。**没有任何代码路径把它改回 `wbdd`**，保护是永久的，且回执不提示「这些行因人工保护被跳过」。
3. **「数据中心→数据导入」默认是「跳过」模式**：后端 `mode` 默认 `skip`——`backend/app/api/imports.py:199`；前端「修复模式」开关默认关——`frontend/src/pages/ImportPage.tsx:97,232`。skip 模式下单头和明细都是 `ON CONFLICT DO NOTHING`，**已存在的单据一个字段都不更新**——`loader.py:390-400`（明细）、`:509-535`（单头走通用 `_upsert_facts`）。只有「需求单与同步」页专用入口固定用 `upsert`——`backend/app/services/maintenance_wbdd_import.py:165-172`。
4. D-27 第 6 条明确：需求数量的修改**不自动改写实际领用数量**（领用行、返还行不跟着变）——`docs/decisions/0005-维保原件同步与缺项差集.md`。

### 3.2 删行不覆盖：按设计只「列候选、人工确认」，且有多重范围限制

1. 原件上传**本身不作废**任何缺失的单/行，只在「需求单与同步」页列出缺项候选，需要用户勾选、填原因、一键确认后才同步作废——D-27「确认与同步作废」第 1-2 条；候选计算 `backend/app/services/maintenance_wbdd_reconciliation.py:100` 起（`build_candidates`），确认端点 `backend/app/api/maintenance_wbdd_import.py:170-179`。
2. 确认作废要求**同时有**导入动作键 `action_maintenance_wbdd_import` 和删除动作键 `action_maintenance_demand_delete`——`maintenance_wbdd_import.py:177-179`；前端 `canReconcile={canVoid && canImport}`——`frontend/src/pages/maintenance/MaintenanceDemandsPage.tsx:413`。没有删除权限的同事**看得到候选也点不了确认**（或看不到确认入口）。
3. 只和**最近一次**带来源快照的成功批次比较——`maintenance_wbdd_import.py:107-112`（`latest_source_batch`）；v1.36.5 之前的历史批次没有快照，首次显示「请重新上传」——同文件 `:118-124`。之后若又传了别的文件，前一个文件的缺项候选就被替换。
4. 整单缺失只在本文件出现的**各日期最小～最大序号区间内**判定；文件里没出现的日期、区间外的单号不会被判为删除——D-27「输入和比较规则」第 3-4 条。
5. 单内缺行只比较本文件实际出现、身份无冲突的父单；人工新增行、上传后新增行不列入；**含人工新增/上传后新增明细的缺失整单会被整单保留**——`maintenance_wbdd_reconciliation.py:185-194`。
6. 走「数据中心→数据导入」通用入口虽然也会保存来源快照（`backend/app/etl/pipeline.py:526-548`），但**差异与确认界面只在「需求单与同步」页**；在通用入口上传后不去该页确认，就不会作废。

### 3.3 作废不覆盖：单头状态变了，但项目侧读模型不认

1. 原件里单据状态改为非「已生效」（作废）时，upsert 会更新单头 `data_status`（skip 模式除外）——`loader.py:617-621`（`_MAINT_ORDER_UPD` 含 `data_status`）。
2. 但**明细行的 `is_active` 不在更新白名单内**——`loader.py:622-624`（`_MAINT_LINE_UPD`）；原件作废不会软作废明细，也**不会级联作废关联的现场领用行**（级联只在 D-27 确认或项目总表作废路径里发生）。
3. 读侧口径不一致：
   - 分析、成本按 `data_status == '已生效'` 过滤（`ACTIVE_STATUS_ONLY = True`）——`backend/app/services/query_filters.py:123-131`、`backend/app/config.py:376`；成本重算作用域也只算已生效——`backend/app/services/maintenance_cost.py:395`。
   - 但**项目总表 03、02 概览、主页全局备件行级表、网页行级接口**共用的 `_assigned_lines` **只过滤明细 `is_active` 和 `active_demand_condition`，不看单头 `data_status`**——`maintenance_project_master_workbook.py:464-504`；而 `active_demand_condition` 在生产 `maintenance_cutover_enabled=false` 时恒为真，墓碑也不生效——`backend/app/services/maintenance_demands.py:135-146`。
   - 结果：原件作废的单，在分析页消失、成本被清，但**在项目页/项目总表/全局行级表里仍然显示**（数量还在，成本变空），业务看到的就是「作废没覆盖」。

### 3.4 对照：项目总表 03 回传（通道 B）

- 03 回传本身支持删行=作废、`操作` 列 VOID、改值、加行（`maintenance_project_master_workbook.py:3825-3840`、`:6316-6331`），作废会级联领用（`_cascade_void_site_lines`）。整单全部行作废时会级联墓碑（`:6405-6425`），**但墓碑在 cutover 关闭时对稳定读侧不可见**（见 3.3）。
- 若业务说的「维保需求单」其实是项目总表 03，失败原因更可能是 2026-09-02 报告所述的 `stale_workbook`（导入推进 revision 后整本过期）或作废优先规则，需要看具体回执/报错。

### 3.5 一句话根因（可能性排序）

重传原件时，「覆盖」只部分生效：**改值**被 `edited_source≠wbdd` 整行永久保护（只要在项目总表里动过一次）或被通用导入默认「跳过」模式吞掉；**删行**按 D-27 只列候选、需有删除权限的人确认，且限最近一批、限日期序号区间；**作废**只改了单头状态，明细不作废、领用不级联，项目总表/行级表读侧又不按单头状态过滤。

## 5. 方案（初步方向，待 §4 确认后成案）

- **作废**：项目侧读模型（`_assigned_lines` 等）补单头 `data_status` 过滤，与分析/成本口径一致；评估原件作废是否级联明细与精确关联领用（参照 D-27 确认流程）。
- **改值**：把整行 `edited_source` 保护收窄为字段级保护（只保护人工改过的字段），或给出「原件覆盖人工」的显式选项；回执列出「因人工保护未覆盖」的行和字段。
- **入口**：通用导入识别 WBDD 文件时提示/默认修复模式，或引导去「需求单与同步」页；上传完成后显著提示缺项待确认数量。
- **删行**：若业务要上传即作废，需要修改 D-27 并重新评估风险；否则优化候选可见性与权限提示。
