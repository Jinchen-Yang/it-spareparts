## 1. 原始需求（用户原话，逐字记录，不改写）

> 成品收货也要进入循环池。修好后可选择再测也可以不测。不动，氚云不涉及维修和坏件等等。然后委外回来的都手动选择是直接进闲鱼销售？一类一贴。全自动上架

- 转引来源：任务书 §2.1（2026-11-08 交付）；原句含问号，保留原样。
- 任务书 §2.1 说明：委外去向那句在来源会话里带问号；本次任务把「全部手动选择、可直接去闲鱼」写成明确要求，按此执行，不再把去向清单退回给用户。

**任务书同时明确的执行点**（下面各点是任务书裁定，不是用户逐字原话）：

- 成品收货也入池。
- 修好后可以再测，也可以不测。
- 不写氚云，不改氚云进销存。
- 委外回来的去向全部手动选择，允许直接去闲鱼。
- 全自动上架。
- 复用现有待办派工；工人响应里不能出现项目、供应商、SN。
- 不写变卖台账 `maintenance_bad_salvage`。
- 去电商与 outbox 同一数据库事务；载荷只有 PN 身份、好坏、数量、投递 id，不带项目、SN、成本、价格。
- 售出由商城回写 `mark-sold`。
- 前端页面另案（本需求交付后端行为与契约）。

## 2. 背景与动机

返还收货/外部来源的坏件与成品目前没有「一件实物走到哪、能不能卖」的统一循环事实：检测、维修、委外、待处置、结案分散，且没有把可售件送到商城上架的稳定通道。HOLD PR #520 已有一版后端草稿，但其自述决策 D-0056 / 需求00010 与已合并的 #517 编号冲突，必须整文件弃用重写；#522 的商城契约草案存在 `unchanged` 语义漏洞。本需求依据用户任务书重建循环域：itsp 管循环事实与投递，商城管合帖、标价与上架，itsp 不写氚云、不写变卖台账、不出价、不直接调用闲管家。

## 4. 方案

- 决策：[D-0057 坏件循环池与闲鱼可售意图](../decisions/0037-坏件循环池与闲鱼可售意图.md)。决策: D-0057。
- 总体方案与任务拆解：任务书 §4–§11（T0–T11，顺序不能跳）。本需求跟踪 T0–T9 与 T11；T10 前端由用户另案。
- itsp 侧（T1–T5）：
  - **T1 数据模型**：`maintenance_cycle_unit`、`maintenance_cycle_event`、`maintenance_cycle_sell_intent`；Alembic 新修订从实施时单 head 串接；五个 `page_cycle_*` 权限键默认对所有内置角色（含 admin）为 false，测试夹具单独打开。
  - **T2 状态机、收货互锁、字段裁剪**：入池（`handoff-from-receipt`）、工位转移、成品/修好/委外路径、收货 update/void 与已流转单位互锁、工人视图字段裁剪。
  - **T3 待办接线**：复用现有 `work_item.open_items` / `claim`，两个 subject、公共池领取、转移时开关待办；待办摘要不含供应商/SN。
  - **T4 出站 worker**：租约质量对齐目录 outbox；默认关闭、不监听外网；mock transport 测试；回执语义按 D-0057 §4。
  - **T5 契约文档**：`docs/integrations/cycle-sell-intent-v1.md`，内容与任务书 §8 一致并写明商城尚未实现。
- 商城侧（T6–T9）：T6 只读待核实（十项表）；T7 入账与合帖（幂等账、合帖行、缺图/缺类目/缺标价 blocked、发布模式默认 `off`）；T8 闲管家适配与开关（`dry_run` 不发外网；`live` 需允许名单+确认开关）；T9 售出/取消与 itsp 回写端点。商城待核完成前不编码 T7+、不编造闲管家参数。
- 边界：不合并/不关闭/不改 #520/#521/#522；不部署、不迁移生产、不改发布控制器；测试与本地脚本禁用 `docker rm`、`docker run --rm`、`docker prune` 类命令。
