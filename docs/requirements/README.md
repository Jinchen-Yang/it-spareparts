# 需求工作区（it-spareparts · docs/requirements/）

> 本目录是**维保智能体侧需求的唯一登记处**，也是**文档专家 agent 的工作区**。
> 姊妹仓库 `spareparts-shop`（电商系统）有对等工作区：`spareparts-shop/docs/requirements/`。
> 职责链：登记需求 → 澄清挖掘 → 生成方案 → 持续演进。
> 规则沿用 [AGENTS.md](../../AGENTS.md)：需求文档 ≠ 决策口径；涉及口径的改动仍必须先落 `docs/decisions/` 编号，再动代码。

## 双仓库工作区责任划分

| 需求类型 | 主档仓库 | 另一侧 |
| --- | --- | --- |
| 维保智能体功能（PN 主数据治理／维保业务／经营分析／智能体平台／对外只读接口） | **it-spareparts（本目录）** | 涉及商城消费方时，shop 侧建**关联条目**只登记其本侧范围 |
| 电商系统功能（商品／图库／库存／AI 资料／渠道上架） | spareparts-shop | 涉及上游时，本目录建关联条目 |
| 跨两侧的需求 | 落在**主要实现方**（无法判定时与用户商定，主档唯一） | 关联条目**不复制主档全文**，只写本侧范围＋回链 |

- **编号**：两仓库各自独立流水号（均从 00001 起、五位零填充、只增不复用）。跨仓库引用必须带前缀：`itsp#需求NNNNN`、`shop#需求NNNNN`。
- **写入边界**：每个仓库的文件只在各自仓库内改动；绝不跨仓库写文件。
- 本会话（文档专家 agent）同时维护两侧工作区。

## 目录约定

- 每个需求一个文件：`需求NNNNN.md`，编号从 **00001** 起、五位零填充，**只增不复用、永不重排**。
  作废的需求保留文件与编号，状态改为「已作废」并注明原因。
- 新需求由登记代理按 [`_template.md`](_template.md) 创建，编号 = 当前最大编号 + 1。
- 需求内容**实时更新**：每次澄清、调整、方案变化都要同步改对应文件的正文与「变更记录」，并刷新下方台账的「最后更新」列。不做无记录的静默改写。
- 商城侧（spareparts-shop）提出的需求**不会自动成为本仓库需求**：先建关联条目（状态「待立项」），经管理员确认立项后才转正式需求排期——沿用本仓库既有政策。
- **事后补登（治理建议，非已拍板时限）**：客户输入若先以 issue／决策／分析文档承载，应在后续治理中补登 `需求NNNNN`（可转引原始来源并回链，不复制全文）；补登编号仍只增不复用。依据：2026-11-08 台账治理（[D-0056](../decisions/0036-需求口径确认.md)）与 `team/reports/req/2026-11-08-需求现状与下一轮候选.md` §1.3；具体时限未拍板。

## 需求状态机

`草案` → `细化中` → `已成方案` → `已转issue` → `已实现` → `已关闭`

- 关联条目额外可用 `待立项`（等待管理员确认是否承接）。
- 任一状态可转 `已作废`（注明原因与替代去向）。
- 已关闭的需求再有新变化时，**开新编号**登记，并在「关联」里回链旧编号。
- **状态词收敛（2026-11-08）**：台账与文件「状态」只使用状态机词；暂缓/暂不动工用「草案／已成方案（暂缓：原因与日期）」表达，不再自造「已立项／暂存／开发中」。历史自造词在本次回写中统一替换。

## 文档专家 agent 工作法

1. **登记**：用户提出需求 → 建文件、领编号，在「原始需求」一节**逐字记录原话**（不改写、不概括）。原件未入库或原话不可得时，须**转引**可核查来源（issue／决策／分析文档）并标注「转引」与原因，不得改写或编造。
2. **挖掘**：主动澄清模糊点、列出隐含假设、指出与现有需求或 `docs/decisions/` 口径的冲突与关联，填入「澄清与假设」。
3. **成案**：需求稳定后生成对应方案，写入需求文件「方案」一节；大方案需独立文档时放 `docs/` 对应目录并双向回链，方案中标注 `决策: D-NNNN` 或 `决策: 无`。
4. **演进**：需求变化时更新正文 + 追加变更记录 + 刷新台账（含决策／issue／PR／发布版本列）。
5. **梳理**：定期回看台账与全部在途需求，主动找重复、冲突、可合并、可深化项，向用户提出优化建议——不只是被动记录。
6. **交接**：任何代理凭本 README + 台账即可接手，不依赖某个会话的记忆。
