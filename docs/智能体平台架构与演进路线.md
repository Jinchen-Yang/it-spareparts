# 智能体平台架构与演进路线

> 目标：把"AI 定价助手"从一个聊天页演进成**对标扣子(Coze)/DeepSeek 网页版**的内部智能体平台——
> 服务端会话、知识库、工作流、Skill/Tools 可插拔。本文档定义分阶段路线与数据模型，
> 避免每期功能各写各的、最后拼不起来。
>
> 状态：P0/P1 已落地；P2-P4 为设计先行，动工前按本文档对齐。

> **2026-08-10 更新**：GitHub #217 与 `docs/agent-platform/read-only-agent-domain.md`
> 已成为后续智能体开发的权威边界。本文保留现状与历史路线参考；凡涉及工作流、Skill、
> 文件写入或自治级别的旧表述，必须服从“业务事实/审批/源文件只读，只能生成运行记录、
> 证据和不可变派生 Artifact”的新约束。

## 0. 第一性原理（设计不变量）

1. **数据诚实**：模型只能引用工具/检索返回的库内数据，平台层不给模型任何"编数字"的通道。
2. **权限在数据层**：越权数据不进 LLM 上下文（三期 RBAC 已验证此路线）。知识库/工作流同样：
   检索结果过 `apply_field_visibility` / 行级过滤后才进 prompt。
3. **服务端为唯一事实源**：会话、知识、工作流定义全部入库；前端是纯视图。
4. **通用原语优于预设管道**（二轮迭代的教训）：给模型细粒度工具 + 手册式提示词，
   让模型自己决策；不写死解析规则。
5. **商品身份 = dim_part.id**：一切新功能（检索、知识库引用、工作流节点）引用商品一律 part_id，
   禁止 pn 文本作键（PN 整改的核心约束，违者会绕过合并重定向）。

## 1. 现状（P0/P1 已落地）

```
前端 React/AntD ──/api──> FastAPI
  ChatPage（服务端会话）      api/chat_sessions.py  ← 会话 CRUD + 会话内 SSE 流
  PurchasesPage（采购记录）   api/purchases.py
  其余 6 页                  api/*
                              │
                              ├─ app/agent/
                              │    runtime.py   多轮工具循环（流式/非流式）
                              │    provider.py  OpenAI 兼容抽象（DeepSeek/Qwen-VL，.env 切换）
                              │    tools.py     工具注册表 _REGISTRY（当前 18 个工具）
                              │    prompts.py   场景手册式系统提示词（A/B/C/D/D2/D3/E）
                              ├─ services/chat_store.py   会话/消息持久化 + LLM 窗口
                              └─ PostgreSQL：chat_session / chat_message（迁移 85424bb7cc56）
```

- **会话**：归属 token.sub，本人可见（管理员也看不到别人的对话——报价隐私）。
  共享口令回退登录的身份（sub 自报）禁用会话功能（fb 标记，403）。
  客户端只发新消息；历史窗口（20 条 / 单条 8000 字符）由服务端截取。
  **中断语义**：点"停止"（/chat/cancel）→ worker 收束，已生成部分以 stopped=True
  落库；断网/关页面（无 cancel）→ worker 跑到底，完整答案落库。
  同一会话同时只允许一轮生成（409），消息顺序不会交错。
  连接纪律：流式期间请求级连接先 rollback 还池；worker 每次工具调用后 rollback。
- **工具**（初版 10 个，当前代码已扩展为 18 个）：search_parts / get_part_overview / get_profit_ranking /
  list_recent_purchases / inspect_file / read_file_rows / read_document /
  lookup_prices_bulk / write_excel / write_report。
- **场景**：A 报价 / B 压价 / C 解释型号 / D 询价单批量 / D2 拆整机 / D3 配整机 / E 经营分析。

## 2. P2 知识库（RAG）

**用途**：产品资料、兼容性矩阵、销售话术、供应商档案、SOP 文档——模型按需检索引用。

### 数据模型（additive，不动现有表）

```sql
kb_collection(id, name, description, owner_sub, visibility,  -- private/team/all
              created_at)
kb_document(id, collection_id FK, filename, source_type,      -- upload/url/manual
            file_hash, status,                                -- processing/ready/failed
            meta JSONB, created_by, created_at)
kb_chunk(id, document_id FK, seq, content TEXT,
         embedding vector(1024),                              -- pgvector
         token_count, meta JSONB)                             -- 页码/标题路径
```

- **pgvector**：`CREATE EXTENSION vector`（postgres:15 需换 `pgvector/pgvector:pg15` 镜像
  或编译安装——**部署注意项**，写入 DEPLOY.md 升级章节）。
- Embedding 走 provider 抽象新增 `embed()`（DashScope/DeepSeek 均有 OpenAI 兼容 embedding 端点），
  失败降级关键词检索（pg_trgm 已有，复用型号检索的基建）。
- 入库管道复用 agent_files 的多格式解析（docx/pdf/xlsx/图片→视觉）→ 切块（按标题/页，
  500-800 token）→ 嵌入 → kb_chunk。
- **检索工具** `search_knowledge(query, collection?)`：向量 top-k + trgm 关键词混合，
  返回 chunk 内容 + 来源（文件名/页码），提示词要求"引用注明出处"。
- 权限：collection.visibility + owner_sub 过滤后才进上下文（不变量 #2）。

### 验收场景
"DDR4 和 DDR5 能混插吗？"→ 检索兼容性文档 → 带出处回答；无文档时如实说没有资料。

## 3. P3 工作流（流程编排）

**用途**：把"询价单处理→批量查价→回填→发采购"这类固定流程显式化、可视化（用户说的"工作流程图"）。

### 设计取向
- 工作流 = **DAG 定义存库，执行器跑节点**；节点类型：tool（现有工具）/ llm（一段提示词）/
  branch（条件）/ human（待人工确认，挂起可恢复）。
- 与对话集成：工作流可以作为一个"复合工具"暴露给 agent（`run_workflow(name, inputs)`），
  也可以从前端独立触发——两个入口一套执行器。

```sql
wf_definition(id, name, description, graph JSONB,   -- 节点+边，前端可视化编辑
              version, enabled, created_by, created_at)
wf_run(id, definition_id FK, status,                -- running/waiting_human/done/failed
       inputs JSONB, outputs JSONB, started_by, started_at, finished_at)
wf_run_step(id, run_id FK, node_id, status, input JSONB, output JSONB,
            error TEXT, started_at, finished_at)    -- 全程留痕，可断点续跑
```

- **先做执行器 + JSON 定义 + 运行记录页**；可视化拖拽编辑器放后（先用 JSON/表单建流程，
  前端画只读流程图——React Flow）。
- human 节点 = 平台化的"治理审核"模式（候选审核已验证此交互），挂起的 run 出现在待办列表。

## 4. P4 Skill / Tools 可插拔

- **Tools**：现有 `_REGISTRY` 升级为带元数据的注册器：
  `@tool(name, description, params_schema, roles=("admin","sales",...), category)`——
  按角色过滤 TOOLS 列表（数据层权限不变量照旧是兜底）；新工具文件放 `app/agent/toolsets/`，
  import 即注册。
- **Skill**：= 提示词片段 + 工具子集 + （可选）知识库 collection + 文件模板 的命名组合。
  现在的场景手册 A-E 就是硬编码的 skill；P4 把它表化：
  `skill(id, name, manual_md, tool_names[], kb_collections[], enabled)`，
  系统提示词在运行时按启用的 skill 拼装。新业务场景（如"维保报价"）不改代码、
  管理页上配置即可——这是"像扣子"的核心。
- **MCP 远期**：provider/tools 抽象已是 OpenAI function 格式，将来接 MCP server
  只需把 MCP tool list 翻译进注册器，不动 runtime。
