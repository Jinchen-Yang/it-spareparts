### 3. 权限体系（backend/app/permissions.py + security.py）

- 权限=代码常量三桶（`DATA_GROUPS`/`PAGE_KEYS`/`ROW_KEYS`）+ 每用户 `sys_user.permissions`(JSONB) 覆盖；`effective()` = 模板打底 + custom 覆盖 + `setdefault(False)`；admin 恒 `_full()`。
- **无 `action_*` 前缀、无 `require_action` 依赖**——需新造（仿 `require_page`，security.py:79-92）。
- **三个必须同步的陷阱**：① 新 key 不进 `_VALID` 会被 `sanitize()` 静默丢弃；② `_full()` 只聚合 DATA+PAGE，不改则 admin/boss 拿不到新 action 权限；③ `readonly` 模板 = `{**_full(), 显式关闭项}` 且同时是**匿名 guest 兜底**——action 类必须在 readonly 里显式 False，否则匿名继承 True。
- 字段脱敏：`config.FIELD_GROUPS` 逐字登记 key → `apply_field_visibility` 递归置 None。新价格治理字段必须逐字登记，否则对无权限角色静默泄漏。
- 权限编辑 UI：`GET /accounts/_meta` 返回 `data_keys/page_keys/row_keys/labels`，AccountsPage 按桶渲染——新增 action 桶两端都要加。
- 旧池端点权限现状：池读挂 `page_boss_board`，rebuild 挂 `require_admin`。

## 二、迁移方案

一个新增量迁移，`down_revision = b9e1f0/b9e1f4a7c2d8`（当前 head）。**只加池与约束配置，不改采购/销售事实表**（规格 §21）。

### upgrade

1. **`part_pool` 加列**（先加可空 → 回填 → 收紧非空）：
   - `name varchar(128)`：回填 `'互通池-' || group_id` → NOT NULL；
   - `description text`（可空）；
   - `status varchar(16)` NOT NULL server_default `'active'` + CHECK `status IN ('active','archived')`；
   - `source varchar(32)`：**存量回填 `'legacy_generated'`**（借 server_default 填历史行后改为 `'manual'` 作为未来默认）→ NOT NULL；
   - `version integer` NOT NULL server_default `1`；
   - `created_by / updated_by varchar(64)`（可空）；
   - `created_at timestamptz`：存量回填自 `updated_at` → NOT NULL + server_default now()；
   - 索引 `ix_part_pool_status_updated (status, updated_at)`（规格 §20）。
   - `member_count / needs_calibration / oversized` 兼容保留不动（规格 §15.1）。
2. **`part_pool_member` 主键改造**：drop PK(`part_id`) → 新 PK(`group_id, part_id`)；加 `added_by varchar(64)`、`note text`（可空）、`updated_at timestamptz` NOT NULL default now()；加 `ix_pool_member_part (part_id)`（反查 PN 所在池）。
   - **为什么改**：规格「一个**有效** PN 只能属于一个**有效**池」+「池只归档不硬删除」——单列 PK 会让归档池成员永久占坑，无法加入新有效池。有效池内唯一性改由 PoolCatalog 服务层保证（写路径唯一 + `pg_advisory_xact_lock` 按 part_id 串行化 + 池行 `FOR UPDATE`），归档→恢复时校验成员未被其他有效池占用。
3. **新建 `part_pool_price_policy`**：`id` PK 自增、`group_id` FK→part_pool CASCADE NOT NULL、`purchase_ceiling_ex_tax / sales_floor_ex_tax Money(14,2)`（统一未税）、`purchase_input_value / sales_input_value Money` + `purchase_input_basis / sales_input_basis varchar(8)` CHECK `IN ('ex_tax','inc_tax')`（原始录入口径）、`valid_from timestamptz` NOT NULL default now()、`valid_to timestamptz` 可空、`changed_by varchar(64)`、`note text`、`created_at`。
   - **部分唯一索引 `uq_pool_policy_current ON (group_id) WHERE valid_to IS NULL`**——DB 层保证每池仅一条当前策略（并发双写第二笔撞唯一 → 409）；
   - 索引 `ix_pool_policy_group_from (group_id, valid_from DESC)`（规格 §20）。
4. **序列安全复核**（规格 §21-6）：重跑 `b9e1f4a7c2d8` 的 DO 块逻辑，`setval` 到 `GREATEST(MAX(group_id), 序列高水位)`，幂等。

### downgrade（复审返修后口径：**不是无条件可逆**）

先跑数据丢失守卫：存在**约束价历史行**（drop 表会永久丢失）或**一 PN 多池数据**（恢复
单列 PK 必然 UniqueViolation）时 **失败即停**——RuntimeError + 事务整体回滚，不删任何
数据。守卫通过（即未产生本迁移之后的新业务数据）才继续：删 policy 表及索引 → 删
member 新列、恢复 PK(`part_id`)、重建旧索引 `ix_pool_member_group` → 删 part_pool 新列/
索引/CHECK。**正常使用后的生产回滚一律恢复迁移前数据库备份，不走 schema 降级。**

### 迁移验收（规格 §21 末）

测试证明：迁移前后每个历史池的 **group_id、成员数、成员集合完全一致**；存量池回填 `source='legacy_generated'`、`name='互通池-{ID}'`、`status='active'`、`version=1`；序列 next 值严格大于 MAX(group_id)。

## 六、复审返修（2026-07-13 第二轮，5 个合并阻塞项）

原方案的以下承诺经复审判定为错误或不完整，已按本节修正（以本节为准）：

1. **有效池 ≥2 成员**（《互通PN池》核心规则 5，原方案第五节曾把"空池"列为合法建池场景——错误）：
   `create_pool` 成员去重后 <2 → 400；`update_members` 先按增删差算**终态**，<2 整体拒绝，
   任何删除不落库。迁移回填的历史池不经运行时校验（§21 存量零变化优先），1 成员历史池
   照常改名/归档，只有把有效池成员改到 <2 的操作被拒。不引入"非有效空壳池"状态——
   那需要规格变更另行评审。
