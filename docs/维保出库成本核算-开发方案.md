## 0. 已锁定业务口径（不要再问客户，按此实现）

| # | 口径 | 结论 |
|---|---|---|
| Q1 | 平均价算法 | **当月加权平均**（当月采购总金额÷总数量）；缺当月向前追溯，**追溯≥1 个月必须标注追溯月数，上限 3 个月** |

## 1. 总体设计原则

1. **旁路新增，零侵入现有成本路径**：维保成本是独立管线（新表、新 service、新 API、新页面），不改 `cost.replay`、`profit.recompute`、`COST_METHOD` 等任何现有语义。现有利润测试必须全绿（回归红线）。
2. **复用导入框架全链路**：reader（双表头/F 码识别、列名容差、ffill）→ mapping → transform → loader（`_upsert_facts` 幂等）→ 批次/作业/报告，全部按采购/销售的既有套路扩一类文件。
3. **注意与销售成本口径的刻意差异**：销售毛利用移动加权/FIFO + `ex_tax`；维保成本按客户确认的"当月加权 + 原值税口径标注"。两者并存、互不影响，文档与代码注释必须写明这是客户拍板的差异而非疏漏。
4. 所有新成本字段**必须登记 `config.FIELD_GROUPS`** 脱敏组，防止对无权限角色泄漏。

## 4. 成本引擎 `services/maintenance_cost.py`

新建独立 service（**不改 cost.py**）。入口 `recompute(db) -> dict`（返回各来源计数报告，风格同 `profit.recompute`）。

### 4.1 价格池构建（一次性内存构建，量级：半年 1.2 万采购行，无性能问题）

全部只取 `query_filters.active_orders`（已生效）、`unit_price > 0`、`pn_std NOT IN MAINT_POOL_EXCLUDE_PNS` 的行；按 `part_id` 分组（与 profit 同约定，pn_std 仅展示）：

1. **直配池**：`{(linked_maintenance_order_no, part_id): (加权单价, tax_basis, 采购单号)}`——来自 `f_purchase_order.linked_maintenance_order_no IS NOT NULL` 的采购明细；同单同 PN 多行按数量加权。`tax_basis = 'inc' if order.is_tax_inclusive else 'ex'`。
2. **采购月度池**：`{(part_id, 'YYYY-MM', basis): (Σ qty×unit_price, Σ qty)}`——采购类型限 `COST_PURCHASE_TYPES`（现值含维保需求，直接复用）。**金额用 `qty×unit_price` 而非 line_amount**（其他款项/运费不摊入，§0）。
3. **销售参考池**：同结构——来自 `f_sales_line` join `f_sales_order.business_type IN MAINT_SALES_REF_BUSINESS_TYPES`；`basis = 'inc' if order.tax_rate > 0 else 'ex'`（销售单价字段即含税口径）。

### 4.2 取价瀑布（对每条有效出库行；月份 = 头表 order_date 所在月）

```
M = 出库月
1. A0 直配   : 直配池[(order_no, part_id)] 命中
              → cost_source='direct', trace_months=0, 记 linked_purchase_order_no
2. A1 当月均价: 采购月度池[(part_id, M, 'inc')] 优先，无则 ('ex')
              → cost_source='month_avg', trace_months=0
3. B  追溯均价: for k in 1..MAINT_TRACE_MAX_MONTHS(=3):
                  采购月度池[(part_id, M-k, inc优先)] 命中
              → cost_source='trace_avg', trace_months=k
4. C  销售参考: 销售参考池按同样 当月→追溯≤3月 规则
              → cost_source='sales_ref', trace_months=k
5. 无成本    : cost_source='none', unit_cost/cost_amount=NULL, flag 'no_cost'
```

- 每步取价含税优先（Q4）；`cost_tax_basis` 记实际采用的口径；`price_month` 记实际取价月。
- 金额量化沿用 `cost.py` 的 `_CENT=0.01`。
- **每层语义（前端标签文案）**：direct=「实际·专属采购」(green)；month_avg=「实际·当月均价」(blue)；trace_avg=「预估·追溯N月」(orange，N=trace_months)；sales_ref=「没有采购有销售」(purple，客户指定原话)；none=「无成本」(red)。
- 有效行定义：头表 `data_status = ACTIVE_STATUS`、`order_date ≥ MAINT_COST_START_DATE`、pn 非空、qty 非空。起算日前的行 `cost_source=NULL`（不计价、不进报表，与 `'none'`「算了但没算出来」区分）。`(qty − return_qty) ≤ 0` 的行 cost_amount=0 并 flag `has_return`。

### 4.3 config.py 新增开关（§8 区域，附中文注释）

```python
# —— 维保出库成本（口径为客户 2026-07 确认，与销售毛利的 ex_tax/移动加权刻意不同）——
```

## 10. 边界情况（实测数据得出，实现时必须处理）

1. **草稿/取消单**：按 `data_status = ACTIVE_STATUS` 过滤（2026 数据：已取消 8 单、草稿 5 单、进行中 7 单）；草稿单存在全空明细行（如 WBDD-20260702-0004），空 PN 走 `empty_pn_inactive` 软错误。
2. **退货/退库**：明细有「需求明细.退货数量」列；`cost_amount = (qty − return_qty) × unit_cost`，`return_qty > 0` 时 flag `has_return`。（联通 2023 人工账中有 52 张负成本退库冲抵单——该底稿周期在起算日前不作验收基准，但**退库冲抵口径仍以它为参照与财务核对一次**。）
3. **打包采购占位 PN「一批备件」**：13 行 / 2,333 万，进池会严重扭曲均价，必须按 `MAINT_POOL_EXCLUDE_PNS` 排除（已向客户提出在氚云拆明细）。
4. **PN 质量**：V 码后缀（约 9% 行）`standardize_pn` 已截断，两侧一致，实测不影响匹配率；多段空格 PN（约 5%）`needs_review=True` 原样匹配。
5. **共用合同**：13 张 XSDD 挂多项目，`contract_shared` 标记，绝不据此算毛利（Q5）。
6. **未来日期**：销售数据见 1 单 2026-12-02 录错；维保 transform 对 `order_date > today + 30d` 记 anomaly flag（不拦截）。
7. **产品成本列**：维保导出 90 列无任何成本列——不要试图从维保文件本身取成本。
