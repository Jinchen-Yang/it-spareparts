## 1. 现有接口真实返回结构（基点实测代码）

### 1.1 GET /api/dashboard/sales（services/dashboard.sales_orders）
一张销售订单一行（订单粒度），金额未税：

```
{ total, page, page_size, as_of, effective_sort, ranking_restricted, profit_restricted,
  items: [{ order_id, order_no, order_date, is_future, salesperson, customer,
            business_type, data_status, part_count, total_qty,
            total_revenue, total_gross_profit, linked_purchase }] }
```
**痛点**：只有 `part_count`，没有任何 PN 明细 → 老板看不到"谁买/卖了什么 PN"。

### 1.2 GET /api/dashboard/purchase-orders（dashboard.purchase_orders）
```
{ total, page, page_size, as_of, effective_sort, ranking_restricted, cost_restricted,
  items: [{ order_id, order_no, order_date, is_future, purchaser, source_type,
            data_status, linked_sales_order, part_count, total_qty, total_ex_tax }] }
```

### 1.3 GET /api/dashboard/part-ranking（dashboard.part_ranking）
```
{ window: {date_from, date_to, as_of, cost_method}, profit_restricted,
  profitable: [...top], loss: [...top],
  counts: {total_parts, with_cost, profitable, loss, no_cost_parts} }
行 = { part_id, pn_std, description, brand, revenue, qty_sold, revenue_costed,
       cost_coverage, no_cost, lines, gross_profit_moving/fifo, gross_margin_moving/fifo,
       purchase_price:{wavg,median,min,max,samples,last_date}, sale_price:{同} }
```
**痛点**：只有 date_from/date_to/cost_method/top，无 part_id/pn/池筛选、无排序分页、无池归属。

### 1.4 GET /api/dashboard/pools（services/pool.list_pools）
旧"潜在节省"语义。sort ∈ {savings, member_count}：
```
{ total, page, page_size, sort, effective_sort, ranking_restricted, ranking_capped,
  items: [{ group_id, member_count, needs_calibration, oversized,
            demand_qty, demand_revenue_ex_tax, theoretical_saving, supply_available_upper }] }
```
sort=savings 时**逐池调用 analyze()**（每池 ~4 条 SQL；生产 ~40 池可接受但非批量）。

### 1.5 GET /api/dashboard/pool/{gid}（pool.analyze）
```
{ group_id, member_count, needs_calibration, oversized, window, supply_window,
  demand:{total_qty,total_revenue_ex_tax,note},
  benchmark:{cost_part_id,cost_ex_tax,low_confidence,supply_ok,sale_part_id,sale_ex_tax},
  members:[{part_id,pn_std,description,brand,purchase_price{...supply},sale_price{...},
            purchase_premium_pct,sale_premium_pct,brand_premium_purchase,brand_premium_sale}],
  savings:{theoretical_max,supply_available_upper,executable:null,label,opportunities[]},
  customer_cross_brand:{restricted,multi_brand_customers,customers[]} }
```
**注意**：成员 `purchase_price` 用的是**供应窗口**（today−365 → today），非页面窗口；无约束价、无订单板块。

### 1.6 约束价现状
`part_pool_price_policy`（valid_to IS NULL 唯一当前行）：`purchase_ceiling_ex_tax` / `sales_floor_ex_tax`（统一未税；含税录入 ÷1.13）。仅 /api/pools* 管理接口返回，看板侧完全没接。

## 2. 新旧接口兼容策略

**全部改动纯增量（additive）**，不改名、不删字段、不变现有字段语义——冻结的 BossBoardPage 旧前端零感知：

| 接口 | 增量 |
|---|---|
| /dashboard/sales, /purchase-orders | items 每行加 `parts[]`、`pn_count`、`pn_preview`、`total_quantity`、`total_amount`、`occurred_date`；旧字段（part_count/total_qty/total_revenue/total_ex_tax…）原样保留 |
| /dashboard/part-ranking | 新增 query 参数 `part_id/pn/pool_group_id/sort/order/page/page_size`（全部可选，缺省=旧行为）；响应加 `filters` 回显 + `items` 分页块 + 行内 `pool_group_id/pool_name/order_count`；profitable/loss/counts 原样保留 |
| /dashboard/pools | sort 白名单扩展（旧值 savings/member_count 继续有效）；items 每行加 `name/description/purchase_metrics/sales_metrics/max_purchase_price/min_sale_price/purchase_violation_count/sale_violation_count`；旧 savings 字段仅在旧排序路径下计算（新排序路径置 null——旧前端不会带新 sort 值，故不受影响） |
| /dashboard/pool/{gid} | 加 `policy`、池级 `purchase_metrics/sales_metrics`、成员级 `purchase_metrics/sales_metrics`（**页面窗口口径**，与遗留 supply-window 的 purchase_price 并存不互改）、`purchase_orders`/`sales_orders` 订单板块（分页）；旧字段原样 |

版本号（version.ts）按任务约束不动——前端集成 PR 再升。

## 3. SQL 聚合方案与防 N+1

新建 `backend/app/services/pool_metrics.py` 作为池指标**单一口径源**，dashboard/pool 共用：

1. **订单 parts 批量装配**（sales_orders / purchase_orders）：先取当页订单（现有 2 条 SQL：count + page），随后**固定条数**批量查询，与订单数/页大小无关：
   - ① 当页全部订单行 + DimPart（`WHERE order_id IN :page_ids`，一条）；
   - ② 行内 part_id → 有效池映射（PartPoolMember ⋈ PartPool WHERE status='active'，一条）；
   - ③ 涉及池的当前约束价（valid_to IS NULL，一条）；
   - ④/⑤ 涉及池在**查询窗口**内的采购/销售加权均价（GROUP BY group_id，各一条）。
   合计新增 ≤5 条 SQL/请求，**禁止逐订单查询**。pn_preview/pn_count 由 ① 在 Python 内聚合，零额外查询。
2. **池列表统计**（pools）：不逐池 analyze，改 4 条批量 GROUP BY group_id：采购指标+越线数（⋈ 当前策略，FILTER 单价>ceiling）、销售指标+越线数、当前策略、成员数（池行冗余 member_count 直读）。排序在 Python（活跃池 ~40，POOL_RANK_ANALYZE_CAP=500 封顶）。
3. **池详情订单板块**：每板块 count + page 两条，`LIMIT/OFFSET` 分页返回 total，不静默截断。
4. **排名筛选**：沿用现有单条 GROUP BY 聚合，追加 WHERE（part_id 精确 / pn_std 相等精确 / 池成员子查询）；池归属批量映射一条。

**统计口径**（全部沿用现行）：
- 金额一律未税（pricing.py 单一真值源：销售 ÷1.13；采购按 is_tax_inclusive）；
- 只统计 `已生效`（query_filters.active_orders）；`upper = min(date_to, today)` 排除未来；
- 采购价格统计限 `COST_PURCHASE_TYPES` + 单价>0 + 数量>0（与 _purchase_price_stats 同）；
- 销售价格统计限 `counts_revenue=True` + 单价>0（¥0 赠送/换货不进价格口径，与复审 P1-6 同）；
- **metrics 块三元组自洽**：total_amount/total_quantity/weighted_avg_unit_price 同一"计价行"全集，`wavg = amount/qty`，qty=0 → wavg **null**（绝不给 0 冒充均价）；
- 正式利润只算已配成本行；未配成本营收/覆盖率照旧单列（本轮不动 KPI）；
- 越线计数：行级、**严格不等**（等于约束价不越线，§13）、按**当前**约束价回看窗口内历史（分析标签，非按历史时点约束价）；约束价该侧为空 → 该侧 violation_count = **null**（“无约束”≠“零越线”）；
- 金额 round 2 位、比例 round 4 位（与利润引擎/_r 一致）；
- 只统计 active 人工池；归档池 404/不进清单（不重启自动 rebuild）；一个 PN 同时只属一个有效池（pool_catalog 写路径已保证）。

## 4. 权限与脱敏保护清单

递归脱敏靠 `config.FIELD_GROUPS` 精确键名（越线派生键必须登记——Slice 2 既定纪律）。**新增登记**：

| 键 | 组 | 说明 |
|---|---|---|
| `pool_avg_purchase_price` | purchase_cost | 池采购均价（订单行参考 & 成员指标内不复用此名的场合用容器遮） |
| `purchase_metrics`（容器） | purchase_cost | 池/成员采购指标整块（内含 wavg 等与销售侧同名键，容器级遮，沿用 purchase_price 容器先例） |
| `pool_avg_delta` / `pool_avg_delta_pct` | purchase_cost | 与池均价差额/比例。**两侧同名**：销售侧行价被 purchase_cost 遮（unit_price 同名先例）而池销售均价公开 → 差额也必须随 purchase_cost 遮，否则 `均价+差额` 反推行价 |
| `manual_limit_delta` / `manual_limit_delta_pct` | purchase_cost **和** pool_price_governance（双登记，任一组关闭即遮） | 与约束价差额/比例：`价-差=约束价`、`价-差=行价`，两头都能反推 |
| `max_purchase_price` | pool_price_governance | 池列表/详情返回的人工采购上限（=purchase_ceiling_ex_tax 的契约名） |
| `min_sale_price` | pool_price_governance | 人工销售下限 |
| `purchase_violation_count` / `sale_violation_count` | pool_price_governance | 越线标记/计数随治理权限遮（config §12 注释既定：防靠排序/颜色反推金额） |

**沿用既有登记，无需新增**：nested parts 的 `unit_price_ex_tax`、`amount`、`total_amount`（均已在 purchase_cost）；`purchase_ceiling_ex_tax`/`sales_floor_ex_tax`（pool_price_governance）；`customer`（customer_info）；`supplier`（supplier_info）；`gross_profit*`（profit_amount）。

**结构性收敛（服务层，字段 mask 管不到的）**：
- `reference_status` 对无采购成本/利润权限**仍可见**（任务明确要求，状态非金额）；但对 `data_pool_price_governance=False`：涉人工约束价的状态（above_manual_max/within_limit/no_manual_limit/below_manual_min）**降级为仅池均价口径**（within_pool_average/above_pool_average/below_pool_average）并置 `manual_reference_restricted=true` —— 否则"多行可见价格 + 越线布尔"可二分逼出约束价原值；
- 按 `purchase_total/purchase_average/purchase_violation_count/sale_violation_count` 排序对相应数据被遮角色：退回 member_count 序 + `ranking_restricted=true`（行序即侧信道，沿用三轮复审先例）；`sales_total/sales_average` 为公开聚合，不受限；
- 受限销售（is_scoped_sales）：销售侧 nested parts 与池详情销售订单板块 = **逐单成交明细**，整段置空 + `parts_restricted`/`restricted` 旗标（沿用 anonymize_sales_rows / customer_cross_brand 先例，2026-06-13 甲方口径）；
- 排名 `profit_restricted` 撤榜逻辑原样保留并覆盖新 `items` 块（毛利排序时）。

**刻意接受的过度脱敏（安全方向，不泄漏）**：`total_amount`/`amount` 已登记在 purchase_cost，销售侧同名键对 cost-blind 角色会一并置 null——该角色仍可从未登记的 `total_revenue`/`revenue` 读到销售额，不损失功能；方向是"多遮"而非"漏"，且与 unit_price 同名双侧遮的既有先例一致。

**已知推断残余（记录在案）**：`reference_status` 对 cost-blind 可见（任务要求）+ 池销售均价公开 → 状态布尔携带 1 bit 序关系信息；无法既满足"状态可见"又零信息 —— 金额与差额全遮后无法恢复原值，视为可接受（与"甲方要异常可见"的需求权衡）。

## 6. 测试与验收指标

新增测试（对应任务七 1–10）：
1. 多 PN 订单 → parts 完整返回（PN 数、字段齐全、金额未税正确）；
2. 分页 total 按订单数（造 1 单 3 行验证 total=1）；
3. **N+1 证据**：SQLAlchemy 事件计数器，2 单 vs 20 单查询数相等（常数）；
4. 时间/PN/part_id/池筛选单独 + 组合正确；pn 精确不混相似 PN（PN-A 不召回 PN-A1）；part_id 与 pn 同给时 part_id 优先；
5. 池 metrics 合计/加权均价/订单数/数量与手算 fixture 一致；qty=0 → wavg null；
6. 归档池：不进 pools 统计/排序/详情（404 带原因）；
7. 未来单、非已生效单不进 metrics/越线计数；
8. 无成本行不进正式利润，进未配成本营收（排名 items 口径）；
9. 受限账号：nested parts 价格/差额/约束价/毛利递归置 null；reference_status 仍可见；governance-blind 状态降级 + 差额遮；全端点 `_leaky_keys` 语义扫描扩展新键；受限销售 parts 整段空；
10. 约束价单侧为空：不标 above_manual_max，violation_count=null，状态=no_manual_limit（非 within_limit）。
