## 独立复审返修（合并前）

首轮独立复审结论为「不可合并」，发现并复现 3 个 P0 与 3 个 P1；本分支追加修复后再次对抗复审通过：

1. 受限销售不再收到公司级逐单销售汇总；服务层在任何业务 SQL 前返回
   `orders_restricted=true / total=null / items=[]`，客户、销售员、单号及排序条件均不能成为存在性侧信道。
2. 销售/采购订单响应显式声明 `contract_version=2`。前后端滚动发布发生版本偏斜时，旧接口不再导致白屏；涉及旧接口不认识的 PN/池/采购员筛选时失败关闭，明确显示「服务升级中」，不展示可能错误的数据。
3. 订单详情使用 `order_no` 全等查询（20+ 相似前缀单的用例仍精确命中），并把单号写入访问日志。
4. 默认有效订单即使收到未来 `date_to` 也会裁到今天；仅显式「全部状态」诊断视图保留未来单。
5. 池列表的节省排序改成批量聚合；池数量从 2 增到 12 时 SQL 查询数保持不变，且需求量、营收、理论节省、供应上限与单池分析逐项一致。
6. 池深链统一保留当前 `from/to`；不可能日期、反向/半开窗口均失败关闭；周/月趋势点击不会越过全局结束日期或今天。
7. 无型号查询权限时 PN 和柱图均为只读展示；新交互均使用真实 `Link`/`Button`，不再用无键盘语义的伪链接。

## 已知限制

1. 销售订单/池列表的「金额合计」字段与成本键同名，对 cost-blind 账号被后端**有意过遮**（PR#93 既定取舍）——前端统一显示「无成本权限」。
2. 池筛选选项取自 `/dashboard/pools`（page_size=100 封顶，生产 ~40 池充裕）。
3. KPI/趋势仅受时间筛选影响（后端无 PN/池维度参数），块头明示统计范围，不静默假装全局生效。
4. `page_pool_analysis` 权限键是后端为未来「全员池价格分析页」预留的（甲方 §12），当前池数据端点均由 `page_boss_board` 把门，故 /pool-analysis 路由同门；给全员开放需后端另开数据面，不在本 PR 范围。
