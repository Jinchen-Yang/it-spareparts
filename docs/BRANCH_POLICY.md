# 分支与生产审批规则

管理员：杨金臣（yangjinchen），GitHub 账号 **@Jinchen-Yang**。
本规则来自管理员在 2026-10-10 的明确指令，覆盖历史文档中的“所有 PR 合入 main”等冲突指引。

## 分支职责

- `main`：受保护的生产发布线，稳定性优先。仅接收管理员批准的发布或修复。
- `test`：Beta 测试与集成线，保留原 main 的开发成果，包括尚未获准生产的备件循环功能。
- 日常 `feat/*`、`fix/*`、`codex/*`、`claude/*` 等从 `test` 开发，PR 默认以 `test` 为目标。
- 测试环境使用 `test`；生产只能部署管理员批准的 `main` 精确提交。合并不等于部署，实际已部署 SHA 和镜像另记发布记录。
- 不将整个 `test` 自动提升到生产。发布 PR 必须明确本次范围，排除未批准功能和迁移；必要时从 `main` 创建独立发布分支，挑选已验收提交。
- 本仓库是 IT 备件系统；独立商城 IT-shop 的需求不自动成为本仓库的需求。跨系统边界必须先由管理员确认。

## main 的强制审批

1. 开发者准备 PR、精确 head SHA、变更范围、CI 结果、验收证据、迁移影响、备份及回滚方案，联系杨金臣管理员审批。
2. **必须由 @Jinchen-Yang 对当前候选版本提交 GitHub `APPROVED` review**。其他人的批准、CI 通过、机器人评论、文档中的“甲方确认”均不能替代此审批。
3. GitHub 配置全仓库 CODEOWNER 为 @Jinchen-Yang；main 要求至少 1 个批准且包含 Code Owner 批准。新提交使旧批准失效，最后一次推送须由不同人员批准。
4. 后端测试（pytest + 迁移链验证）与前端类型检查 + 构建必须通过，分支保持最新，讨论全部解决；管理员同样受保护限制，禁止强推和删除 main。
5. AI 代理即便持有管理员凭据，也不得代管理员提交批准、伪造审批、使用管理员绕过、临时关闭保护或自行认定已获批准。没有明确的人工审批就停在待审批状态。
6. GitHub 不允许作者批准自己的 PR。需要进入 main 的 PR 应由其他开发者账号发起，并由 @Jinchen-Yang 审批；不要为了让管理员自己发起的 PR 通过而降低规则。
7. main 合并后的生产部署仍须管理员明确授权，先完成备份和可执行回滚方案，再按精确 SHA 发布并做真实环境验收。
