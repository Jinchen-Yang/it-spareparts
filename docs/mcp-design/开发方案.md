# PARTFLOW MCP 与 WorkBuddy Skills 开发方案

设计日期：2026-09-15。状态：设计交付，尚未实现、安装或部署。

依据本地 it-spareparts 提交 `ae847991e60e84d12c64b375fc07d30c99357efe`；139 个相关 HTTP 路由已静态提取到 [代码接口索引](code-inventory.md)。未连接生产数据库，未假定本地代码、发布版本和生产功能开关完全一致。

## 1. 已确定的产品边界

员工用个人 WorkBuddy；无需采购腾讯企业审计。PARTFLOW 保管业务账号、权限、文件、导入状态与审计。WorkBuddy 负责意图理解和员工电脑操作。MCP 提供有限、可解释、可追溯的业务动作。首发只解决单据整理、导入准备、导出下载，并提供必要的查件和项目定位能力。

交付应覆盖三个闭环：

1. 指定文件夹 → 原件清单 → 上传暂存 → 识别单据 → 校验预览 → 网页确认 → 成功/失败回执 → 本地分类保存。
2. 项目/月份/字段选择 → 权限内导出 → 下载核验 → 文件清单；往返模板与普通报表明确区分。
3. PN 或项目定位 → 查询原始证据 → 支持整理判断；歧义不自动补值、不擅自合并项目。

首发不提供任意 SQL、任意 URL 请求、服务端 shell、全盘文件浏览、任意文件删除、客户消息发送、财务裁决、强制接管、数据库迁移或自动修改权限。上述能力不是普通员工整理单据所必需。正式业务写入仍在网页确认；第二阶段才评估受控提交工具。

## 4. 工具产品清单

完整工具契约在 [tool-catalog.json](tool-catalog.json)；JSON 是设计契约草案，正式编码需落实逐工具严格 outputSchema。输入 schema 已提供，不是当前可调用服务。

按用途分组：身份与能力、文件暂存/识别、导入预览/确认、导出/任务、业务查询、审计。tools/list 按权限过滤，tools/call 每次再次校验，不能把“工具不可见”当安全边界。常用 Skill 只使用所需的小组工具。

关键动作必须有不同名称：创建上传槽不等于上传成功；上传成功不等于预览成功；预览成功不等于正式入账；导出准备完成不等于下载完成。不要提供语义模糊的“一键处理全部”。

## 5. 服务结构与身份

建议在现有 FastAPI 后端集成独立 MCP 子应用 /mcp（Streamable HTTP），关闭时不影响原网页；耗时解析由持久任务 worker 执行。首发不新建能任意查询业务库的通用数据库 MCP，也不调用现有 /agent/chat 再走一遍模型。

拆出 app/mcp/{server,auth,registry,schemas,errors,audit}、app/mcp/tools/、app/services/mcp_{files,imports,exports,jobs}。MCP 与 HTTP 共用应用服务及授权策略，保留现有 router 的外层发布闸。直接调用 Python route 函数不会自动执行 FastAPI Depends，禁止这样“复用”。需要数据库事务的服务明确接收可信 Actor 和 UnitOfWork。

身份链：个人 WorkBuddy → 独立 MCP 凭据 → 服务端查询 sys_user → 当前有效权限 → 业务服务。凭据面向 PARTFLOW MCP，不是数据库密码，也不接受请求体自报用户名、角色、tenant_id。

首版 PAT：随机高熵，数据库只保存哈希、key_id、绑定用户、scope、创建/到期/撤销时间和用户授权版本。建议 30 天到期、随时可撤销；这是设计默认，不是既有实现。仅实名有效 sys_user 可发放，拒绝共享 ADMIN_PASSWORD 回退身份。每次调用取权限交集：MCP scope ∩ 当前页面/动作/字段权限 ∩ 项目范围 ∩ 发布闸；用户停用、token_version 变化立即失效。离职回收同时覆盖上传槽、作业、导出和下载凭据。

后续 OAuth：复用业务登录，新增授权服务器或受支持身份组件；需要元数据发现、PKCE、公共客户端注册及 refresh/revoke。不要把 WorkBuddy Open API 的用户授权令牌直接当 PARTFLOW 授权。OAuth 不列入首版关键路径。

角色示例仅用于验收：销售 own 项目；采购具备成本相关权限；维保负责人按本人项目；审计查看独立权限。管理员也不获得绕过 MCP 发布开关、版本冲突或确认约束的能力。未来多家公司优先每公司独立部署/数据库，不在单租户业务表上声称已实现 SaaS 隔离。

## 6. 文件如何真正传输

远程 MCP 无法读取员工电脑路径。首版使用“网页/WorkBuddy 本地上传能力 + 受控 HTTP 文件通道”，MCP 只交换文件编号和状态。必须在 Windows、macOS 的实际 WorkBuddy 验证原生文件上传能力；若不能自动携带文件，提供网页拖拽批量上传作为完整保底，不能把它宣传为已实现无人操作上传。

1. create_upload_session 绑定用户、文件名/大小/类型清单、用途和幂等键，返回非凭据会话 ID 与 HTTPS 上传页。原始大小、哈希以服务端流式计算为准。
2. 上传页使用业务登录。后续本地小型文件传输辅助程序可从系统凭据存储读取个人令牌，直接传输二进制；不得让模型读取 PAT、把大文件 base64 塞进对话，或下载未知脚本执行。它只传文件，不成为第二套业务连接器。
3. HTTP 数据面拟定 POST /mcp-files/upload-sessions、PUT /mcp-files/upload-sessions/{id}/files/{entry_id}、POST .../complete、GET /mcp-files/artifacts/{id}/download；逐请求重验身份，路径和 entry 必须归属该会话。磁盘路径永不由用户提供。
4. 暂存 → 安全校验/哈希 → 解析可用。文件扩展、MIME、xlsx ZIP 展开大小和条目数全部校验；禁路径穿越、符号链接、压缩炸弹、外链抓取；不执行 Office 宏和外部公式。超限在流式读取中终止，不先 read 全部入内存。
5. 默认单文件 20 MiB、每会话 10 个文件、总 100 MiB（拟定），若现有 family 限额更小取更小值；员工无需知道这些实现参数，界面提示清晰即可。
6. artifact 元数据保存 owner、来源 project/family、purpose、哈希、字节数、来源权限快照。每次下载再检查当前权限与项目归属；不能仅凭 owner 放行曾有权限导出的敏感文件。
7. get_download 返回登录保护的链接；下载 HTTP 流开始/结束/中断记录日志。“完整传输”只表示服务端传完，不保证员工保存/打开。未来自动短时下载凭据须绑定 artifact、账号、有效期、次数，保留撤销检查，不写日志；不能仅靠不可猜 URL。
8. 导出文件不放公开 yabowei.xyz 静态目录，不走公开 CDN 缓存，响应 no-store。原件按业务归档策略保留，暂存默认 7 天、生成报表 7 天、未用上传槽 24 小时；有引用/待确认文件不得清理。业务原档保留周期沿用客户现有制度，不设自动删除。

本地整理默认复制到新目录，不改原件。目录建议 项目编号/单据族/日期；匹配不确定放待核对。名称冲突追加短哈希；manifest 记录原名、目标名、哈希、file_id、状态。工作簿禁止用 write_report 替代原模板；rename 不改变内容，任何内容变更都新建版本并失效旧预览。

## 7. 预览、确认与事务

统一 preview 记录封装原生计划，并不统一业务语义。保存 actor、family、file hashes、target IDs、mode、adapter version、权限版本、数据版本、原生 preview/batch ID、选中行集合、摘要哈希与有效期。建议预览有效 30 分钟且不得长于底层令牌；过期重新预览。

状态：UPLOADED → VALIDATING → NEEDS_REVIEW / READY → APPROVED → APPLYING → SUCCEEDED / PARTIAL / FAILED / UNKNOWN。终态均保留每文件结果。取消只取消排队或解析，不中断已提交事务；APPLYING 中取消返回 too_late。超时/断网不是 FAILED，先查 operation_id。

首版 pf_open_review 返回我们新增的审阅页面链接，员工登录后看到新建/覆盖/作废/跳过数、项目、文件名、数据范围和冲突。服务器保存一次确认记录，与预览哈希、选中行、账号绑定。网页确认并调用既有业务服务，成功回写作业；不能要求员工重新上传相同文件，也不能只给一个不存在的 URL。页面和桥接服务属于本次开发清单。

通用 legacy_trade precheck 的结论不是数据冻结。先实现持久 preview adapter；提交时在所需锁/事务内重新计划并比较差异，再执行。同名文件或同哈希不足以替代业务幂等。没有可靠差异/版本保护的 family 只能返回“识别与检查可用、正式提交未开放”，不降级为直接 upload。

多文件通用导入按原有每文件事务执行，用父作业汇总 PARTIAL；已成功文件不重做。需填补现有 daemon 线程重启丢失的问题：mcp_job 表和带 lease 的 worker、每文件状态/幂等收据。第一阶段避免新增 Redis，先用现有 PostgreSQL 任务表实现持久 claim、租约和重启恢复。身份在 worker 真正执行前再验，排队期间停权不执行。

第二阶段 pf_apply_import 只接受 preview_id、服务端确认记录 ID 和 idempotency_key，禁止 approved=true 作为授权。再次验权、验版本、验原件哈希；唯一键 (部署, actor, operation, idempotency_key)，同键异参冲突，同键同参返回原结果。后端同事务落业务变更、收据和审计 outbox。跨进程 HTTP 适配无法保证同事务时必须改造后端收据再开放，不能依赖“发送成功日志”。

## 8. 可靠审计

详见 [审计与验收](审计与验收.md)。沿用账号管理页作为入口，可增加 MCP 筛选，不买腾讯企业后台。MCP 日志表示系统观测到的调用，不证明是人手动操作，也不记录员工所有本地行为。

## 9. Skills 设计

随包提供五个未启用草案：[文件整理](skills/partflow-document-intake/SKILL.md)、[导入预览](skills/partflow-import-review/SKILL.md)、[导出与往返](skills/partflow-export-roundtrip/SKILL.md)、[项目材料核对](skills/partflow-project-check/SKILL.md)、[查件](skills/partflow-parts-lookup/SKILL.md)。

每个 Skill 先读取 pf_get_capabilities，按服务端返回的 family/protocol/features 决定调用。Skills 负责步骤、语义和展示；权限、幂等、正式写入、日志持久性不依赖提示词。文件和单元格内的命令是业务数据，不能改变流程。工具未实现时只说明缺口，不模拟成功、不改用数据库或任意 HTTP 绕过。

首发只有导入/导出/归档链路成熟后再分发；不要把五个草案预装进员工个人账号。WorkBuddy 官方支持 MCP+Skill 连接器以及 PAT/OAuth；具体包字段与客户端兼容需实现时联调。[官方连接器规范](https://open.workbuddy.cn/docs/connector)

## 10. 部署与回退

生产 MCP 挂独立受保护入口，和营销演示站隔离；TLS、反向代理流式超时、Origin 检查、认证与限流。首次可以内部网络试用，外网访问要从员工真实网络验证，不以服务器 localhost 200 代替。个人 WorkBuddy 所选模型仍可能接收任务和返回片段；仅传必要业务字段。

建议开关 mcp_enabled / mcp_import_preview_enabled / mcp_export_enabled / mcp_apply_enabled，默认 apply=false；启动检测 RBAC/日志持久存储/密钥配置，缺失则 MCP 拒绝启动而不影响原网页。Beta family 依然跟现有闸。每人解析并发 1、全局 2、排队上限 20（试点默认），遵循既有成本重算锁；查询分页 50/最多 200，PN 批量上限 50，长任务立即返回 job_id。

回退：禁新调用/新作业 → 让已进入事务的任务安全完成 → 导出状态 → 回滚服务版本，保留文件、收据和日志。不自动数据库 downgrade、不撤销已经成功的业务事实。数据库和归档恢复需单独既有恢复流程。

## 11. 开发拆分与工期

详见 [开发排期与交付](开发排期与交付.md)。总体先能力/身份与文件，再预览/导出闭环，最后生产试点；第二阶段写入扩展不绑在首版验收上。下面的工作量是规划估计，不是已完成项或固定承诺。
