## 3. 解析问题清单（有证据）

**P1 列名变体 `项目名称` 未映射 → project_raw 丢失并被覆盖为 NULL。**
- 证据：`scripts/projcheck.py`。09-28 以后的 47 个批次最后写入 1,874 单，project_raw 非空 0。
- 因为 loader 用 upsert 把 excluded 值写进去，这些单**原来有的项目名也被冲掉了**。
- 影响：近一年 project_raw 覆盖率只有 83.8%，项目维度的统计会漏单。

**P2 缺失列被当成空值，覆盖已有值。** storage_center 是典型：121 个文件无此列，它们最后写入的 4,190 单全为 NULL。这与字段契约 §2.3（not_provided ≠ 空）冲突。receiver_address 已有例外处理，其余字段没有。

**P3 记录ID 模板整文件静默丢弃。** 6 个文件的数据行全部判 missing_raw_id、0 行入库，批次仍记 success。例：批次 243「维保备件需求单2026_09_01_19_48_45.xlsx」，289 行。上传者看不到失败。

**P4 个别调整发货仓 → adjust_warehouse_flag 全部为 NULL（映射语义错）。**
- 文件里有 9,694 个值，DB 为 0。
- replay 证实这一列装的是**仓库名**，不是 是/否。例：`9.8-9.11维保备件需求单.xlsx` 第 118 行值为「广州成品仓」，解析结果 None。
- transform 按 bool 解析，只接受「是/否」（transform.py:439），共丢失 9,609 个值，且只计入 rows_display_issue，没有报错。

**P5 历史批次的展示字段从未回填。**
- db_compare：1,771 单、3,712 行的展示字段 DB 为 NULL，但文件里有值。
- 它们的最后写入批次是 07-02 / 07-28 的早期导入。当时代码还不写展示列，此后没有新文件覆盖这些单。
- 例：文件 `维保备件需求单_2026-07-28-18-09-29-167.xlsx` 行 3b8bb1，库房需发数：文件 2.000，DB NULL。

**P6 早期代码按 30 字截断，痕迹仍在库里。**
- 文件 `维保备件需求单_2026-08-17-22-04-12-719.xlsx` 的多列：文件 33~49 字，DB 恰好 30 字。涉及收货人、收货人电话、收货地址、仓管员、快递单号#、选择收货地址。
- 差异数：warehouse_keeper 11,271，receiver_phone 2,510，receiver_address 7,341，express_no2 7,674。
- 现行 spec 长度更长（64/128/32…），但收货人电话在 32 字处仍会截断（文件最长 79 字）。现行代码仍会截断，见 §4。

**P7 核心单头字段不按 DB 长度裁剪。** demand_type/business_type/data_status 是 16，salesperson/warehouse 是 64，project_raw 是 256。transform 不裁剪，超长就会整批失败。目前文件最大长度都在限内（最长项目名 47 字），属潜在风险。

**P8 单头只取每张单的第一行。** 后续行的不同值被静默忽略，地址除外。冲突统计见 §4。

**P9 坏日期静默置 None。** maint_start/maint_end 解析失败直接变 None，不计数、不报错。文件侧这两列全是 `YYYY-MM-DD` 字符串，目前未见坏值。

**P10 需求数量为空按 0 计（R10 / D-31）。**
- 入库时保留 NULL，读取侧按 0 处理（maintenance_return_request_summary.py:198、maintenance_dashboard.py:2082、inventory.py:211）。
- 现在只有 1 行 NULL、3 行 =0。规模小，但这一行在看板上和「真需求 0」无法区分。
- bad_number 会**整行丢弃**，而不是置 NULL；数量见 §4。

**P11 express_no：文件为空、DB 有值，19,820 单。** DB 里的值都很短（约 3 字）。来源不明，可能有别的写入路径，**未核实**。

**P12 order_date 1 单不一致。** 文件 2025-10-27，DB 2025-12-04（单 d5116f）。原因未查明。

**P13 产品成本（118 个文件）未映射。** 是否需要入库待产品判断。

**手工修改不算解析错误，单列：** qty 22、serial_numbers 18、description 1、return_qty 1。都是 D-34 字段保护下的 manual_override。

- 数量列文件侧都是 int，解析后没有改值（number_changed 0）。
- 日期列都是 `YYYY-MM-DD` 字符串，没有解析失败。
- 合并单元格经 ffill 后，单头字段在单据级 100% 还原。
- 多 sheet（Hidden_Options）不影响：reader 只读第一个可见页。

## 5. 结论与建议（仅建议，未改代码）

**稳定字段**（文件与库一致，类型安全）：
- 主键与单据号：数据ID、需求单号、需求明细.数据ID。
- 制单日期、销售订单、客户名称、需求类型、业务类型、出库仓库、维保起止日期。
- 需求明细.需供货产品、需求数量、各类数量列。
- 发货仓库/ObjectID、发货SN。

**有风险的字段：**

| 优先级 | 问题 | 影响 | 建议 |
|---|---|---|---|
| 高 | P1 项目名称(必填) 未映射 | 09-28 起新单全部没有项目名，旧值被 NULL 覆盖（1,874 单）；项目维度统计漏单 | mapping 加别名 `项目名称(必填)`/`项目名称` → project_raw；修复后重放 09-28 以后的文件 |
| 高 | P4 个别调整发货仓按 bool 解析 | 9,609 个调整仓信息丢失 | 改成 str 或修正映射，先跟业务确认这一列的含义 |
| 高 | P2 缺失列覆盖成 NULL | storage_center 等字段被新导出清空（4,190 单） | loader 按字段契约 §2.3 区分「列不存在」和「值为空」：列不存在就不 SET |
| 高 | P3 记录ID 模板静默 0 行 | 6 个文件（3,493 行）数据没入库，批次却显示 success | 旧模板要么支持 记录ID→raw_id，要么 precheck 直接拒绝；0 行入库的批次不应标 success |

## 6. 未验证 / 受阻事项

- 没在隔离库跑完整的 `run_import`：只做了内存 transform 回放，加上与快照的逐值比对。
- 绝大多数字段的业务含义没有文档出处，已标「含义未确认」。
- 7 个 superseded 批次没有单独分析。
- express_no 的另一写入来源（P11）、order_date 不一致（P12）未查明。
- 枚举取值统计脚本（distinct.py）因表头读取失败放弃；P4 的取值已由 replay 样例证实（仓库名）。
- replay 只做到 transform 这一层，loader 的 upsert 覆盖行为（P2）是用快照数据反推的，没有实际执行写库验证。
