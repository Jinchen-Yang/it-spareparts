# 账号与权限中心 v2 — 编码前设计方案

日期：2026-07-14 · 分支：`feat/permission-center-v2` · 基点：`23723aa`（v1.13.1, PR#91 后 main）

## 0. 问题与现状审计结论

甲方核心痛点：权限项是开发语言（`data_purchase_cost`）不是业务语言；不知道每项"能看什么/能做什么/依赖谁"；勾了权限仍进不了页面（依赖不透明）；不能批量设置；职位模板是 Python 硬编码（`permissions.py ROLE_TEMPLATES`）不可改不可增。

现状（基点代码）审计事实：

| 部件 | 现状 |
|---|---|
| 权限键 | 19 个：5 `data_*` + 11 `page_*` + 2 `action_*` + 1 行级（`own_customers_only`） |
| 模板 | `ROLE_TEMPLATES` Python 字典，5 角色（admin/boss/sales/purchaser/readonly），不可运行时修改 |
| 账号自定义 | `sys_user.permissions` JSONB；前端保存时写入**完整键图**（非 diff），故"来自模板"与"单独调整"当前不可区分（`is_custom` 只表示 JSONB 非空） |
| 有效权限 | `effective(role, custom)` = 角色模板打底 + custom 逐键覆盖；admin 恒全开 |
| 失效机制 | `token_version` 已具备：改密/停用/改权限递增 → 旧 token 下次请求 401（`verify_token_db`） |
| 审计 | `sys_audit_log(entity_type='sys_user')` 已记录建号/改权/改密/停用，含 before/after 快照 |
| 后端准入 | `require_page` / `require_action(require_data=)` / `require_admin`；账号管理整页 `require_admin` |
| 依赖校验 | 仅 1 条：`action_pool_set_policy → data_pool_price_governance`（`combo_errors` + 接口层兜底） |

| 迁移链 | Alembic 单头 `f2a7d9c3e6b1`；测试库 `:5433/spareparts_test`，conftest 跑 `upgrade head` |

## 1. 七个设计决定（甲方任务书第三节逐条回答）

### 1.1 模板是动态继承还是复制快照 → **复制快照**

产品语义已裁定："仅保存模板只影响以后使用/重新套用模板的账号"。动态继承下改模板必然静默改所有账号，与该语义矛盾。因此：

- 套用模板时，把模板权限图**快照**进账号（`sys_user.template_perms` JSONB）+ 记录 `template_code`、`template_version`。
- 账号有效权限 = `template_perms`（快照底座） ⊕ `perm_overrides`（稀疏 diff，只存与底座不同的键） 。admin 角色恒全开不变。
- 模板后续修改**不**触碰任何账号的快照。

### 1.2 模板修改后如何影响已有账号 → **两个显式动作**

- **仅保存模板**（`PUT /role-templates/{code}`）：模板 `version+1`，零账号变化。账号列表里该模板的账号显示"模板已更新至 vN，此账号仍在 vM"的落后标记。
- **保存并同步账号**（`POST /role-templates/{code}/sync`）：`dry_run=true` 先返回逐账号 diff（旧有效权限 → 新有效权限，标出变化键），前端确认后 `dry_run=false` 执行。同步 = 用新模板图替换账号快照，**保留** overrides（可选 `clear_overrides=true` 一并清除）。同步后组合非法（如 override 开着 `action_pool_set_policy` 而新模板关了数据可见）→ **整体拒绝**并逐账号报人话原因。

### 1.3 如何防止管理员锁死自己 → 五层保护

1. **内置 admin 账号**（username=='admin'）：不可停用、不可降级、权限恒全开、不参与批量与模板套用（现状保留）。
2. **最后有效管理员**：停用或降级任何 admin 角色账号前检查"active 且 role=admin 的账号数"，动完后为 0 → 400 拒绝。（共享口令 ADMIN_PASSWORD 回退仅在 sys_user 无该用户名行时可用，不算数——按最坏情况保护。）
3. **不可对自己动刀**：操作者不能停用自己、不能给自己降级、不能撤销自己的 `page_accounts`/`action_account_manage`。提示"请由另一位管理员操作"。
4. **高风险键只有 admin 角色能授予/撤销**：`page_accounts`、`action_account_manage`、role=admin 的升降，非 admin 的账号管理代理无权操作（详见 §3）。
5. **内置 admin 模板锁定**：不可编辑、不可停用、不可套用、不可同步（升管理员唯一路径 = 单账号 `PUT role=admin`，仅 admin 操作者，受第 2 条检查）。

### 1.4 批量修改事务边界 → **单事务、全成或全败、预览指纹**

- 一次批量 = 一个 DB 事务。先对全部目标账号做完整校验（存在性、保护规则、组合合法性），**任何一个不过 → 整体 400**，响应体逐账号给出原因，库里零变化。
- 防 TOCTOU："预览与实际结果一致"用**指纹**保证：dry-run 响应含 `fingerprint`（对 [操作类型+逐账号变更后有效权限] 的规范化 JSON 做 SHA-256）；执行请求必须带回该指纹，执行时重算比对，不一致（期间有人改过账号/模板）→ 409 整体拒绝，要求重新预览。
- 生效：受影响账号 `token_version+1`（旧 token 立即失效）；逐账号写审计（action=`account_bulk_update` / `account_template_sync`，reason 记操作摘要与操作者）。

### 1.5 权限依赖关系 → 声明式依赖图，后端最终校验

```python
ACTION_DATA_DEPENDENCIES = {"action_pool_set_policy": "data_pool_price_governance"}   # 既有
ACTION_PAGE_DEPENDENCIES = {"action_account_manage": "page_accounts"}                 # 新增
```

- 保存账号/模板、批量、同步时用 `combo_errors()` 按**最终生效权限**校验，人话报错（现有机制扩展）。
- 接口层兜底不变：`require_action(key, require_data=...)`；账号写接口用 `require_action("action_account_manage")`。
- 依赖图随 `_meta` 下发，前端矩阵据此画"依赖关系"、做勾选自动补齐（补齐的键打"随依赖开启"标记）、给"为什么不可用"文案。前端禁用只是体验，**后端是最终裁判**。
- "无采购成本权限不能靠池均价/差额/导出反推"：已由 `FIELD_GROUPS.purchase_cost` 登记的派生键脱敏保证（benchmark/savings 等已登记），本次补回归断言，不改机制。

### 1.6 数据迁移和回滚 → 只加不删 + 双写旧列 + 对账测试

**升级**（新迁移 revision，down_revision=`f2a7d9c3e6b1`）：

1. 建 `sys_role_template` 表；seed 5 条内置模板（code=角色名，权限值 = 迁移编写时刻 `effective(role, None)` 的**冻结字面量**，含两个新键，非 admin 全 False；`is_system=true`，version=1）。
2. `sys_user` 加 4 个可空列：`template_code`、`template_version`、`template_perms`(JSONB)、`perm_overrides`(JSONB)。**不删不改 `permissions` 旧列**。
3. 回填每个账号：`template_code=role`（未知角色回退 readonly）、`template_perms=对应内置模板冻结图`、`perm_overrides = 旧有效权限(模板⊕旧permissions) 与快照的逐键 diff`。逐账号数学上保证：新 `effective_for_user()` ≡ 旧 `effective(role, permissions)`（新键除外——新键对非 admin 全 False，即"无新能力"，行为与迁移前完全一致）。

**回滚**：downgrade 删新表新列即回旧世界。且 v2 每次写账号权限时**双写**旧列 `permissions = 完整新有效权限图`——旧代码语义下 `effective(role, 完整图)=完整图`，因此**即使在 v2 上改过账号再回滚，有效权限也不漂移**。

**对账测试**：构造覆盖全部角色×（无自定义/有自定义）的旧式账号行，跑回填逻辑（抽成可 import 的纯函数供迁移与测试共用），断言逐账号逐键新旧有效权限一致；再断言 downgrade 后旧路径结果一致。

## 2. 数据模型

```
sys_role_template
  id            PK
  code          String(64) unique      -- 内置=角色名；自定义=slug（前端用 tpl_ 前缀自动生成）
  name          String(64)             -- 显示名（可改）
  description   Text
  base_role     String(16)             -- 该模板账号的基础角色 ∈ {boss,sales,purchaser,readonly}；内置 admin 模板=admin
  permissions   JSONB                  -- 完整键→bool 图（保存时规范化补全）
  is_system     Boolean default false  -- 内置 5 条=true：不可删；admin 内置不可编辑/停用/套用
  is_active     Boolean default true   -- 停用=不可再套用/同步；已用账号不受影响
  version       Integer default 1      -- 乐观锁：PUT 必须带 version，不匹配 409
  created_by/created_at, updated_by/updated_at

sys_user（新增列，全部可空）
  template_code     String(64)   -- 套用的模板 code（不做 FK：模板停用/历史 code 仍要可显示）
  template_version  Integer      -- 套用时模板版本（对比当前版本显示"落后"）
  template_perms    JSONB        -- 套用时的权限快照（有效权限的底座）
  perm_overrides    JSONB        -- 稀疏 diff：仅存与快照不同的键
  permissions       (保留)       -- 旧列，v2 双写完整有效图，供回滚
```

**role 与模板的关系**：role 保留（`require_admin`/`require_roles("purchaser")`/`FULL_SCOPE_ROLES` 里 boss 的文件 ACL、销售行级语义都挂在 role 上）。v2 起 **role 由模板的 `base_role` 决定**——套用模板即同步 role，消除"勾了采购权限但 role 还是 readonly → 替代料维护仍 403"这类勾了也进不去的暗坑。单独改 role 的口子只留"升/降 admin"（仅 admin 操作者，受最后管理员保护）；其他转岗一律走"套用模板"。

**新权限键 2 个**（默认对所有非 admin 模板 = False，迁移后行为与现状零变化）：

- `page_accounts`（组：页面入口，敏感级 critical）——能打开"账号与权限中心"查看账号与模板（只读）。
- `action_account_manage`（组：高风险管理能力）——能建号/改权限/改密/停用/批量/管理模板。依赖 `page_accounts`。

账号管理接口从 `require_admin` 改为：读 → `require_page("page_accounts")`；写 → `require_action("action_account_manage")`（admin 恒通过，二者语义与现状对 admin 完全一致，同时支持向骨干员工受控委派）。

## 3. 权限业务语言（PERMISSION_META）

`permissions.py` 为每个键补齐八要素元数据（名称/一句话说明/能看什么做什么/不能看什么做什么/典型岗位/敏感级 low·medium·high·critical/依赖/风险提醒），经 `/accounts/_meta` 下发。例：

> **查看采购成本**（敏感级：高 · 典型岗位：采购、老板）
> 允许查看采购单价、采购金额、池采购均价以及由采购成本派生的差额与节省额。
> 不代表可以修改采购数据；关闭后所有接口（含导出、AI 助手）中相关字段一律置空，无法通过排序或差额反推。
> 风险：泄露进货底价。

矩阵按五组展示：**页面入口**（page_*）、**数据可见范围**（data_*）、**操作能力**（action_pool_*）、**行级范围**（own_customers_only）、**高风险管理能力**（action_account_manage；page_accounts 在页面组但标 critical）。

## 4. API 设计

```
GET    /role-templates                     列表（含 usage_count：总数/在用）      [page_accounts]
POST   /role-templates                     新建（可带 copy_from）                [action_account_manage]
PUT    /role-templates/{code}              改名/说明/权限；body 必带 version     [action_account_manage]
POST   /role-templates/{code}/archive      停用（内置不可停）                    [action_account_manage]
POST   /role-templates/{code}/restore      恢复                                  [action_account_manage]
GET    /role-templates/{code}/accounts     使用该模板的账号                      [page_accounts]
POST   /role-templates/{code}/sync         同步账号 {usernames?, clear_overrides, dry_run, fingerprint?}

POST   /accounts/bulk                      {usernames, operation, dry_run, fingerprint?, ...}
       operation ∈ apply_template(template_code) | grant(keys) | revoke(keys) | reset_to_template
GET    /accounts/_meta                     v2：+groups +meta +dependencies +templates
GET/POST/PUT /accounts...                  语义升级（模板字段、来源区分、保护规则），路径不变
```

守护规则汇总（写路径统一走一个 `_guard_account_write(operator, target, change)`）：

| 规则 | 行为 |
|---|---|
| username=='admin' | 任何修改类操作 400（除查看） |
| 目标 role=admin | 仅 admin 操作者可动；批量一律拒绝（选中即整批 400） |
| 升/降 admin、授/撤高风险键 | 仅 admin 操作者 |
| 最后有效管理员 | 降级/停用后 active-admin 数为 0 → 400 |
| 操作者=目标 | 停用/降级/撤高风险键 → 400"请由另一位管理员操作" |
| 组合非法 | combo_errors 人话拒绝（模板保存、账号保存、批量、同步四处统一） |

## 7. 测试计划（对应任务书第九节逐条）

后端 pytest（:5433 测试库，conftest 自动跑迁移链 = 迁移升级验证；另加 downgrade→upgrade 往返用例）：

1. 模板持久化：POST 建模板 → 新 Session 重读存在（=重启存活）。
2. 仅保存模板：PUT 后逐账号有效权限不变，version+1，落后标记出现。
3. 同步一致性：dry-run diff == 执行后实际逐账号有效权限；带错指纹 409。
4. 批量原子性：3 个账号中 1 个组合非法 → 400 逐账号原因、其余 2 个零变化；合法时全部生效。
5. 组合校验：action 无 data / action 无 page 被拒（模板、账号、批量、同步四路径）。
6. 最后管理员：唯一 active admin 不可停用/降级；操作者不可自撤。
7. token 失效：批量/同步后旧 token 401，重登拿到新权限。
8. 审计：模板 CRUD/同步、批量均落 `sys_audit_log`，operated_by=真实操作者。
9. 越权：受限账号（无 action_account_manage）直调 /accounts 写接口与 /role-templates 写接口 403；无 page_accounts 读接口 403。
10. 迁移对账：旧式账号行（各角色×有无自定义）回填前后逐键一致；双写列在旧 effective 语义下等价。
11. 脱敏回归：关 data_purchase_cost 后池 benchmark/savings 字段仍为 null（防反推）。

前端：vitest（矩阵来源标记/依赖补齐/分组全选逻辑）+ `tsc && vite build`。

E2E（run-it-spareparts 起栈）：admin / 普通（purchaser 模板）/ 受限（readonly 裁剪）三账号浏览器实测；截图：权限矩阵、批量预览与结果、模板编辑、同步预览；受限账号直调 API 403 证据。

## 8. 合并与生产门槛

**不可合并条件**（任一不过即结论"不可合并"）：数据库迁移升降级测试不过；权限安全用例（§7 之 5/6/7/9）不过；迁移前后逐账号对账（§7 之 10）不过。

**生产门槛**（即使 PR 可合并也不上线）：staging 全量权限回归 + 生产备份恢复演练（铁律：操作前先备份）之后，方可 `alembic upgrade head` 部署。
