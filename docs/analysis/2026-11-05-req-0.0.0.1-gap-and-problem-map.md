## 0. 一句话总问题

在氚云仍是录入源的前提下，一线与管理层需要在本系统内用一张**可信、可筛、可导出、可纠偏**的经营读模型，把销售/采购事实与维保项目执行（需求·领用·返还）连贯核对与日常维护——而不是反复回氚云或散落 Excel。

## 4. 未实现项：用户本质需求 → 选型

### 域① 销采经营读台（主缺口）

**本质需求（非功能清单）**

1. 一眼认出卖/采是什么货（PN+描述同构）
2. 按单号快速对账统计
3. 截一张图汇报 PN 结构（维保需求 vs 销售订单）
4. 采购分析也能带走当前筛选结果
5. 榜上的人应是「还在看的人」（离职清洗——缺真值）

**该域要解决的一个问题**：销售与采购两套只读分析在产品可读性、单号检索、PN 排行/截图、导出完备性上不对称，同一经营问题被迫在两套 UI 心智间切换。

| 子项 | 选型 | 理由 |
|---|---|---|
| R15 PN+描述 | **直接加功能** | 采购已有；销售补 description 展示即可 |
| R16 采购导出 | **直接加功能**（对齐销售 D-33/D-44 契约） | 对称缺口 |
| R16 `group_by=pn` | **采购模块内扩展** | 扩展现有 group_by，不碰维保服务 |
| R16 PN 紧凑双榜 | **采购侧独立实现**；最多抽共享条形榜呈现壳 | 事实域是 `source_type_raw`×采购金额（D-39），不是维保净量（D-35）；禁止接 `maintenance_analytics` |
| R17 订单号筛 + 单号并排 | **直接加功能** | 销售加筛；采购调列序 |
| R18 | **不做** | 口径已说明 |
| R19 | **先决策后做**（倾向不做直至有花名册） | 无离职真值；绑 #136 |
| R20 | **先决策后做**（默认不做改名） | 与 D-39 冲突；已有「采购产品」列 |

**建议切片（小 PR）**：R15 → R17 → 采购 `group_by=pn` → 采购导出 → PN 紧凑双榜（先短决策）→ R19/R20 闸门外。

### 域②③ 变相满足项：是否二次开发

**结论**：不必按用户原文做口径级二次开发；感知差距用**入口/文案/引导**消化。

| 条目 | 感知差距 | 推荐 |
|---|---|---|
| R6 | 用户找「覆盖开关」 | 加强分流说明；**禁止**静默覆盖开关 |
| R8 | 「删除」≠「归档」；入口不在卡墙 | 文案+入口发现性；**禁止**物理删除 |
| R9 | 用户要待返义务数 | 维持 D-31；坚持则须新决策 supersede |
| R10 | 用户在总表改上传失败 | 总表只读硬提示指向独立入口；**反对**总表可写（高危区） |

## 5. 「加功能 vs 重构成一体」总原则

对照 AGENTS：不做整体重写；重构一律 strangler + 契约测试。

**允许定点 strangler**

- 项目总表 / 收货往返 / 需求覆盖等同契约多入口（高危：`master_workbook`、loader、identity）
- 读模型守恒问题抽共享查询（不重写分析产品）

**禁止为以下事项重构**

- 加列、改筛选项标签、导出 CSV、紧凑榜删维、离职人员隐藏
- 为「销采维保看起来是一个模块」合并巨型 API/页面
- 以重构名义放开 AI 写业务状态

**本批默认路径**：R15–R18/R17 几乎全是读侧——直接加功能 + 契约测试；R16 紧凑图学维保**截图形态**，走采购自己的金额与 `source_type` 契约。
