## A. 维修分配与权限隔离

**现状（已上线）**：
- 无派工：待修池按 PN 汇总件数（待修 = 合格坏返 − 有效结果扣数），维修员**线下自取**实物、按 PN 报
  修好 N + 废品 M。D-0057 时代的派工/检测/领取/结案等 11 个逐件接口已在 D-0058 全部删除。
- 拍板原话（D-0058）："他们线下会自己拿对应的，池子里找到对应PN填数量就行。"
- 权限：`page_cycle_repair` 单键，仅实名 `sys_user`；维修员可见**全池**（PN/描述/待修数）与自己的记录；
  无外部维修方账号概念，委外与外部送修在"本期不做"清单里。

**差距**：
1. 恢复"分配"即恢复 D-0058 删掉的核心设计，需新决策编号。
2. 账本影响：分配若**预留**待修数，数量不变量从两项（坏返、有效扣数）变三项（+已分配未出结果）；
   若只做**指派登记**不预留，则可能出现两人对同一 PN 报数、合计超待修（现有 409 拦截仍有效，但体验是抢单失败）。
3. 对外维修方进场方式：独立账号体系？数据最小化边界（现维修员响应已不含价格/来源/项目/SN，可直接沿用）；
   这同时是"委外"的恢复，D-0058 §5 明确本期不做——需明确这次是否就做。

**需拍板**：
- 分配粒度（PN + 数量？还是到坏返批次？）与是否预留待修数。
- 对外维修方是否开账号、开什么权限、能否作废/重报。
- 分配人是哪个角色（主管键 `page_cycle_manage`？还是新键）。

## B. 电商上架人工干预

**现状（已上线）**：修好 → 同一事务生成可售意图 → worker 推商城 → 商城验目录身份与经办人 →
**自动**加库存、listing 置 `buyable`；真实闲鱼发帖是 HeldPublisher 占位，**本来就人工**。
两端一致性由契约保证：`deliveryId` 幂等、`unchanged ⇔ 库存已加`、一次投递整笔或零。

**两种解读（需会上澄清）**：
1. 担心"自动加库存/自动可买" → 改商城：`applied` 后 listing 进"待上架"态，内部人员确认后才 `buyable`。
   itsp 与推送契约不变，改动集中在商城 `_apply` 尾部与 listing 状态机；库存数字先到、曝光后置。
2. 担心"两端数据对不上" → 现契约已保证不会对不上（幂等键 + 回执语义 + 作废勾选规则），
   可能只需澄清现状 + 补一个商城侧核对视图，无代码改动。

**需拍板**：哪种解读；若解读 1，"库存已加但未上架"中间态的可接受范围、由谁点上架（经办人？）。

## C. 换购（以旧换新）

**现状**：无换购概念。可复用的既有资产：
- itsp 售前询价/报价模块（D-0046/D-0052/D-0053）——会议要求"售前报价和销售环节知晓可换购"落点在这里。
- 商城 SKU/库存/销售记录数（D-36 `salesRecordCount`）。
- itsp 循环三数（按 PN 的待修/已上电商/废品）——"哪些 SKU 有维修价值"的数据底座。
- 目录互通契约（catalog v2 / resale v1）**明确不带商业字段**（D-36 边界）。

**缺口**：
1. **单一真值源**：`可换购` + `换购价` 放 itsp 主数据（`dim_part`）还是商城 SKU？两侧都要可见 →
   无论放哪边都必须新增一条跨仓契约（现契约不含商业字段，是 D-36 的刻意边界）。
2. **换购价形态**：每 SKU 绝对价（如 500 元）还是规则（原价 − N）？
3. **换购收回的坏件进哪**：现行待修池只认 RKD 坏返行（挂维保项目/领用）；电商换购回收的坏件是
   **新来源**，D-0058 删掉的"外部入池"接口需要以新形态恢复（不占收货数量的入池）。
4. **辅助维修决策的产出**：什么报表？建议口径 = 按 PN 的（换购回收量、坏返量、修好率、价格带）交叉，
   数据分别在两系统，需定聚合方。

## D. 建议的会议产出

1. A/B/C 各自拍板或明确延期，新口径落 `docs/decisions/` 新编号（D-0061 起）。

   商城侧无改动。
4. 若 B 拍解读 1，开发量集中在商城 listing 状态机；itsp 零改动。
