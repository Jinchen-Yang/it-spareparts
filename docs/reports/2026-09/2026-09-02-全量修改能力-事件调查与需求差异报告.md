## 一、结论摘要

1. **"下载 Excel 全量修改维保所有数据"的版本确实存在过**：能力在 v1.23 成型、**v1.24.x（2026-08-21 ~ 08-26）达到顶点**——所有业务表支持改值/删行=作废/加行，整本覆盖上传，几乎不会撞冲突。
2. **杀死该体验的是 v1.25.0 = 提交 [`3036183`](https://github.com/Jinchen-Yang/it-spareparts/commit/3036183)（2026-08-27）**，它做了三件事：整本 CAS 硬校验（表过期 409 零写入）、**把 WBDD 导入与需求单作废等全部事实写入接入 revision 推进**（此后任何导入都会让手里的表立即过期）、合同总额限"唯一/当前/未共享"合同可改。该版本随 [`0a8a022`](https://github.com/Jinchen-Yang/it-spareparts/commit/0a8a022) 于 **08-29 20:55 上生产**——客户感知的"能力消失"时点。
3. v1.25 的收窄**事出有因**（修"过期工作簿静默覆盖新数据"事故），因此恢复能力**不能靠回滚代码**（会丢 8/27 之后全部修复并重开数据互踩洞），要走"行级冲突校验 + 强制接管"的方案。
4. 期间叠加了**分支治理事故**（双头基线 8/28-9/2、09-02 当天两次绕规部署），放大了"啥啥都有问题"的感知。

## 三、需求

### 3.1 客户需求（原始证据：客户微信报障 + 转述）

1. **改错能改**："硬盘返回的那个如果做错了，重新修改覆盖上传"——错误的录入要能通过整本重传修正（09-02 03:19 宋丽芳报障原文）。
2. **批量作业流**："这个我们尽量今天一天把它改完"——以 Excel 为载体的大批量数据修正。
3. **传了要能看到**：上传后要明确知道"这次改成了什么"（当前 409/0-inserted 的观感 = "传了没反应""现在又不能改了"）。
4. **订单→建项目**：传销售订单后能建维保项目（已恢复：36 个项目已建；PR #300 在做 WBDD 导入自动挂靠，首次部署已回滚，修复在途）。

### 3.2 我方需求（2026-09-02 拍板，五点）

1. **全量可改**：项目工作簿除隐藏/系统字段外**所有字段可修改**——改值、删行（=作废）、加行（=新建），适用于每一张表。
2. **权限归位**：全量修改权属于**项目负责人 + 销售人员**（限本人负责的项目），不再仅管理员。
3. **实时联动**：上传成功后，系统全部相关展示（卡片墙/项目卡/看板/金额回款消耗）立即反映。
4. **改动可见**：回执逐表逐行逐字段列出本次改动（旧值→新值、新增/作废行数、覆盖明细）。
5. **全程审计**：下载/上传/校验/应用/强制接管，**含失败尝试**，全部留痕可查。

## 四、现状 vs 目标差异

证据基线：生产运行版本（09-02 17:38 `9b30126`）+ main（`bf15a360`）代码。

| # | 能力项 | 现状（证据） | 差距 | 目标 |
|---|---|---|---|---|
| 1 | **可编辑字段范围** | 各表均有编辑能力，但：① 01_项目概览基本只读，仅合同总额可改且限"唯一/当前/未共享"（`3036183`）；② 成本/金额类多为系统计算列锁定；③ V1 规格"01/02 全只读（表 6 规格明写）" | 项目主档信息（名称/期限/负责人/销售/合同要素）无法在工作簿中改；合同要素编辑受三条件限制 | 除三类不可改（隐藏系统字段/跨表身份字段如 XSDD/派生自动重算字段）外**全部开放**；共享合同可改但提示影响范围 |
| 2 | **删行/加行** | 03/04/05/06 支持（V2.2.0 `420416f` 起逐步落地，06 为 `fb7e24b`）；01/02 不适用或受限 | 覆盖面基本达标，个别表行操作类型不全 | 每张业务表：删行=作废、加行=新建、改行=更新，语义统一 |
| 3 | **并发冲突处理** | **整本 CAS**：任何导入/他人写入推进 revision → 手里的表过期 → 409 零写入（一夜 18 次实证）；无"强制接管"路径 | 一处变更作废整本工作；冲突死循环；错误提示无"谁在何时更新了什么" | **行级冲突校验**（只校验用户改过的行）+ **强制接管**（确认后覆盖，回执列明覆盖了谁的什么改动，全程审计） |
| 4 | **操作权限** | 工作簿 validate/apply 要求 `page_maintenance` + `action_maintenance_expense_collection_upload` + `data_profit`（`maintenance_project_master_workbook.py` API 依赖链）——管理员/boss 级配置 | **项目负责人/销售默认无上传权** | 项目负责人/销售对**本人项目**拥有下载/上传/校验/应用/强制接管全权（项目范围 fail-closed） |
| 5 | **实时联动** | apply 成功后刷新屏障已建（PR #291：等待父页面与已挂载 tab 刷新）；卡片墙/面板读同一事实表 | 刷新链存在但字段级展示映射有断点（部分表字段改后对应卡片字段不变化，无 E2E 断言保障） | 每张表每个可编辑字段 → 展示面的映射有 E2E 断言：**改完即所见** |
| 6 | **上传回执** | apply 返回结构化摘要（行级计数、`orders_updated` 等键，`29cb15b` 曾修摘要键覆盖） | 字段级"旧值→新值"明细不全；updated 类计数不在前端摘要展示（造成 09-02 09:50"传了没反应"观感）；无冲突/覆盖明细 | 回执逐表逐行逐字段 diff；前端明确展示"本次修改 N 处（明细）/新增 X 行/作废 Y 行/覆盖 Z 处他人改动" |
| 7 | **审计** | 成功操作落 `sys_audit_log`（含 before/after json 列）；**失败尝试零记录**（18 次 409 实证无痕）；下载仅 access log | 失败/被拒操作不可追溯，排障只能翻 nginx 日志 | 下载/校验/应用/强制接管/失败拒绝全部落审计，含操作者、项目、携带版本、拒绝原因 |
| 8 | **导入与工作簿的互斥** | 导入推进 revision（`3036183` 接入 etl/loader）——防覆盖正确、体验误伤 | 二者并行时互相作废 | 行级校验天然消解：导入改 A 行不影响用户改 B 行 |

### 附：不建议走的路

- **回滚到 v1.24 语义**（把导入摘出 revision 推进）：等于重开"旧表静默覆盖新数据"的洞（v1.25 修的就是这个），且丢失 08-27 后全部修复——只回语义也需逐字段重审，工作量不小于正向方案。
