# D-38 工作簿首次应用回执

- 日期：2026-10-16。
- 来源：S-B-379fu 用户原始第 5 项“重放返回原回执”；依据本次 V2 工作簿真实重上传验证发现的回执重建缺口。
- 状态：已授权验收要求的技术固化，候选实现与测试中；不新增业务口径、编辑权限或发布授权。

## 背景

V2 工作簿已有按项目、导出身份、文件 SHA 与实名操作者形成的应用幂等键和 operation 记录，重复应用不应再次写事实。但仅凭 operation 重建结果会使用新计划、新批次号和当前业务状态，不能还原首次成功的 changes、warnings、voided_rows 等完整回执。HTTP 原文件再上传也可能先被当前版本冲突拒绝，未进入服务层重放。

## 决定

1. **首次完整响应与业务同事务保存。** 保留既有 `MaintenanceProjectWorkbookOperation`、幂等键和锁协议，不新增迁移。复用 `MaintenanceProjectOperationAudit` 追加一条命令完成审计：`entity_type=master_workbook_operation`、`action=apply_completed`、`entity_id=str(operation.id)`、`operated_at=operation.created_at`、同一项目与实名操作者；审计主键独立生成。`after_json` 保存 `schema=master_v2_apply_receipt_v1`、`operation_key`、首次完整 `response` 和布尔元数据 `requires_contract_amount_manage`（首次 plan 是否包含合同额修改）。事实、版本、原有审计／事件、operation 与该快照一起提交，任何环节失败整体回滚。
2. **有快照的重放返回首次结果。** 读取服务端保存的完整 response，只将 `replayed` 改为 true；包括首次 `import_batch_id`、变化、冲突、接管、警告和作废明细在内的其余字段保持一致。不重新执行事实编辑，不新增审计、事件或 operation，不推进 workbook revision。命令完成审计与每单事实审计、P3 逐行审计／每单 correction outbox 分别计数。
3. **先鉴权，再按已完成身份重放。** HTTP apply 在当前登录、项目范围和工作簿编辑资格校验后，以项目、文件 SHA 和当前实名操作者查询已完成应用，可在重新生成当前业务计划前返回保存快照。`requires_contract_amount_manage=true` 时仍执行当前 `_require_contract_amount_manage`，不能因旧请求成功而绕过金额资格；该标记由首次服务端 plan 生成，不能信任客户端或从当前差异推断。提前查询快照只读、不取新锁或提交；服务层首次应用与普通重放保留原锁前缀、幂等事务锁和 operation 行锁，应对首次应用与重试并发。客户端不提供或覆盖快照，已有快照格式或身份校验失败则拒绝，不当作历史缺快照降级。
4. **历史缺快照保留兼容，不伪造原回执。** 旧 operation 没有首次完整 response，保留既有重建结果与防重复执行行为，但不承诺与首次完整回执相等。不从当前库态推测首次批次号、变化或警告，不回填假快照。完整原回执保证适用于本协议保存了快照的成功应用。

## 影响与验证

- 本条只固化用户要求的幂等回执，不改变 D-01 删行、D-02 三路合并、D-03 金额资格、D-33 网页与 Excel 同权或现有成本／版本语义；不新增网页编辑入口、业务状态写能力、迁移或历史业务回填。
- 用真实 V2 validate/apply 与 HTTP 同文件重上传验证：除 `replayed` 外首次完整结果相同，事实、审计、事件、operation 和 revision 无重复；覆盖多单多行、单头修改、接管与作废提示、金额修改和当前权限校验。
- 注入保存回执快照失败，验证整个应用回滚；保留旧 operation 缺快照的兼容测试，并明确该路径不能准确恢复首次完整 response。自动化结果与 main 审批、用户验收和生产部署分别记录。
