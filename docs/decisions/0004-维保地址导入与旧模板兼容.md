- 确认日期：2026-10-12（上海）。
- 来源：杨金臣在接手地址交接任务后，逐项回答本会话的三个业务问题。
- 状态：需求单与领用地址均已实现并通过本地契约/真实 HTTP 验证；待生产候选审批与部署后验收。
- 当前发布基线：`main` `02bd8ed`，独立分支 `release/address-fields-20261012`。初始调查曾基于 `test`；用户于 2026-10-12 明确更正本次必须与未来功能隔离，旧 PR #354 已关闭，未修改或合入 `test`。

## 已确认规则

1. **领用地址复用现场位置。** 复用 `maintenance_site_issue.site_location`，表示实际领用地址。需求单 `receiver_address` 表示收货地址，两者分别保存；不根据需求单收货地址自动覆盖领用地址。现有普通页面手填的必填及 256 字符限制继续保留，不静默截断。
2. **缺列或空白保留原值。** 旧模板没有地址列，或地址列存在但留空，更新既有单据时保留原地址；新建且未填写时，按对应入口的既有必填/选填规则处理。清空只能由明确的清空操作触发。需求单原件与领用工作簿现支持可选「地址操作」列填写「清空」，单元格中的地址文本「清空」本身不触发操作；需求单另兼容「收货地址操作」别名。
3. **本文件同单地址矛盾，保留原地址。** 同一张单出现两个不同的非空地址时，指出单号与数据行号，保留该单原地址，其他单据的合法地址继续处理。相同地址重复、首行填写而续行空白不构成矛盾。新建单没有旧地址时保持未填并提示冲突，不从其他单据继承。

需求单实施细则：地址表头仅明确识别「收货地址」「地址」及选填注解，不把「选择收货地址」当地址；操作列允许「保留」「设置」「清空」。同单不同非空地址、不同操作或非法操作均提示并保留地址，即使其中一行填了清空。无冲突时明确操作优先于地址单元格的普通填写规则。通用入口 skip 模式仍跳过已有单据，upsert 与专用入口才更新已有地址；回执中的地址数量描述已解析单据的处理意图，不宣称每个同值重复上传都造成实际变更。

领用实施细则：`06_领用返还` 增加「领用地址」「地址操作」，兼容「地址」「现场位置」明确别名，按表头位置读取。缺列、空白及未改的签名基线不产生地址回写；同单一行改址传播到单头，多个不同新地址保留原址并提示 Excel 行号。地址加入独立签名/并发保护，不加入旧七字段缺行哈希、自动编号原料或重新取价触发条件。原有并发接管方式与作废优先不变。

## 与现有工作簿规则的关系

- 第 3 条处理同一份文件自身的地址矛盾，不替代 D-02 的并发三路合并与覆盖回执。
- 签名往返工作簿中的单头地址应与现有单号/领用日期一样规范化：只改一行，未修改的同行沿用基线，不因此报告矛盾；若两行分别修改成不同的新地址，按第 3 条保留原地址。
- 旧工作簿没有地址列或地址基线，不代表用户请求清空。新增字段不得使原本未修改的行变成地址写入。
- 地址不参与来源单据身份、领用自动编号、项目归属、数量及成本口径。地址变更的审计与版本更新沿用各入口现有规则。

## 实施边界

- 需求单复用已有 Text 字段 `receiver_address`；「选择收货地址」继续独立保存到 `delivery_address_option`，不得模糊匹配为地址。
- 领用页面、接口与项目总表 `06_领用返还` 读写同一 `site_location`；兼容原有字段名和旧模板。
- 两类 Excel 地址字段按明确表头名称识别，不依赖位置。具体别名限定在对应文件类型，不影响采购、销售和入库等其他导入。
- 地址的查看和修改沿用对应入口既有项目范围、客户信息及动作权限；不因补地址放开领用、成本、删除等权限。导出和签名基线也须验证权限。
- 删除、作废、恢复及级联由另一台电脑负责；本任务不新增这些业务规则，集成时保留已确认实现。供货分类暂缓。
- 历史原件、数据库与当前页面的只读核查不是历史补录。用户于 2026-10-12 追加授权：完成本次地址修复、审核与验证后发布生产；不再经过 `test`。本次使用 `main` 派生的独立候选，仍遵循精确 SHA 人工 GitHub 审批，不自动合入未来功能。历史地址批量补录仍未授权。

## 2026-10-12 补记：页面表单地址建议预填

- **新增口径。** 页面「人工登记领用」的新建表单允许按已关联维保需求单的收货地址给出建议预填。仅当领用地址为空且用户尚未手动编辑时才预填；预填值带「已按需求单收货地址预填，可修改」标注，用户可修改、可清空，提交以用户所见为准。
- **与规则 1 的关系。** 该口径不构成规则 1 所禁止的「自动覆盖」：规则 1 约束的是导入/工作簿回写已有单据，不得根据需求单收货地址自动覆盖领用地址；页面建议预填是显式的 UI 建议，用户可见、可控、可改。与配套 sync-plan「不自动互相代填」的边界即在于此：是否为用户可见并可修改的建议。
- **脱敏约束。** 地址建议受 customer_info（data_customer）脱敏约束，无权限用户不显示地址。管理员如需让领用登记人使用地址建议，须显式授予 data_customer。
- 关联实施文档：[2026-10-12 领用地址建议预填实施计划](../superpowers/plans/2026-10-12-pn-demand-suggestion.md)。

## 2026-10-13 修订：领用地址即需求单联系地址（业务口径裁定）

- **裁定内容。** 仓库所有者明确：领用地址就是维保需求单的联系（收货）地址，二者为同一业务概念。规则 1 基于「两者语义不同」的前提自本日起不再成立；页面新建领用单按「PN → 需求单 → 地址」自动带入属正常业务行为，不是需要禁止的「自动覆盖」。
- **地址取值规则。** 地址跟随**本单/本行关联的那张需求单**（行级 demand_order_no 为锚点；未显式关联时按单号对应关系）。同项目多张需求单地址不同（实测 67% 项目如此）不再是禁用理由，而是「跟单走」的规则；多行关联不同单时头级地址仍不自动代填。
- **可改与可查。** 自动带入的地址仍可人工修改；人工改过即人工覆盖。带入与回填会使收货地址随 site_location 展示给有维保页权限的用户（不再受 customer_info 门禁约束）——这是本裁定的已知后果，由所有者接受。
- **存量回填。** 历史领用单地址为空且能锚定到有地址需求单的，允许按上述规则批量回填（2026-10-12 的「历史补录未授权」限制在本裁定范围内解除）；执行前须出干跑清单并留审计。
