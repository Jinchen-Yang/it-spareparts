## 2. 保持不变

1. 两条业务线仍然分开。PN / SKU 主数据是唯一共用主档，本决定不改 `dim_part` 的建档规则。
2. 循环货不进入 itsp 主库存、前置库、氚云。不写 `inventory`、`stock_dynamic`、采购单、销售单、`maintenance_bad_salvage`。
3. itsp 只记出口和件数。出口就是「出口 = 电商」：有效结果上的修好数，加上修好数大于 0 时同一事务里的一条可售意图。不在库存行上打标记。
4. 价格只在商城。itsp 不出价，不用成本、采购价或销售均价填闲鱼价。
5. 合帖推荐默认仍是 `(partId, conditionBucket)`。用户原话「一类一贴」不变；本决定不把它说成对 `category_major` 的点名否定。本期推送的桶固定为好件，坏件桶不使用。
6. `SHOP_CYCLE_SELL_ENABLED` 默认关闭。商城发布模式、live 允许名单、live 确认开关仍默认关闭。代码合并不打开发真实闲管家。
7. AI 不写循环数据（issue #217）：不写结果、扣数、作废、可售意图。
8. 不合并、不关闭、不改写 HOLD 的 #520 / #521 / #522。
9. 五个 `page_cycle_*` 页键仍默认全关（含 admin），仍按实名账号显式授权。本决定只改这三个键的能力，不新增页键：`page_cycle_repair` 维修员、`page_cycle_wip` 采购三数、`page_cycle_manage` 主管。`page_cycle_recycle` 与 `page_cycle_test` 保留在权限图里，本阶段没有任何能力。

## 3. 数量规则

1. 待修数是算出来的，不单独存余额。待修 = 合格坏返件数 − 有效结果已经扣掉的件数。
2. 合格坏返行只认 `maintenance_rkd_return_line`：`line_status=active`，件况是 `坏品` / `坏件` / `故障`，`part_id` 非空，数量是大于 0 的整数。手工登记和入库单导入都算。不认 `maintenance_bad_return`。
3. 件况为空、成品、废品、非整数数量、没有 `part_id`、档案不是 `active` 的行，不进待修。件况为废品的行保持废品，不写入结果，也不计入循环账本里的废品数。循环废品数只来自结果上的废品件数。
4. 一次提交的修好数与废品数都是 0–1000 的整数，至少一件，合计不得超过该 PN 当前待修数。没填的件数留在池里。
5. 扣数按该 PN 的坏返行先进先出（`occurred_at` 空值最后，然后 `rkd_line_id`），在行锁里完成。每一行坏返上，有效结果扣掉的件数合计不得超过该行当时的合格件数。
6. 返还行被改小、作废、改离坏返件况、改 `part_id`，以及入库单重新导入做出上述变化时，用同一条不变量整笔拒绝。这同时补上现行重新导入不检查循环占用的缺口（`maintenance_return_receipt_import.apply` 今天直接改写 `qty` / `part_id` / `line_status`）。
7. 作废整笔退回，不支持只作废其中几件。填写人本人在创建当日（Asia/Shanghai）可以作废，主管随时可以作废，都要原因。修好数可能已经加进商城库存时，必须先在商城手工减库存，并勾选「商城已手工减库存」。本期不自动回冲商城库存；自动回冲只留扩展点，不改扣数表的形状。

## 4. 谁看什么

| 角色 | 页键 | 能看、能做 | 不能看、不能做 |
| --- | --- | --- | --- |
| 维修员 | `page_cycle_repair` | 待修池：PN、描述、待修件数；提交修好 N 与废品 M；自己的结果记录；当天作废自己的记录 | 来源、项目、客户、供应商、维修史、残值、价格、别人的记录、返还行 |
| 采购 | `page_cycle_wip` | 每个 PN 的待修、已上电商、废品 | 任何明细、任何写操作 |
| 主管 | `page_cycle_manage` | 全部结果、扣自哪些返还行、推送状态、作废任何人的记录 | 成本、价格、token；本期页面不展示 SN |
| 销售 | 无循环页键 | 不进入循环 | 本阶段不从循环页面新建 PN |

描述取 `dim_part.description`。返还行上的描述、备注、项目不出现在维修员响应里。

## 5. 本期不做

委外、工单闭环、对外 SN（内部身份只用结果 id + 返还行 id）、外部客户送修、回公司、内部采购单、氚云回写、真实闲鱼发帖、用循环动作改 itsp 库存。生产库还没有循环表；后续替换 #528/#529 的一件一行模型，不保留第二套真值。不在本决定的实施里打开出站开关，不部署，不升 `frontend/src/version.ts`。

公司以后要使用循环件，走普通采购，不在结果记录上增加「回公司」数量列。

## 6. 后续动作

1. 按实施计划的切片替换 main 上的一件一行代码。文档切片先合；功能切片未获本决定以外的新口径前，不得恢复派工、维修中、回公司或 `qty=1` 的逐件推送。

3. 合帖键只有在用户明确说「一类 = `category_major`」时才改商城侧；itsp 载荷字段仍不为此改名。
