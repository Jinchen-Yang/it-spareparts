# D-0022 误取消确认的完整恢复

- 日期：2026-10-21。
- 来源：金臣 2026-10-20 14:43 裁定——「误确认取消时要能完整恢复，包括子行与领用，并在产品内提供行级恢复入口」；#427 编码检察官第 4 条。
- 状态：已确认（本条为实现 lane B 配套，D-34「确认连带作废」的逆向操作）。
- 关联：D-34（0012 原件字段保护与终态确认）第 5/7 条；D-12 既有作废/恢复权限沿用。
- 编号说明：撰写时 main 最大决策号为 0021，取 0022；**合并前再核号**。

## 背景

D-34 允许人工确认「来源单头已取消」后连带软作废需求行（`maintenance_line`）、精确关联领用行（`site_issue_line`）、整单 void 的领用单头（`site_issue`），并写墓碑。若确认属于误操作，既有 `restore_demand` 只恢复墓碑，明确不逆向复活子行与领用（「恢复不逆向复活挂靠/子行」），也无产品内入口，业务上无法完整纠错。

## 决定

1. **恢复以「确认回执」为唯一依据，不猜。** 确认取消时在回执（`sys_import_batch.report_json['_source_cancel_confirmations']`）内追加 `restoration` 前置快照（schema=1）：受影响单头/需求行/领用行/领用单头/墓碑/停用挂靠的 before/after 实体快照。恢复只逆转快照记录的本次变更；回执缺少该快照（本功能上线前的历史确认）返回明确的「不可自动恢复」并列出缺失项，不凭审计文本猜测。
2. **精确逆转范围**：恢复只把「本次确认作废」的对象改回确认前状态——需求行 `is_active/voided_at/voided_by/void_reason` 四字段、领用行 `is_active`、被整单 void 的领用单头 `normalized_status/raw_status/status_mapping_state/status_mapping_version/voided_at`、墓碑 `restored_*`（version+1，事件 type=restored）。确认前已因其他原因作废的行不在快照内，不复活。requirements 更正写反向记录（`return_obligation_corrected`，不删原记录，版本只增不减）。
3. **漂移零写。** 恢复前在全局数据变更锁内复验：任一被恢复实体与快照 after 不一致（人工改动/重新导入）、来源单头或挂靠再次出现（重传、重挂、墓碑已被实名恢复或换代）、项目停用，均整次拒绝并列出冲突项，数据库零写入；预览/执行均带 `expected_digest`，不一致同样零写。
4. **幂等与回执。** 恢复回执写入同一批次 `report_json['_source_cancel_restorations']`（key=操作人+幂等键摘要）：同键同请求重放返回原回执零写；同键异请求 409；不同键对已恢复的确认返回明确「已恢复」状态，不二次写。
5. **不复活挂靠、不做任何删除。** 与既有 `restore_demand` 语义一致：恢复不逆向复活项目挂靠（assignment 保持停用，重挂走正常 assign 流程）；恢复只新增反向记录/改回状态字段，不删除任何行。仓库关联（assignment links）在作废时已按停用挂靠对账，恢复不动挂靠故不对账；重挂时由 assign 流程对账。
6. **字段保护账本（D-34 第 1 条）不受影响。** 作废与恢复都不触碰 `edited_source/manual_override`；恢复后保护状态与作废前一致。
7. **权限与审计沿用确认取消**：`action_maintenance_demand_delete` + 项目范围 + 实名操作人，等待锁后复验权限；每个被恢复实体写审计 `action=RESTORE`，原因中引用原确认回执（批次与回执键）。项目工作簿 revision 升版。
8. **产品入口**：取消影响面板提供「已确认作废恢复」入口（按项目列出可恢复的确认回执），预览→二次确认→显示恢复回执；无权限隐藏；冲突逐项展示原因。行级 /rows 表内入口因并行 PR 文件冲突本期不并入，待后续。

## 影响

- 确认回执新增 `restoration` 快照字段：旧读取方（confirmation-status、重放）只取 `result`，不受影响；回执体积增大（实体全列快照，行数上限沿用 MAX_DELETE_LINES）。
- 恢复后需求行/领用行回到有效态，但项目总表要看到该单需人工重挂（见待决策 1）。
- 无迁移：恢复回执与快照均存 `sys_import_batch.report_json`。

## 待决策

1. **恢复是否同步复活原挂靠**：当前实现保持与 `restore_demand` 一致（不复活，重挂走 assign 流程）。选项 A：维持（已实现）；选项 B：恢复时同步把快照中停用的挂靠行复活（需金臣裁定是否违背「恢复后以人工重挂为准」）。
2. **领用已部分返还后再恢复**：若作废期间对该领用单其他行登记了返还/免返，恢复会与返还事实并存；当前按「漂移零写」拒绝（不猜）。是否允许「带返还痕迹恢复」待裁定。
3. **来源同单号重新上传已生效后是否允许恢复**：当前一律拒绝（来源再现=冲突）。是否提供「放弃来源、仅恢复现场领用」的变体待裁定。
4. **跨项目**：确认后单被重挂到其他项目 → 冲突拒绝；是否允许跨项目恢复待裁定。
