## D-18（草案）系统定位：维保备件循环系统；不做工单系统

- **甲方原话要点**：做到明年就是一个完整的"维保备件循环系统/IT 循环系统"；工单系统"我们公司基因不是干这个的"，太重，厂商/众包平台更合适承载。
- **口径**：本系统只做**备件环节的循环**——坏件返还 → 检测/维修 → 再入库 → 再销售，以 **SN 序号为唯一追踪线索**。不建工单管理系统；对外提供**工单结果接入接口**（接收外部工单体系的诊断结果与坏件事实）。
- **边界**：现场服务外包、派工、工程师管理均不在本系统范围。

## D-19（草案）返修状态不贴物理标，仅系统内按岗位可见

- **甲方原话要点**："贴标对我没有意义……一旦贴个标，全公司人都会知道这东西不好用，库房都不敢用修过的件"；返修信息"最好维保自己知道"。
- **口径**：返修/维修历史**不进入物理标签、不出现在库房与销售可见的任何视图**；仅在系统内以权限可见性控制——**维保岗可见，库房/销售/普通查询不可见**。
- **实现落点**：现有 45 键权限体系 + 行级/字段可见性；涉及坏件台账、返还收货台账（D-17）、型号全景与库存视图的可见性过滤。落地前需在 #136 增补确认"哪些岗位构成维保可见集合"。

## D-20（草案）委外维修按批次平均口径核算，不承诺 1:1 SN 对应

- **甲方原话要点**：送修量大（月均约千件级）；维修会改变 SN——焊芯片、BIOS 重洗、硬盘降容（16T→14T）后 SN 随之改变，"我只能说算一个大概平均的成本"。
- **口径**：送修批次与返回件**不强绑 1:1 SN**；成本按送修批次聚合平均分摊；追溯粒度到批次（送修单、回件单、数量、金额），逐件对应仅作可选线索不作为成本依据。
- **关联**：与坏件返还台账（D-17）、M-P0-06 返件义务的关系需在确认后梳理。

## D-21（草案）AI 只产提案，人工批准后落库——#217 红线的适用澄清

- **背景**：会上描述的目标流程为"员工用 AI 识别合同 → AI 把信息插入数据库 → 管理员审批 → 入库"；与 issue #217 不变量 1"AI 永远不得写业务状态"存在字面冲突。
- **建议口径**（需甲方书面确认 + 安全评审）：AI **不直接写**任何业务表；AI 产出**待审批提案**（结构化草稿，含来源附件与置信度），**实名管理员在系统内批准后**，由系统以"该管理员的操作"落库并写审计。批准动作必须实名、可拒绝、可修改后批准。
- **前提**：依赖 AI-P0 系列切片（Capability Policy、Artifact、审计）先行落地；在 #217 平台地基完成前，任何"AI 参与写库"的流程不开发。

## D-22（草案）循环第一批数据源：坏件库/滞销库存量建档

- **甲方原话要点**：数据来源包括维修单、备件系统导入、"变卖库存，比如说我们的滞销库还有坏件库已有的"；录入 → 建档 → 补齐图片/检测报告（PDF）/型号上下文/销售文案 → 齐全性校验 → 可销售。
- **口径**：循环系统的第一块落地是**存量坏件/滞销件入循环**：建档、附件（图片 + PDF 检测报告，走现有 agent 文档解析/视觉 OCR 基建）、齐全性校验、可售清单。
- **待确认**：齐全性校验的字段清单与"可销售"的判定标准；检测报告的出具方与格式样本。
