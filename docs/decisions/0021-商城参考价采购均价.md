# D-43 商城参考价：恢复采购均价

- 日期：2026-10-20。
- 来源：杨金臣 2026-10-20 裁定，商城必须继续拿到采购价；本次任务明确了计算与兼容边界。
- 状态：已拍板。补充 D-42 销售参考均价，纠正其中第 4 条“不返回采购价”。
- 编号说明：历史 `0020-商城参考价销售均价.md` 与 `0020-项目总表同号领用单合并.md` 撞号，且分别使用 D-42 / D-0042；保留历史文件，本次检索确认 0021 / D-43 未占用后采用此编号。
- 范围：只扩展既有 GET `/api/integrations/resale/parts/price-reference`，无迁移，不写业务状态，不进入目录批量接口。

## 决定

1. **输出顺序与空态**：原 `kind="sale"` 含税、未税两条值及顺序不变，其后追加 `kind="purchase"` 的 `inc_tax`、`ex_tax` 两条，`source="itsp采购均价"`。某一域无合格样本时不输出该域条目，不伪造零价；只有采购样本时可以仅返回采购两条。
2. **窗口与权重**：采购按 `FPurchaseOrder.order_date`，复用 `resale_price_reference_window_days`（默认 30，上海业务日含今天、闭区间）、`half_life_days` 与 `weighting`。每行 `d=0.5^(age_days/half_life_days)`；`qty_weighted` 取 `w=qty*d`，`line_mean` 取 `w=d`；各税基均价为 `Σ(w×该税基单价)/Σw`。共用现有衰减及加权函数，不新增配置。
3. **过滤**：订单状态复用 `resale_price_reference_order_statuses`；固定 `qty>0`；`include_zero_prices=false` 取单价 >0，true 取 >=0，负价/NULL 始终排除。复用 `exclude_confirmed_source_error`，以 `_dq_exists("purchase", ...)` 排除已确认源数据错误，未确认疑点不排除、不做离群裁剪。`counts_revenue` 是销售行收入属性，对采购不适用；采购不连接销售单据来判断收入。
4. **单头批次行**：遵循 D-39 补充，只计 `f_purchase_line.import_batch_id = f_purchase_order.import_batch_id` 的明细。旧批次残留（含重复行号及新批次已删行号）仅在读侧排除，不清理事实数据。
5. **税基与精度**：复用 `purchase_analytics._rate_expr(FPurchaseOrder)`，票面非零税率优先，否则 13%。按 D-39 行级规则，`is_tax_inclusive=True` 时原始 `unit_price` 为含税价、未税价 = 原价 ÷ (1+r)；False/NULL 时原价为未税价、含税价 = 原价 × (1+r)。不套用单头金额缺口回退。按日期、有效税率、原始税基分组精确聚合，Decimal 换算及衰减加权，只在最终 HALF_UP 两位时舍入；不能直接调用会逐行舍入的行金额函数，也不能使用固定 13% 的旧型号分析换算。合格样本中税率 <0 或 >=1 时整次请求 503，不返回部分价格；金额沿用商城上限校验（整数位最多 14 位）。
6. **名义侧**：直接复用 `_nominal_side_expr` 的行级结构性规则。未标税率（NULL/0）时，含税单的 ex 侧为名义；False/NULL 标记单的 inc 侧为名义；已标税率两侧均非名义。每条价格的 `nominal_sample_count` 分侧统计参与明细行数，既不是数量也不是衰减权重。
7. **样本字段**：采购条目 `sample_count` 为参与采购行数、`order_count` 为 distinct `FPurchaseOrder.id`，`window` 为实际共同窗口。沿用 `latest_sale_date` / `oldest_sale_date` 字段名，在 purchase 条目中分别表示最新/最旧合格**采购订单日期**；`occurred_at` 为最近合格采购日上海零点，不是真实成交或抓取时刻。
8. **已上线商城兼容性**：不得新增 ReferencePrice、顶层、`calculation` 字段。仅扩展提供方 `kind/source` Literal。顶层 `calculation` 继续只描述销售样本，其计数/日期必须与 sale 条目一致；无销售时计数为 0、日期为 null，即使存在采购条目也如此。采购口径通过条目及本文表达。测试内用独立、与商城等价的 `extra=forbid` DTO 锁定字段集合、金额 ge0/max_digits18/4 位小数、source ≤256、prices ≤100，并校验销售元数据一致性。
9. **身份、错误与隐私**：PN 解析、认证、错误码和 no-store 沿用 D-42。不输出供应商、采购员、单号、行/订单 ID、原始证据或税率明细；采购聚合失败与销售失败一样为固定文案 503。
10. **部署顺序建议**：本次面向已支持 purchase/sale 及现有元数据的已上线商城，itsp 先于商城或同窗发布即可，商城继续按 `users.can_view_purchase` 过滤采购价。历史 D-42 中“旧 shop 不兼容”针对引入元数据前的消费者，不适用于本次仅新增 purchase 条目。本次开发不含 push、PR、合并或部署；上线仍按仓库发布审批执行。

## 实施与验证

- 入口链路不变：服务 Bearer 认证 → 参数与 PN 身份解析 → 采购/销售只读聚合 → 白名单 DTO → no-store 响应；无跨库写入或新事务状态。
- 复用一个 Decimal 加权算法，分别查询两域样本，避免采购混入销售 calculation；每张订单的日期、税率和原始税基唯一，分组 distinct 订单数求和仍是全域 distinct 订单数。
- 验证边界为现有公共 HTTP GET：窗口首末日、衰减手算、两种权重、税基混合、名义侧、旧批次残留、状态/价格/数量/源错误、单域空态、503、销售回归及隐私；跨库 JSON 夹具加入采购两条并经冻结商城 DTO 验证。
- 仅使用隔离 PostgreSQL 合成样本；运行参考价及相关采购分析测试、可用静态检查。无 UI 改动，开发验证不代表实际生产验收。
