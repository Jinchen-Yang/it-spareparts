## D-02 上传冲突：行级校验，不整本拒绝

- **状态**：已拍板。
- **口径**：上传只校验**用户改过的行**；未触碰行即使服务端已变也自动 rebase（不 409）。改同一行才冲突，冲突时**不阻止改动**，写入用户值，回执列明「覆盖了谁在何时的什么改动」，并落审计。
- **例外（唯一保留的拒绝）**：被作废的行，别人改了**不复活**——作废优先，回执提示「该行已被 xxx 作废，修改未生效」。

## D-09 报销「修复模式」删除侧：只在单合同、无排除行时执行

- **状态**：已拍板（2026-09-04）。
- **适用范围**：通用数据导入的报销页 `mode=upsert`（以本表为准）。**不改 D-01**——D-01 说的是维保总表工作簿的删行语义，另一条路径。
- **口径**：修复模式的「删除侧」（把本表未出现的旧报销行作废）只在**同时**满足两条时执行，否则整批不作废、退化为「覆盖同键、只增不删」，并在回执与预检里写明原因：
  1. 本表没有任何行因缺销售订单被排除（`missing_link = 0`）——有行被排除，本表就不完整，被排除行的旧行会落进别人贡献的合同范围里被误作废；
  2. 本表只触及**一个**销售订单——「以本表为准」的删除承诺只有在本表完整覆盖它触及的合同时才成立，文件自己证明不了；修复模式的设计形态是单合同工作簿报销页往返，多合同全公司导出触发合同级全量替换是实现副作用；
  3. 每张报销页都带**页级「销售订单」锚**（系统导出的项目工作簿报销页形态）——无锚的逐行表即使只写一个合同号也只是用户断言；不加这一条，把多合同导出按合同拆成多份单合同逐行表分次上传即可绕过第 2 条（对抗核验实跑证实）。
- **不做逐行豁免**：任何一次身份不匹配都不构成「旧行真的消失了」的证据（改过金额的内容签名对不上；旧行可能是源表还没有「数据ID」列的年代按内容键入库的）。
- **实现约束**：删除侧规则只写在 `backend/app/etl/expense_void.py` 一处，loader 执行、pipeline 门禁、precheck 预检都消费它——预演与执行不允许存在第二份实现。
- **依据**：2026-09-04 客户支付单事故；按回执提示过滤后重导实测作废 431 行、¥497,806.94 消失、批次报 success（PR #314 说明）。
- **代价**：多合同文件在修复模式下无法删旧行；要删请用对应项目的工作簿报销页逐个合同做。

## D-10 报销「修复模式」导入前作废预演：预演即承诺

- **状态**：已拍板（2026-09-04，用户选定顺序「先结构性规则 D-09，再预演」）。
- **适用范围**：通用数据导入 `mode=upsert`，且报销页会真的执行删除侧（D-09 三条全部满足：单合同、页级锚、无排除行）。抑制形态与非报销文件不适用，也不需要令牌。
- **口径**：预演不是描述，是**承诺**——要么真实导入的作废集合与预演**逐行一致**（同一批 raw_line_id、同状态、同金额、同合同号），要么这次导入根本不发生。三样东西兑现它：
  1. 作废判定只有一份实现（`expense_void.classify`），预演走无锁投影、导入走加锁实体，规则同源；
  2. 字节同一性：预演令牌把 `文件 sha256 + 作废指纹 + 合同` 用服务端 HMAC 绑在一起；提交时按**实际收到文件**的 sha256 认令牌，预演后改过文件即拒绝；
  3. 装载期指纹复核：loader 在无锁探针后与加锁重读后**各算一次**指纹，与令牌不符就在任何写入之前整批中止（`void_plan_drift`），连本表的同键覆盖也不落地，提示重新预演。
- **强制点在 HTTP 入口**：`/import/upload` 与 `/import/upload-batch` 对会作废的形态要求令牌（`void_preview_required`）；`run_import` 本身不强制，既有直接调用路径与用例不变，且两个公开入口都没有绕过预演的后门。
- **一批只允许一个会作废的报销页**：同批两个会作废的页，文件 #1 提交后文件 #2 的作废集合已变而两份预演都算自同一库态，逐文件独立事务之下不可能同时兑现；后端硬拒（`void_preview_multiple`），不交给前端判合同交集。
- **指纹刻意覆盖的范围**：作废行的 `(raw_line_id, 状态, 金额, 合同号)`、已作废集合、抑制原因、合同集合；**不**覆盖本表会同键覆盖的行——它们永远不在作废集合里，纳入只会制造无意义的拒绝。合同号必须在元组里：费用归集工作簿不取全局导入锁，能在探针→加锁重读的窗口里改合同号，该行仍会被作废，若指纹不看合同号则一声不响。
- **令牌 30 分钟过期**；过严拒绝的真实发生率上线后需观测。
- **已知残余**（本条不覆盖，如实记录）：探针→加锁重读窗口内被并发**插入**到该合同名下的新行本次不会被作废（不在 affected_ids 里），预演与实际一致，但「以本表为准」本身在这一点上是漏的；同键覆盖把 `data_status` 写成「已作废」这条第二通道不进 `expense_rows_voided`。
- **依据**：对抗核验（4 勘察 + 3 方案 + 2 证伪）与 2026-09-04 客户支付单事故；PR #313/#314/#315 的连续发现。

## D-11 报销幂等键形态冲突：原生数据ID接管旧键，同形态才是真重复

- **状态**：已拍板（2026-09-05，生产验收①发现，zcode 报告 + 对抗核验后落地）。
- **背景**：同一笔报销明细在不同导出视图下落成不同形态的幂等键（§17.4）：带「报销明细.数据ID」⇒ 原生 UUID 键；无数据ID有单号序号 ⇒ 复合键 `单号#序号@合同域hash`；两者皆无 ⇒ `EXP:` 内容键。批次 168 用旧视图落成复合键归因，客户新导出带数据ID，同一 (项目, 单号#序号) 出现两把键，归因去重守卫判为真重复整批 422——客户侧无解。
- **口径**（`maintenance_expense_integrity.duplicate_identity_verdict`，loader 归因守卫消费）：
  1. **接管**：既有归因是遗留形态、来行是原生键，且**同一合同域**（复合键的 `@hash` 正是为了让跨合同同名单号不互撞）⇒ 旧归因让位（删除 + 项目事实审计 `supersede`，before 含全部列、after 含接管行与差异）、旧键事实行软作废（导入覆盖审计）、随后为原生键建归因。旧键事实行**必须**作废：预算看板与合同工作簿按事实行汇总，只换归因会双计。
  2. **原生键权威**：既有原生、来行遗留 ⇒ 来行作废并跳过归因，不降级——否则月度大导出与手工薄来回传会让键形态反复横跳。**前提**：原生侧仍在计数（归因 approved、事实行生效、且不在本批缺行作废集合里）；否则退回整批拒绝——两把键都作废等于整条业务行从所有读模型消失且回执不报错。
  3. **真重复**：同形态不同键（如报销单退回重提换了数据ID）、跨合同域、或既有是手工独立归因（无事实行）⇒ 仍整批拒绝，422 详情与作业记录带冲突对（单号#序号、项目、两把键、原因）。
  4. **无序号内容键**（`expense_ref` 只有单号，与带序号原生行永不相等）：只在内容摘要（合同|日期|金额|事由|人员，与 transform 共用同一函数）逐字节相同时接管；对不上就回执 `unresolved`，不猜。
- **锁序**：先归因行 `FOR UPDATE`，flush 删除，再锁事实行——`autoflush=False` 下 delete 只是 pending，反过来会与按协议顺序加锁的费用归集工作簿 apply 成环（对抗核验实跑出 DeadlockDetected）。
- **回执**：`expense_rows_voided_by_identity` 单列（不进 `expense_rows_voided`，也不计入 D-09 抑制形态的「免于作废」），另有 `legacy_takeovers` / `legacy_skipped` / `legacy_unresolved` / `takeovers_amount_changed` / `legacy_siblings_active`（接管所在报销单仍有未覆盖的旧键行 ⇒ 本表可能只覆盖了该单一部分，提示核对）。不设金额门槛：源端更正金额是合法场景，等额重排又能绕过门槛；差异记审计、计数上报。
- **配套**：合同重算循环跳过「已作废且无归因」的事实行——否则接管留下的旧键行会让该项目此后所有合同修改/新建/归档被拒。
- **第三族：从未建归因的旧键孤儿行**（2026-09-05 验收③补充；`legacy_orphan_disposition` / `retire_orphan_raw`）。批次 168 时代有旧键事实行落库却没建成归因（当时归因失败），它们不在接管路径上（没有旧归因可让位），却仍以「已结束」生效：看板按事实行汇总双计，合同重算守卫把它当真重复而 400。口径：**旧键形态、无归因、其业务身份（同合同域 + 同单号#序号，或同内容摘要）已被仍在计数的原生键归因持有** ⇒ 带审计软作废（`SysAuditLog` `expense_identity/void`，`after.superseded_by` 指向原生行）。跳过而不作废等于永远留雷。两条路径都做：导入时原生行在归因前顺手清（回执 `expense_attribution_legacy_orphans_voided`，计入 `expense_rows_voided_by_identity`）；合同重算命中时就地清再继续，而不是 400。原生侧已作废/未 approved、跨合同域、既有归因不是原生键或无事实行支撑、孤儿本身是原生形态 ⇒ 仍按真重复拒绝。存量 3 条（`BXD-20260413-0019#1`、`BXD-20260312-0046#1`、`BXD-20260617-0026#1`，均 `@f02a8f6c`）由下一次客户原件跳过模式导入一次性清掉。
- **依据**：2026-09-05 生产验收①（`BXD-20260328-0004#1`：`…@f02a8f6c` × `1ab68a49-…`，项目 `5eee74ea-…`）；用客户原件回放：接管 1、看板单计、合同可改。
