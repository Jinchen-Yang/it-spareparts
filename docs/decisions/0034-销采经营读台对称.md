# D-0054 销采经营读台对称

- 日期：2026-11-05（Asia/Shanghai）。

- 状态：本轮实施口径。审核已通过。未验收、未上线。

## 范围

销售分析与采购分析上的只读呈现与只读取数：

1. 销售订单列表：每个已展示明细在 PN 下显示该行描述（R15）。
2. 销售分析增加订单号字面包含筛选（R17）。
3. 采购订单列表与采购订单 CSV：销售单号紧挨采购单号（R17）。
4. 采购分析 `group_by=pn`（R16）。
5. 采购订单 CSV 导出（R16）。
6. 采购 PN 紧凑双榜（R16）。

读者、页面键与角色硬界不变。销售侧仍是 `page_sales_analysis`，`ENABLE_RBAC` 开启时仅 `admin` / `boss`。采购侧新读面全部挂在现有 `/api/purchases/analytics/*`，经现有 `_guard_scoped`：仅 `admin` / `boss`；`purchaser`、`readonly`、销售及其他角色即使持有 `page_purchase_analytics` 也 403；`own_customers_only` 403。`ENABLE_RBAC=False` 的旁路语义不变。禁止把上述能力挂到 `page_purchases`。

## 决定

1. **销售列表描述。** 订单列表保持一单一行。`_order_products` 增加独立字段 `description`，取 `f_sales_line.description`。每个 `line_id` 的 PN 与含税单价同高、同序（`line_no`、`id`）。`null`、空串、`btrim` 后为空不占第二行，也不显示 `/`。有描述时描述单行省略，不把源文本换行撑高单价行。销售订单 CSV 仍只拼接现有 PN 与含税单价，本决定不写入描述。多产品不压成一个单价，单头金额只出现一次。

2. **销售订单号包含。** 谓词只加在 `_order_query`：`f_sales_order.order_no` 字面包含，`strip` 后 `contains(..., autoescape=True)`，`%` 与 `_` 是字面字符，区分大小写。纯空白等于不加条件。Query `max_length=64`，超长 422。该条件是单头条件，不把金额切进行级口径（行级仍只由大类/品牌触发）。列表、分组、趋势、KPI、金额直方图、订单 CSV、已记录费用的入选销售单，以及这些口上的金额上限，使用同一谓词。品牌、大类、销售候选项计数与订单详情（按 `order_id`）不改。前端控件紧挨品牌多选之后，URL 与 `toSalesApiFilters` 同步。

3. **采购两单号相邻。** 订单列表与采购订单 CSV 列序为：采购日期、采购单号、销售单号、采购类型、采购员、销售人员、客户、供应商、采购产品、项目名称、明细行数，其后为金额列。采购类型仍显示 `source_type_raw` 原文，列名仍是「采购类型」。采购产品仍是 PN 加描述，列名仍是「采购产品」。缺关联销售单号继续显示「/」。

4. **`group_by=pn` 与分类同一行级口径。** `summary` 与 `orders` 两处 `line_mode` 同时改为：存在分类筛选，或 `group_by` 为 `category` 或 `pn`。行只计单头批次行，并内连接 `dim_part`。实付是匹配行 `line_amount` 之和。含税、不含税、名义侧复用分类行级表达式，不新写税率公式。单头金额不得在按行连接后求和。分组键与下钻谓词是同一个 `coalesce(nullif(btrim(dim_part.pn_std), ''), '(空)')`。服务白名单、API 正则、前端选项三处同时加入 `pn`。默认分组仍是 `source_type`。趋势仍以 `day` / `month` 调用 `summary`。

   从 PN 分组进入订单列表时，列表金额与产品格只含该 PN 的单头批次行；若同时有分类筛选，两者取交集。订单明细保留单头三口径，并另附匹配行合计。匹配条件与列表相同：`group_by=pn` 时传入该 PN 键；分类条件仍按现有抽屉规则传入。

   **分组送达：** 除 `pn` 外的分组仍一次返回全部分组，分组合计等于 KPI 的既有契约不变。`group_by=pn` 的 `groups` 按页送达：默认 50，上限 200，查询参数 `groups_page`（前端 URL 键 `gpage`），与订单列表的 `page` 分开。响应含 `total_groups`。KPI 始终是筛选全量。当前页之和不必等于 KPI；测试须能把各页行数与三口径加总后等于该行级 KPI。这是分页送达，不是 TopN 截断，也不设「其他」桶。`pn` 不进入现有条形排行（`RANKING_GROUP_BYS`）。无 `data_purchase_cost` 时，`pn` 分组仍按**订单数**降序、键升序，与其他维度相同，不改成按行数。行级提示按成因写分类或 PN，不得在 PN 下写「只统计匹配分类」。

5. **采购订单 CSV。** 路由 `GET /api/purchases/analytics/orders/export`，注册在 `/analytics/orders/{order_id}` 之前。守卫与 `analytics_orders` 相同，且在 SQL 之前。参数是列表的筛选、`group_by`、`group_key`、`sort`、`order`，不带 `page` / `page_size`。默认 `order_date desc`，并列 `id desc`。无 `data_purchase_cost` 时有效排序回退 `order_date`，与列表同一规则。行集、金额、产品与当前 `orders()` 同一口径。一单一行。先 count；大于 10000 返回 413 且无 CSV 正文；等于 10000 允许。单元格超长同样 413。不得把 `orders()` 的 `page_size` 上限改成 10000 来冒充导出。产品格按 `line_no`、`id`：每个产品一行 PN（空 PN 为 `/`）；有描述则另起一行；产品之间空一行；整格做一次 `sales_export_text.safe_formula_text`。有客户权限时项目名按列表顺序换行拼接，空为 `/`；无客户权限时该列整列不出。供应商、客户、三口径、`nominal_side` 被遮则整列不出。可见但金额为 null 时单元格留空。UTF-8 BOM，整份校验通过后才响应。记 access log，不记行内容。

6. **采购 PN 紧凑双榜。** `GET /api/purchases/analytics/pn-boards`。禁止调用维保分析、维保 explorer，也禁止前端用销售 `CompactTab` 打销售分组口来冒充本榜。一次响应含两榜、`as_of`（与 summary 相同的 `business_today()`）、`filters_echo`。只使用采购分析共用筛选，不读 `group_by`、`group_key`、分页或排序。两榜把采购类型改写为精确等于原文「维保需求」与「销售订单」；其它筛选原样。用户已选采购类型且与该原文无交集：不查库，`items=[]`，`empty_reason="source_type_excluded"`，并给中文说明。未筛类型或筛选包含该原文：`empty_reason=null`；没有行则只是空列表。其余原文不进入任一榜。

   排名对象是该原文下单头批次行的 PN，空键规则与决定 4 相同。分类筛选与这些行取交集，不得因同一张单上还有其他分类的行就把整单算进榜。每榜最多 20 行，响应里没有第 21 名，也没有全量 PN 数组。有 `data_purchase_cost` 时按实付（这些行的 `line_amount` 之和）降序，`nullslast`，再按 PN 升序。负金额留在候选集。金额全空保持 null，不当 0。无该权限时金额键仍在且为 null，按**行数**降序再按 PN 升序；不返回按金额算出的占比、份额或条形比例。金额键只用已在 `config.FIELD_GROUPS["purchase_cost"]` 登记的名字。榜上只发布 PN 键、行数、订单数、`amount_paid`；不附一条「代表描述」，以免把多描述压成假主数据。响应另给各榜筛选全集的订单数、行数，以及有权限时的实付合计。Top20 之和不是全集，两榜之和也不是全部采购。不提供改指标、改 Top 或一键导图的参数。筛选变化后重新请求，不保留上一张图。

7. **金额遮蔽与客户、供应商门。** 新端点先走 `_guard_scoped` 与现有客户/供应商筛选门，再执行业务 SQL。无 `data_customer` 时不按客户筛选或分组。无 `data_supplier` 时不按供应商筛选，导出也不出现供应商列。项目名称继续只在客户字段可见时读取。

8. **异常大额单。** id=149683 及 ≥1000 万的采购单仍不过滤。验收沿用 D-39 的单独说明。

## 明确不做

- 不改毛利公式，不把毛利 null 显示成 0（R18）。
- 不隐藏离职销售；离职花名册仍待 issue #136（R19）。
- 不把「采购类型」改名为「采购产品」（R20）。
- 不把采购类型映射成「维保 / 销售」分组。
- 不改 D-39 三口径公式、税率、名义侧、单头批次、默认「今天」、可见范围。
- 不做项目筛选。
- 不接维保分析服务，不采用 D-25 的 `part_id` 排名身份，不套用 D-37 的负净量停用。
- 不把紧凑榜的「无成本权按行数」回写到既有分组（那些维度仍按订单数）。
- 不改 R6 / R8 / R9 / R10 的已拍板口径。
- 不写任何业务状态，不新增写接口。
- 不改商城参考价、管理员全站税口径、老板看板、销售 CSV 列集合。
- 不加销售列表的品牌列。销售列表已有订单号列；R17 在销售侧只增加包含筛选。

## 验证要求

1. 一单多行、旧批次残留、行合计与单头不一致：`group_by=pn` 不计旧批次；实付等于匹配行 `line_amount` 之和；单头实付不被行数放大。`summary` 与带 `group_key` 的 `orders` 同为 `basis_mode=line`。各页加总等于行级 KPI。
2. 双榜只收「维保需求」「销售订单」；「批量采购」不入榜；类型无交集为 `source_type_excluded`；两榜之和不等于全部采购实付。无成本权时按行数，金额为 null；先按实付取前 20 再抹金额必须失败。负金额可入榜。
3. `sales`、`purchaser`、`readonly`、收紧销售对新增端点 403；`admin` / `boss` 可访问。客户、供应商筛选门仍在 SQL 之前。
4. 导出：10001 单 413 且无数据行；遮蔽列整列不存在；公式转义且负数与负 PN 保持原样；超长单元格 413。拆成明细行并重复单头金额必须失败。路由不被 `/{order_id}` 吃掉。
5. 销售订单号：不传时既有 KPI 不变；`%` 与 `_` 按字面匹配；列表、导出与已记录费用的入选集一致；不触发 `line_mode`。
6. 销售列表：同一 `line_id` 的 PN、描述、含税单价同序；空描述不占行；单头金额不按行重复。
7. 采购列名仍为「采购类型」和「采购产品」，销售单号紧挨采购单号。
8. 新增采购读面的依赖中不出现维保分析服务。

用户点按验收另见发布说明。开发浏览器不代替该验收。未授权不得部署生产。
