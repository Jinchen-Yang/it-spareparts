## 0. 用户原话（逐字，转引任务书 §2.1）

> 成品收货也要进入循环池。修好后可选择再测也可以不测。不动，氚云不涉及维修和坏件等等。然后委外回来的都手动选择是直接进闲鱼销售？一类一贴。全自动上架

来源说明（任务书 §2.1）：委外那句在来源会话里带问号；本次任务把「全部手动选择、可直接去闲鱼」写成明确要求，本决定按任务书执行，不把去向清单退回给用户。

## 1. 业务裁定（可执行）

1. **成品收货也入池。** 成品不因是成品自动去电商；入池后件况快照记「成品」，由人在回收池选择后续去向。
2. **修好后可以再测，也可以不测。** `fixed + testing`（再测）与 `fixed + ready`（不测）两条路径都要有；`unfixed` 只能报废。
3. **不写氚云，不改氚云进销存。** 不写 `inventory`、`stock_dynamic`、采购单、销售单，不触发氚云回写。
4. **委外回来的去向全部手动选择**：`testing` / `repairing` / `to_shop` / `to_company` / `scrap` 五个去向手选，没有默认按钮、没有自动分流；`to_shop` 必须带 `condition_bucket`（好/坏）。允许直接去闲鱼。
5. **全自动上架。** 业务口径：去电商不设确认上架弹窗。工程上对真实闲管家的写请求仍受发布开关约束（itsp `SHOP_CYCLE_SELL_ENABLED`、商城发布模式 `off/dry_run/live`、live 允许名单、live 确认开关，四者同时满足才发写请求；默认全部关闭/`off`，来源任务书 §8.6）。
6. **复用现有待办派工**（`work_item.open_items` / `claim`）。工人响应里不得出现项目、供应商、SN。
7. **不写变卖台账** `maintenance_bad_salvage`；任何循环动作不插入、不更新该表。
8. **去电商与 outbox 同一数据库事务。** 载荷只有 PN 身份、好坏、数量、投递 id；不带项目、SN、成本、价格。
9. **售出由商城回写 `mark-sold`**（未发货取消/退款回写 `revert-sold`）；itsp 按服务凭据路径幂等处理，人工兜底与回调冲突 409，不覆盖。

## 2. 合帖键：推荐默认 `(partId, conditionBucket)`

### 2.1 事实与措辞边界

- 用户原话只有「**一类一贴**」四个字；没有出现 `part_id`、`condition`、`category_major` 等字段名。
- 设计代理曾把合帖写成同 PN，并问过若「一类」是指 `category_major` 要说一声；下一条用户没有回答这个差别，直接要求写接口。
- #520 决策草案 §6、#522 写成 `part_id + conditionBucket(good|bad)`；用户对架构 plan 的「没有问题」是对整份 plan 的笼统回复，**不构成对 `category_major` 的点名否定**。
- **本决定的措辞是「推荐默认」**；不把该默认表述为用户对 `category_major` 的点名裁定或否定。

### 2.2 推荐默认

1. itsp 侧：每一件循环单位出站一行，载荷固定 `partId` + `conditionBucket(good|bad)` + `qty=1` + `deliveryId`（投递事实）。
2. 商城侧：对外一帖的**推荐键是 `(partId, conditionBucket)`**。同一 PN 的好件与坏件是两帖；不同 PN 即使 `category_major` 相同也是两帖。
3. 采用该默认的理由：D-36（`0014-主数据库与商城目录互通.md`）已按稳定 `part_id` 建好坏两条零库存 SKU；大类（例如「硬盘」）合成一帖无法按型号发货，也会把不同来源的件数混在同一对外帖里。
4. 唯一业务开口：**只有用户在商城合帖任务（T7）开工前明确说「一类 = `category_major`」，才改商城合帖键**；itsp 载荷字段不用改（仍按件投递 `partId` 与好坏）。没有改口就按本推荐默认做完。

## 4. 投递与回执语义（工程口径，来源任务书 §8）

1. 商城接收路径（拟定，T6 核实前不编码）：`POST /api/integrations/cycle/sell-intents`，独立服务 token；请求字段只有 `schemaVersion` / `deliveryId` / `unitId` / `partId` / `conditionBucket` / `qty`。出现项目、客户、SN、供应商、备注、成本、价格、人员字段 → 422 不入库；itsp 自己也不发送。
2. 回执 `status`：`applied`（首次入账并处理发布）/ `unchanged`（该 `deliveryId` 先前已 `applied`，库存不再加）/ `blocked`（条件不足，库存未加、帖子未建）/ `conflict`（身份冲突或人工保护）。**`unchanged` 的前提是账上已有该 deliveryId 的成功入账行**；先前只是 `blocked` 时重放不得返回 `unchanged`，禁止用它表示「什么都没做」。
3. `blocked` 双路续跑（推荐默认）：itsp 按 5 分钟 / 15 分钟 / 1 小时 / 6 小时重试、封顶 6 小时；商城在正式图/类目/标价从缺变齐时尽力回调 itsp `requeue`（仅 `deliveryId`），仍为 `blocked` 的行 `available_at` 改为现在。webhook 丢失只影响速度，不丢正确性，不依赖人工点「继续上架」。
4. 售出/取消：商城按 `stock_applied=true` 且未分配的 delivery 依 `applied_at, delivery_id` 升序分配；差数整笔回滚进异常队列，禁止负库存；逐件调用 `mark-sold`；未发货取消/退款作废 allocation、回补库存并调用 `revert-sold`（itsp 仅当当前 `sold` 且 `shopOrderLineId` 一致时改回 `to_shop`）。已发货后退货不改 itsp，不写变卖台账、不建闲鱼售后闭环。
