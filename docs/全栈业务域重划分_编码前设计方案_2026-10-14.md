# 全栈业务域重划分 · 编码前设计方案

- 日期：2026-10-14
- 决策依据（用户当日拍板）：①**前后端都按业务域同构**分块（页面 = 域的门面，能力 = 域的 API 面）；②后端分块深度 = **逻辑域包**（单进程单库不变，不拆服务）；③节奏 = **先落完在途功能，再开重构窗口**——销售/采购侧尚有几个小功能、维保侧改动更多，均完成后再迁移。
- 性质：目标态蓝图 + 迁移批次。本文档不授权立即动代码；实施须按 §六 前置条件逐批开 issue。决策: 无（纯结构规划，不触业务口径；迁移中如发现需改行为，先走 `docs/decisions/`）。
- 输入：[2026-10-14 全流程重构调研报告](reports/2026-10/2026-10-14-全流程整体重构调研报告.md)（现状度量与三路证据）。

## 一、为什么重划（现状错位清单）

| # | 错位 | 证据 |
|---|---|---|
| 1 | 后端 58 个 api 文件中 **38 个 `maintenance_*`** 平铺，无子域边界；对应 64+ 个 `maintenance_*` service 与 72/118 张表 | api/ 目录清单；DB 路调研 §2 |
| 2 | `operations.py`（7,276 行）一个文件横跨领用/合同/回款/任务/工作区 5 个子域，是 churn 全仓第一的根因 | 后端路调研 §2 |
| 3 | 前端导航 8 组与后端能力无对应关系：「数据中心」混装主数据+导入+治理；「型号查询」在销售组但属主数据查询；「互通池」「互通PN池管理」分属两组但同域 | `nav.tsx:123-235` |
| 4 | 项目面板 13 个 Tab 组件与后端子域零对应，跨子域能力（如返还收货）长成 1,006 行单文件 | `pages/maintenance/panel/` |
| 5 | 旧域页面（Inventory/Profit/MasterData 等）平铺在 pages/ 顶层，与已有子目录域（purchases/、maintenance/）并存 | pages/ 目录 |

## 二、目标域划分（前后端同构）

**8 个顶级域，维保域内拆 5 个子域。** 每域四要素对齐：前端页面 ↔ api 文件 ↔ services 模块 ↔ 表组。

### 域 1 · 主数据与查询（master）

| 要素 | 内容 |
|---|---|
| 前端 | 型号查询（PartSearch，自销售组迁入）、备件主数据（MasterData）、互通池（Pools）+ 池分析详情、互通PN池管理（PoolManagement，自数据中心迁入） |
| api | `parts` `substitutes` `pools` `pool_analysis` |
| services | standardize、part_resolver、part_overview、pools/pool_metrics/pool_policy 等部分 |
| 表 | part_*（5）、dim_*（3）、池相关表 |

### 域 2 · 采购（purchasing）

前端：采购分析/采购异常/采购明细（3 页不动）。api：`purchases`。表：f_purchase_order/line。**近期销售采购侧小功能落此域与域 3。**

### 域 3 · 销售与利润（sales）

前端：利润分析（Profit）。api：`profit`、`resale_catalog_search/export`（无页面，消费方待核实，见 §七 Q1）。表：f_sales_order/line。**注意**：销售订单（XSDD）事实在此域，但「销售订单导入→建维保项目」是向维保域的单向供给（D-05），域间走显式接口。

### 域 4 · 库存（inventory）

前端：库存查询。api：`inventory`。表：库存事实。维保前置库（front_stock）归维保-operations 子域（服务维保领用），不在此域。

### 域 5 · 维保（maintenance）——5 子域

| 子域 | 前端 | api（38 个 maintenance_* 的目标归属） | 核心语义（决策锚点） |
|---|---|---|---|
| **5a 项目与合同 projects** | 维保主页（卡墙）、项目面板的概览/验收/任务 | `maintenance_projects` `maintenance_project_assignments` `maintenance_project_scope` `maintenance_acceptance*` `maintenance_manager_directory` `maintenance_recovery` | 稳定项目/XSDD 即身份/归属/生命周期（D-05、D-08）；验收免审批（D-13） |
| **5b 需求与补库 demands** | 需求单与同步、补库申请、面板的备件与需求单 Tab | `maintenance_demands` `maintenance_wbdd_import` `maintenance` `replenishment` `maintenance_front_stock` | WBDD 墓碑/一键作废（D-12）、缺项同步（D-27）、补库版本（CONTEXT） |
| **5c 领用与返还 operations** | 面板的领用与返还/收货台账 Tab | `maintenance_project_operations`（site-issue 部分）`maintenance_return_receipts` `maintenance_return_receipt_import` `maintenance_bad_returns` `maintenance_bad_salvage` `maintenance_warehouse` `maintenance_ckd_import` | 现场领用事实/收货台账/卡墙返还率（D-15、D-17）；生产失败关闭清单 |
| **5d 资金与费用 finance** | 面板的合同回款/费用报销 Tab | `maintenance_ledger` `maintenance_collection_evidence` `maintenance_collection_plan_imports` `maintenance_collection_reminders` `maintenance_expense_reconcile` `maintenance_project_batch_transfer` | 收款单台账/幂等/裁决（D-16 全部）、报销修复模式（D-09/10/11） |
| **5e 工作簿协作 workbook（基建）** | 无独立页面（各 Tab 的导出/上传入口） | `maintenance_project_master_workbook` `maintenance_project_workbooks` `maintenance_project_workbook_v3` `maintenance_manager_workbooks` `maintenance_expense_collection_workbook` `maintenance_doc_import` | 往返工作簿协议/行签名/三路合并（D-01/02）、并发内核与 K3 锁序 |

维保内另有两块横切能力，归属：**成本计价**（取价证据/双税/缺口重算：`maintenance_cost` 等）→ 独立共享模块，供 finance 与 operations 消费，不单设子域页；**维保迁移控制**（`maintenance_migration*`、切换 manifest）→ 5a 下的基建模块。`maintenance_analytics` `maintenance_boss_board` `maintenance_audit` → 域 7。`maintenance_ai_fallback` → 域 8。

### 域 6 · 数据与治理（data）

前端：数据导入（Import）、数据治理（Governance，含数据质量两面板）。api：`imports` `governance` `data_quality` `data_quality_calibration`。含 `etl/` 通用链路与原始件归档。维保专用导入（wbdd/doc/ckd/ledger/return_receipt）的**解析与装载**留在域 5 各子域，**网关与归档基建**复用本域——run_import 内嵌的 wbdd 特判在批 3 改为显式钩子。

### 域 7 · 分析与看板（analytics）

前端：经营看板（Boss）、维保数据分析（MaintenanceAnalytics，含排名钻取）。api：`maintenance_analytics` `maintenance_boss_board` `dashboard`（旧，消费方待核实，见 §七 Q2）。原则：跨域只读读模型统一归此域；分析筛选与权限范围沿用 D-25。

### 域 8 · 平台（platform）

前端：账号与权限（Accounts + PermissionCenter + Matrix）、系统设置、AI 助手（Chat，保留顶部快捷入口）。api：`accounts` `role_templates` `system_settings` `chat_sessions` `agent` `maintenance_ai_fallback`。权限 45 键守卫层零改动（D-07）；AI 只读红线（#217）在此域执行。

## 五、后端逻辑域包目标结构

```text
app/domains/
  master/  purchasing/  sales/  inventory/  data/  analytics/  platform/
  maintenance/
    projects/  demands/  operations/  finance/  workbook/
    cost/            # 共享计价模块（无 API 面）
app/etl/             # 仅保留通用网关；专用解析随子域
```

迁移规则：域包内 `api.py / services/ / models.py` 自洽；**域间只准 import 对方域的显式接口模块**（`<domain>/public.py`），违者 CI 检查拒绝（新增 import-lint 规则）；`app/api/`、`app/services/` 旧路径保留 re-export 门面直至批 4 收尾删除。models 域归组沿用旧导入路径（`models/__init__` re-export），**无任何 DDL**（`alembic check` 零 diff 为每批验收项）。

## 六、迁移批次（重构窗口内，风险升序）

**前置（现在 → 窗口开启）**
1. 本蓝图经用户确认后冻结；在途功能（销售/采购小功能、维保改动）照常落 main。
2. **窗口开启后的新功能直接按目标域包结构写**（新代码不欠新债）；窗口前的在途功能按旧结构完成即可，不要求改道。
3. 死代码先清（BadReturnPanel / MaintenanceProjectCard / CollectionPlanImportModal 等 0 引用件）——纯删除降低后续 diff 噪声。

**批 1 · 前端导航归组**（纯 nav.tsx + 重定向，页面代码零改动）：按 §三 重排 + NAV_REDIRECTS 兜底。验收：vitest 全绿 + 手工核对每条重定向。
**批 2 · 旧域归包**（master/purchasing/sales/inventory/data/platform 六域纯搬家）：api/services/models 按域归组，旧路径 re-export。验收：全量 pytest + `alembic check` 零 diff。
**批 3 · 维保子域拆分**（重头戏，顺序内含依赖）：workbook 基建先行（并发内核 + K3 锁序入 `workbook/`，etl 调用点收敛）→ operations（site-issue 块搬出，`operations.py` 解体开始）→ finance（回款/报销，D-09/10/11 契约测试护航）→ demands → projects。每步独立 PR，302 端点路由与契约不动。验收：三套 site-issue 契约测试 + 收款台账 review3/4 契约测试 + 06 表往返 + 真库全量 pytest。
**批 4 · 收尾**：analysis 域收编、旧 re-export 门面删除、import-lint 常驻 CI、面板 Tab 按 §四 重排。

每批开独立 issue、独立 PR（沿 AGENTS.md：不塞巨型 PR）；main 合并逐批走管理员 SHA 审批。
