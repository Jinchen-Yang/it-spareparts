## 1. 要解决的问题

### 1.1 领用页面信息不足

当前"领用与返还"页面（`SiteReturnTab.tsx`）主要展示单号、PN、SN、数量和状态，备件描述、现场备注等信息没有充分展示。部分字段数据库已有（如 `MaintenanceSiteIssueLine.remark`、`DimPart.description/brand/category_major`），但接口未返回或页面未使用。

### 1.2 返还管理与实际需求不一致

原有逻辑围绕"领用明细对应返还义务"（`MaintenanceReturnObligation` / `MaintenanceBadReturn*`）设计，且默认沿用领用件 PN。

现在确定的口径是：

> **按项目统计已返还数量，可进一步归属维保需求单；不做逐件、逐 PN、逐条领用匹配。**

当前 Excel 入库数据（`maintenance_rkd_return_line` 只统计坏品类测试结果、且要求能归属项目）、旧返还工作流及页面汇总尚未形成符合这个口径的统一链路。

### 1.3 Excel 免返修改未完整生效

当前项目工作簿修改"是否应返还"（是/否）后，只更新领用行标记（`no_return`），不同步返还义务（`maintenance_project_master_workbook.py` 直接写 flag，无 correction event），网页继续读取旧义务状态。导出中的"应返数量/返还状态/返还单号"还是固定占位值（`_v2_site_row_values` 硬编码 `—` / `待确认品类`）。

## 2. 最终业务规则（已与用户确认，本节内容不在优化中改动）

### 2.1 登记流程

**必选项目 → 可选维保需求单 → 必选 PN、填写数量 → 可选件况 → 提交**

| 字段 | 规则 |
|---|---|
| 项目 | 必选 |
| 维保需求单 | 可选，只提供当前项目下的需求单 |
| PN | 必选，通过搜索选择实际返件，不限制为原领用 PN |
| 数量 | 必填，必须大于 0 |
| 件况 | 可选（坏件/成品/废品等）；不选保留"未填写"，不默认当成好件或坏件 |
| 登记人 | 服务端自动记录当前登录用户，不能手工冒填 |
| 登记时间 | 系统自动记录 |

### 2.2 统计口径

**项目已返还数量 = 当前项目全部有效返还记录的数量之和。**

**需求单已返还数量 = 当前项目下，关联该需求单的有效返还记录数量之和。**

**未关联需求单数量 = 项目内未选择需求单的有效返还记录数量之和。**

举例：

| 有效记录 | 数量 | 归属 |
|---|---:|---|
| PN-A | 3 | 需求单 A |
| PN-B | 2 | 未关联需求单 |
| PN-C | 4 | 需求单 B |

页面显示：项目已返还 **9 件**，需求单 A **3 件**，需求单 B **4 件**，未关联 **2 件**。

随后把 PN-B 的 2 件关联到需求单 A：项目总数仍为 **9 件**，需求单 A 变为 **5 件**，未关联变为 **0 件**。**这是同一批记录的不同汇总视角，不能再次相加。**

件况（成品/坏品/废品/未填写）不影响返还数量统计，只作为明细信息保留。

**不变式（新增，写成测试断言）**：任意操作后，Σ(各需求单已返还) + 未关联 = 项目已返还总量，恒等成立。这是防重复计数/漏计数的机器可查表达。

### 2.3 修改、作废与审计

| 操作 | 统计影响 | 审计要求 |
|---|---|---|
| 新增 | 计入有效统计 | 记录登记人、登记时间 |
| 数量 5 改成 3 | 有效数量减少 2 | 保存前后值、原因、操作人及时间 |
| 更换 PN、件况或备注 | 数量不变 | 保存变更内容 |
| 补选或更换需求单 | 调整需求单归属，项目总数不重复增加 | 保存前后关联 |
| 转移项目 | 原项目减少，目标项目增加 | 同时校验两个项目权限 |
| 作废 | 整条记录退出有效统计 | 必填原因，保留原记录，不物理删除 |

- 采用版本校验，防止并发修改静默覆盖。
- 本期默认不提供"恢复作废"；误作废可重新登记，保留替代关系或备注。
- 历史查看包含：谁登记、谁修改（改了什么、为什么）、谁作废、Excel 来源（上传人、批次、原始明细身份）。
- **审计口径对齐 1.27.0 起的规范（新增）**：新端点不只记成功——权限拒绝、校验失败、版本冲突等**失败尝试同样落 `sys_audit_log`**（生产排障时"旧端点只记成功"吃过亏）；回执 `report_json` 不藏 `updated` 类字段，供事后核对。

### 2.4 免返与实际返还分离

免返（"是否应返还=否"）影响应返要求，**不删除、不隐藏、不作废实际返还记录**。

### 2.5 本次不做的内容

- 不要求返件 PN、SN 与原领用一致。
- 不建立逐件对应关系，不做 FIFO 等自动分配。
- 不按领用数量强行限制真实返件数量。
- 不新增寄出、运输、仓库审批等完整物流流程。
- 不修改库存流水、采购金额或领用成本。
- 不把第一份（总部/另一部门）入库数据混入本次统计。
- 不直接改写 WBDD 源表中的"已返数量"，提供独立的实际返还统计。
- 不在分母不完整时推算"待返数量"或"返还率"。
- 页面登记表示**登记已经收到的返件**，不是填写计划寄回数量。

## 3. 实现路径

### 3.1 页面结构

保留现有项目面板及 Ant Design 风格，优化"领用与返还"页（`SiteReturnTab.tsx`），不重新启用已停用的旧工作流组件（`SiteIssueWorkflowPanel` / `BadReturnPanel`）。

```text
领用与返还

[项目已返还数量]  [已关联需求单数量]  [未关联需求单数量]

领用记录
单号 / 日期 / PN与描述 / SN / 数量 / 是否应返还 / 现场备注

返还汇总
维保需求单 / 已返还数量 / 查看明细
未关联需求单 / 已返还数量 / 查看明细

返还明细
[登记返还] [导入入库单]
筛选 / 搜索 / 修改 / 作废 / 操作历史
```

**需求单返还总数只出现在汇总层，不重复挂到每条领用行上。**

### 3.2 领用信息展示

主列表优先补充：

- PN 与备件描述，分两行展示（参考 `PartsOrdersTab.tsx:231-243` 既有样式）。
- SN、数量及已有的现场备注（`remark` 需在 `site_issue_line_dict()` 透出）。
- 明确的"应返 / 免返 / 按规则判断"信息。

展开详情补充：

- 品牌、品类、单位等主数据（`DimPart`，通过 `part_id` 批量关联，不按 PN 文本模糊匹配）。
- 已有的领用人、发出人、现场位置等信息。
- 来源单据及关联需求单信息。

描述来源区分：当前型号描述不冒充领用当时的历史描述；现场备注不被操作原因替代。空值如实显示。桌面展开查看，移动端保留关键字段。

### 3.3 页面登记

| 字段 | 必填 | 行为 |
|---|---|---|
| 项目 | 是 | 项目面板内默认当前项目 |
| 维保需求单 | 否 | 仅搜索当前项目下的需求单 |
| PN | 是 | 搜索实际返件，显示描述便于确认（复用 `PartPicker`） |
| 数量 | 是 | 校验正数 |
| 件况 | 否 | 统一选项，保留未填写状态 |
| 备注 | 否 | 记录必要说明 |
| 来源单号/凭据 | 否 | 有原始收货依据时可填写 |

项目变更后清空不属于该项目的需求单选择。登记人、时间由服务端生成。

### 3.4 统一返还数据与汇总

优先复用、扩展现有入库返还事实结构（`MaintenanceRkdReturnLine`），不再额外建立一套重复计数的独立手工台账。

核心信息：

| 类型 | 信息 |
|---|---|
| 业务归属 | 项目、可空需求单关联（`source_order_id` 对齐现有 WBDD 身份） |
| 实际返件 | PN、描述、数量、件况 |
| 来源 | 手工登记或入库导入、来源部门/表单标识 |
| 外部身份 | 原始单据 ID、明细 ID、单号（保留来源隔离，不按单号跨来源合并） |
| 有效性 | 当前有效或已作废 |
| 审计 | 创建、修改、作废信息及版本 |

- 汇总从有效记录实时计算，不维护缓存总数。
- 现有"坏品数量"统计与新的"全部实际返还数量"必须区分命名，不能混淆。
- 需要 Alembic 迁移（新增需求单关联、作废/版本/审计字段、汇总索引）。

**迁移与存量数据纪律（新增）**：

- 生产 `maintenance_rkd_return_line` **已有数据**（坏品口径）。迁移只做加列/加索引/加表，**不重写、不删除既有行**；上线前用只读查询留档行数与关键分布，作为迁移前后对照，不把"当前核查结果"当部署时点的保证。
- 消费者切换（`maintenance_bad_returns.py`、`maintenance_recovery.py`、`maintenance_boss_facts.py`、`maintenance_analytics.py`）**先并存后切换**：新统计以新字段/新端点上线，旧坏品口径保持原样直到新口径验收通过，再单独提交切换提交——避免一 PR 里语义偷换。
- 迁移走常规链（单头卡口 CI 已有），部署顺序 = 先 app+迁移、后前端。

### 3.5 Excel 入库导入

**标准格式**：以第二份文件（`入库单_2026-09-11-20-37-34-424.xlsx`，维保部门）的业务表头为基准。支持真实双表头、主单合并行和明细续行结构；按字段名识别，不依赖固定列位置或不可靠的 sheet dimension。

**解析复用（新增，别重造）**：主单合并行 + 明细续行与收款单「主表+明细展开」是同一族问题——`5f63077`（收款单块铺开）已有成熟解法和契约测试：块首信号（如明细序号==1 / 稳定字段 ID 绑定）、向下填充字段清单（**必须含块首才有的"数据状态"类字段**，只填单号/日期修不好）、openpyxl 维度陷阱（此类文件 `read_only` 报 1×1 须 reset_dimensions / 用常规 reader）。直接移植其模式与夹具。

**导入通道（新增决策）**：**扩展 `doc-imports` 专用通道 + 异步 job**（`upload-batch` 形态），**不走通用 `/import/precheck`**。理由：通用链路存在已证实的超时家族——前端 30s→120s 刚解堵（#322/e0c80b02），后端逐 cell 安全扫描实测 18.8MB=94s（dimension 快路径尚未落地），总部那份 1,815 单/14,665 件的量级进通用链路必超时；而 `doc-imports` 通道现成具备大文件能力（`maintenance_doc_import.py` 的 `MAX_PREVIEW_BYTES=256MB`，超阈值走流式解析，51MB 实测 ~30s），66MB 标准文件直接通过，app 级 `MAX_UPLOAD_MB=100` 亦覆盖。

**流程**：

```text
选择文件
→ 文件安全与完整性校验
→ 解析主单和明细
→ 识别返件业务、项目及需求单
→ 展示预览、异常和变更
→ 用户确认（preview_token）
→ 原子写入
→ 刷新汇总
```

**关联规则**：

- 有有效 WBDD 关联时，优先据此定位需求单和项目。
- 能明确确定项目、但没有需求单时，允许登记到项目。
- 项目不能确定，或需求单与项目冲突时，进入待处理。
- 不通过 PN 猜项目、猜需求单。
- 未生效、已取消等源状态不直接新增为有效返还事实。

**预览分类**：新增 / 无变化 / 变更 / 待关联 / 不纳入（含原因，如采购补货）/ 无效。不能只显示"上传成功"。

**件况全收**：成品、坏品、废品均计入返还（区别于现有代码只收坏品类的 `RKD_RETURN_TEST_RESULTS` 过滤），件况作为明细属性保留。

### 3.6 重复上传与跨入口更正

- 同一来源下，使用稳定单据 ID + 明细 ID 判断重复；不把文件名或上传时间当业务身份。
- 相同来源明细、内容一致：不重复写入。
- 内容变化：展示差异，明确确认后更正并审计。
- 已被人工修改：旧文件不能静默覆盖。
- 已作废：重复上传不能自动复活。
- 文件中缺少某行：不能推断该返件已作废。
- 源单据后来取消：作为明确的更正操作处理，保留历史。

### 5.2 三个实施细节（2026-09-11 已拍板，落为实现规则）

**1. 返件类别范围 → 拍板：拆旧返件 + 旧库退返**

- "维保拆旧返件"、"旧库退返"两个明确返件类别**自动计入**已返还数量。
- 采购入库、销售退货、其他入库**不算**返还；"其他入库"即使带 WBDD 关联，也仅提示人工确认用途，不自动计数。
- 依据样表实况：拆旧返件 315 单全部带 WBDD、旧库退返 13 单无 WBDD、采购入库 23 单带 WBDD——不区分类别会把采购补货误计为返还。

**2. 整机计数 → 拍板：记 1 台，明细仅展示**

- 整机是计量单位：整机返件计数**记 1 台**。
- 其下组成备件明细**保留展示、不计数**（避免 1+6=7 重复计算）。
- 落地方式沿用既定建议：整机行与组成明细各自独立成行、带父子层级标记；汇总只取整机层，明细层可查。

**3. 数量精度 → 拍板：手工限正整数**

- 页面手工登记只接受**正整数**（件/块/台）。
- Excel 导入沿用源值：遇小数数量如实入库并**标记待审**，不静默取整。
- 若未来出现线缆等按长度计量物料，再按单位扩展小数能力（本期不做）。
