# S1 根代理控制面审查与阶段证据

对象：`codex/authz-s1-control-plane`，基线 `16c38c3063c2f971d3c0cce65f02924f1250e053`。本报告记录本地候选证据，不代表精确提交 CI、全域迁移或生产验收已完成。根代理实现 core，独立检查另一作者的 management、HTTP adapters、模型及 migration；跨模型审查见同目录 `s1-implementation-independent-review.md`。

## 控制面审查

已逐段核对 management 的来源读取、单资源更新、模板保存、批量预览与执行、建号、安全属性、生命周期和列表摘要，及 HTTP 分发与错误包装。

- 来源是模板保存快照与整资源个人覆盖；等值覆盖仍是覆盖，空动作仍是拒绝。运行时只消费 Grant，不从来源或角色补允许。
- 完整账号锁集合按 ID 排序，安全及生命周期命令先取管理员名单锁，模板命令先取模板锁；锁后重验操作者和目标 epoch。未把读快照的 SHARE 锁放在写入口依赖链上。
- bulk 执行使用显式目标 ID/用户名、每账号 epoch、每资源版本、模板版本、目录版本和预览指纹。执行是一个数据库事务；并非前端逐人调用。模板保存不追改已套账号，清除覆盖恢复保存版本，显式同步才采用新版本。
- 创建与重置密码不在预览、配置快照或审计记录中包含密码。普通资料命令仅接受显示名；混入安全属性或空旧权限字段也整笔拒绝。
- 在根审查提出损坏配置诊断与降级边界后，作者补齐了持久来源/Grant 校验，以及 marker 存在时拒绝 downgrade。读取错误返回可识别的 409，不排序混合 JSON 值导致 500，也不自动修补为允许。

第三角核心审查另外复现了目录漂移导致 cutover 后回旧允许；根代理补齐完整目录与执行定义一致性校验，启动及请求对无执行定义的既有 marker 均返回 503。独立反例及终轮合并回归结果见最终阶段记录。

当前覆盖范围内无未解决的控制面实施阻断。后续业务适配仍需落实对象关系、范围、信息投影和写入锁序，不能用 S1 接口存在代替其正确性。

## 重构效果与限制

旧销售专用账号写入口已退役，账号、模板、批量和同步共用一个管理编排；主体、目录、启用状态、PDP 和查询绑定各有一个实现来源。异类资源批量决定严格按资源配对，避免把字段或范围合并为主体全局能力。新增模型只有规范来源、模板模块包及持久切换记录；沿用 token_version 作为授权 epoch，没有引入第二个会话版本。

S1 的主要增量是公共控制面与协议验证，没有完成其余领域的数据投影迁移。完整 CI、前端全套结果和第三角度核心独审完成后才能退出本阶段；最终是否可合并要等 S4 的全模块覆盖、测试和重构比较，当前不作可合并结论。

## 后续种子来源及完整 CI 修订

下一阶段只读检查暴露“空配置不能证明旧来源”。作者给账号和模板增加默认 false 的持久迁移资格，迁移时存量及旧创建入口显式 true；规范建号、空配置和复制模板始终 false。根核对全部构造点、模型默认值、来源编排及执行层，没有将该标记加入运行时允许条件，也没有让模板应用传播资格。

根与跨模型独审分别发现无 cutover 时仍可创建规范空对象，原 downgrade 会删去来源，下一次 upgrade 将这些行改成旧存量。独立账号/模板两例真实 PostgreSQL 先失败，作者随后增加“存在非旧来源即拒绝降级”。根补查检查与 DDL 的竞争窗口，最终迁移先取得三个相关表的事务独占锁，再判定 cutover/来源并执行 DDL。独审用另一事务未提交的 canonical 行及 `pg_blocking_pids` 验证等待后读取新来源并拒绝，不丢列、来源或 Alembic 版本。

修订前 `bad6976` 的完整 CI：前端 165 文件 / 1,968 tests、构建与依赖扫描通过，后端有 10 个历史测试失败，不能退出阶段。7 项 direct-handler 调用仍传旧字典身份，1 项旧 schema 夹具使用当前 ORM 新字段，2 项迁移往返后沿用被授权回填撤销的旧 token。修复只适配测试接入：typed identity、旧 schema 反射插入，以及先断言旧 token 401 再真实重新登录；原锁、撤权、历史权限、非空业务降级及数据保留断言不变。来源保护还要求历史迁移夹具明确记录真实旧来源；不修改生产守卫来迁就夹具。补充提交仍须完整 CI 通过。

根进一步运行所有直接调用 downgrade 的测试选集，先定位旧 SQL/ORM fixture 来源与池迁移隔离问题，逐项修复后完整选集 123 passed / 254.91s（`/tmp/itsp-authz-s1-all-downgrades-final.log`）。池迁移此前仅请求 `migrated`，不执行每例标准 `db` 清理，前序提交的维保历史会正确触发无关降级保护；改为依赖 `db` 后，先写维保历史再跑全部池迁移的 16 项组合通过，原业务历史保护断言不变。另 root 三个 SQL 历史 fixture 文件全量 37 passed，两个项目备注文件分别 22 / 34 passed。跨模型复审检查了所有新增 fixture diff，未发现删减原断言或改动业务守卫。
