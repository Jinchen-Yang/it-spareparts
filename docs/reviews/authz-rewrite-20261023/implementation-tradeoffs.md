# 统一权限实现的成本收益判断

基线：`7a9fd2098acb6be0009a59a84e7d7330bb960d6b`；范围为本工作树的现有实现与已完成的授权审计。框架事实按本轮官方文档核验，成本列为工程判断，尚未执行压力测试或完整迁移。本文不修改业务。

## 单一推荐

**选择自托管 Cerbos 作为统一权限决定与查询计划引擎，保留 FastAPI、SQLAlchemy、React/AntD；在本项目内实现一层稳定的 authz 接口、权限配置界面和业务字段政策。** 不为了权限迁移 NocoBase/Frappe，也不同时引入第二个通用政策引擎。

理由不是 Cerbos 能包办所有权限，而是本项目最难、最容易出错的部分是：同一政策既检查单条对象，又在列表、统计、分组和导出前形成正确查询范围。Cerbos 的 `CheckResources` / `PlanResources` 与官方 SQLAlchemy adapter 提供了较直接的复用路径。增添一个受控本地服务的负担，在本项目中比长期自行维护一套通用范围表达式编译器更合理。具体查询映射、字段推导和迁移仍由应用负责。[官方 SQLAlchemy adapter 与 FastAPI 示例](https://docs.cerbos.dev/cerbos/latest/recipes/query-plan-adapters/sqlalchemy)

这是选型推荐，不是已经证明上线可行。第一项实现应把下面列出的复杂范围和故障语义做成可运行切面；若核心查询兼容性不成立，要明确记录失败原因再调整，不能留下生产失败时退回旧宽权限的旁路。

## 比较中的三个关键边界

### 1. OPA已经能做SQL过滤；仍须检查本仓适配成本

当前官方文档提供SQL过滤编译API、UCAST和列遮罩；SQL教程明确区分无条件允许、拒绝与条件过滤。Rego过滤需要符合可转换的子集，返回条件后仍由应用将其作用于查询；列遮罩也需应用执行。因此不能以“OPA只会true/false”排除它，也不能把教程SQL直接拼接当成完成本仓所有SQLAlchemy查询适配。[SQL过滤教程](https://www.openpolicyagent.org/docs/filtering/tutorial-sql-filtering)、[可编译策略子集](https://www.openpolicyagent.org/docs/filtering/fragment)、[列遮罩](https://www.openpolicyagent.org/docs/filtering/column-masks)

### 2. PyCasbin的SQLAlchemy Adapter是政策存储，不是业务行范围

官方Adapter职责是政策加载/保存，数据权限文档另列隐式权限查询和批量检查。它们能帮助授权，却不等于自动把“本人项目∪负责客户”的语义编译进本系统的分页、COUNT/SUM和GROUP BY。若选PyCasbin，应诚实地把类型化Scope compiler算入实现和长期维护成本。[Adapters](https://casbin.apache.org/docs/adapters/)、[Data Permissions](https://casbin.apache.org/docs/data-permissions/)

### 3. Cerbos也不替业务理解利润推导

官方SQLAlchemy adapter支持一组逻辑/比较/集合运算，并提供多表关联映射；不支持的运算仍需显式扩展。复杂项目关系需要验证JOIN不会重复计数，必要时由应用提供安全的EXISTS/子查询映射，不能将任意政策表达式无条件当作可执行SQL。[Adapter支持边界](https://docs.cerbos.dev/cerbos/latest/recipes/query-plan-adapters/sqlalchemy)

对“本人记录可看成本，全公司只能看数量”，记录范围和字段授权必须一起处理；不能把允许行集合与允许字段集合各自取并集后做笛卡尔积。金额推导、supplier筛选、price_trend/advice、文件再下载等依然需要统一FieldPlan。本轮审计已经证明仅替换末端mask不能解决这些问题。此成本在各引擎方案中都存在，不应只计入某一个候选。

## 推荐实现的最小运行形态

保留当前PostgreSQL和应用服务，新增一个仅内网可达的Cerbos PDP，政策从版本化本地文件读取；官方Disk driver支持文件目录，并不要求先引入Hub或外部政策数据库。[Cerbos存储配置](https://docs.cerbos.dev/cerbos/latest/configuration/storage)

账号、模板快照、个人覆盖和业务关系继续由应用中的可信持久层管理；引擎消费应用验证后的主体/资源属性。对每次账号调整生成动态政策，还是稳定政策读取受控Grant属性，要由切面实测冻结，避免把同一规则分散到数据库判断和政策文件两处。界面通过既有AntD生成分组配置、来源解释与预览；首期不为权限再迁前端框架。

新增服务的真实成本必须纳入交付：镜像/依赖固定、启动探针、政策校验、版本可核对、备份回退和拒绝策略。PDP不可用、计划无法解释或版本不符时拒绝受影响操作；不能故障时退回旧代码放行。普通只读请求可以共享同次请求的决定，但后台任务、提交前以及结果下载必须重新检查当前授权边界。

## 实施与成本验证顺序

1. **先建立可运行切面**：同一主体对项目/销售合成记录执行单条检查、列表/COUNT/SUM/GROUP BY、候选、导出和Agent查询；验证显式拒绝、空映射、关联去重，以及范围和字段组合不扩权。
2. **接入真实模块一组**：优先旧采购与利润/Agent已有反例，保留领域计算，统一查询前字段用途和输出投影。以现有探针证明新行为确实收窄，补齐允许路径，避免只测403。
3. **建设可配置的授权闭环**：目录、模板快照、覆盖、影响预览、锁内保存、版本变化、失效传播和恢复路径。管理员看到的是业务选项，不直接编辑CEL/Rego/SQL。
4. **逐模块迁移与覆盖校验**：入口、服务、任务、文件映射收敛到同一契约；保留D-03、D-25等已确认例外；只有该切面验证完成后删除其旧门。最终“全覆盖”依赖清单与验证，不依赖引擎产品名称。

本文不提供“几天/多少LOC”的数字承诺：当前还没有第一个真实模块的改造吞吐、查询计划兼容率或完整权限回归基线。后续可用首个切面的实际修改文件、查询形态数、回归失败原因与验证耗时重新估算；不能把386个入口按固定小时简单相乘，也不能把149,025行后端都算作重写成本。
