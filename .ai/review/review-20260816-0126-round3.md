## 六、建议清单（不替代 Blocker）

1. 把 import 定义为明确状态机：`previewed → validated → applied`；任何 head/line issue、未知状态、未解析项目、身份冲突都必须在一个事务内零写失败，所有 apply/accept 使用行锁或版本 CAS。
2. 项目、仓库、费用号与文档行都使用稳定 ID；项目名称仅作 alias/展示，来源字段码与中文表头先归一成同一 field identity，再执行 mapping。
3. C3 只允许在本地 parser 给出可审计失败原因后触发；敏感列默认不出境，prompt 采用 allowlist/redaction，provider、操作者、hash、字段清单均写审计。AI 只给提案，不改变 fail-closed。
4. C4 在业务确认“台账/BXD/formal 各自金额列、税基、粒度”前不得输出 matched；先确定 source batch/version/provenance，再以费用号为全集键做明确聚合，并套用 visible project IDs。
5. 并发测试使用两个独立 DB session/barrier；迁移测试在 guard 抛错当刻断言 revision、表、行数、内容 hash 不变，再清理环境。
6. HTTP 验收至少覆盖 Admin、本人项目负责人、其他项目账号、仅 page、仅 action、缺 data；分别验证 200/403/404/409、403 零写、owner 改 display name、`Cache-Control: no-store` 与敏感字段脱敏。
7. XLSX 安全门应在 multipart 读取层限制总请求/part 数和总字节，并在解压后限制 sheet、行列、单元格、sharedStrings、公式、外链与嵌入对象；不要在 async 路由中直接执行同步 LLM/全表 parse。

## 八、合并与生产门

### PR 合并结论

**❌ 不可合并。**

至少必须：

1. 关闭上文 18 项遗留 Blocker，并新增能实际命中每个反例的测试；
2. 关闭 N1/N6 两个数据安全问题，禁止未脱敏 LLM 外发和跨项目财务读取；
3. 使 C3 真实双表头/多 sheet/真实尺寸主链可工作，并为 accept 建立原子幂等；
4. 在业务确认金额口径后重做 C4 的聚合、来源版本、全集和项目 scope；
5. 建立 DB 级约束、双事务并发测试与完整 HTTP 权限矩阵。

### 生产发布结论

**❌ 不可生产、不可灰度。**

当前风险不是“少数边界显示错误”，而是可造成：

- 未税金额被标为含税、费用对账误判；
- 坏行被跳过后批次仍 applied，错误库存/计划/合同进入 canonical；
- 双 apply/双 accept、跨批关系和重传数据造成不可确定结果；
- 业务人员、账户、客户、附件等样本外发；
- 项目范围账号读取全库报销金额。

在上述数据正确性、权限和迁移可逆性闭环前，现有绿色测试不能作为生产放行依据。
