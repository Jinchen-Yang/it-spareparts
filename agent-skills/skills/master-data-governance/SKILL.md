# PN 主数据治理

## 业务背景

低毛利高流水的备件生意里，同一真实配件被不同员工以不同 PN/描述重复录入 →
采购无法比价、销售报价口径错、毛利泄漏不可见。治理体系（详见主仓库
《PN主数据整改方案-定稿》）以 **part_id = 商品身份** 为中心：合并重复型号、审核别名、
跟踪质量问题。治理操作在 **Web 治理工作台**完成；本 skill 让助手能解释机制、
辅助判断、回答"为什么"。

## 核心机制（回答用户疑问的依据）

| 概念 | 要点 |
|---|---|
| **合并 (merge)** | 重复型号合并：旧 PN 成墓碑（status=merged），事实行 repoint part_id（不改写 pn 文本），查询沿 merged_into 链自动重定向（链长恒 ≤1）。合并后自动重算利润+库存成本 |
| **回滚 (unmerge)** | 仅支持按合并日志 LIFO 回滚最近一次（前镜像还原），回滚后同样重算 |
| **候选 (match candidates)** | 系统按相似度发现疑似重复，score≥0.70 才入队、按业务量排序；🔴 **任何分数都不自动合并，必须人工审**。垃圾 compact（<5位或纯数字）不入队 |
| **别名 (alias)** | pn_raw → part_id 映射，approve/reject/reassign 三种处置；reassign 会重指既有事实行 |
| **质量问题** | 占位符品牌（"待定11111"）、PN待复核（含空格歧义）等自动扫描入队，修复后自动关闭 |
| **墓碑不复活** | 再导入已合并的旧 PN 时自动重定向到目标，不会重建墓碑 |

## 典型问答场景

### "为什么我查 X，结果显示的是 Y？"

X 已被合并到 Y（redirected_from 机制）。解释：历史数据没丢，全部归到 Y 名下统计；
事实单据上仍保留当时录入的原文可追溯。若用户认为**合并错了**：
指引到治理工作台的合并历史页做回滚（仅最近一次可 LIFO 回滚），回滚后利润/库存成本自动重算。

### "这两个型号是不是同一个东西？"（合并前辅助判断）

1. 分别 `get_part_overview`，对比：描述/品牌/品类、规格、价格区间是否吻合。
2. 给**判断依据**而非结论代签：价格区间重叠 + 描述一致 → "高度疑似重复"；
   价格差一倍 → "可能是不同规格（如大/小盘位、16G/32G），建议不合并"。
3. 🔴 提醒：合并影响利润和库存归属口径，在治理工作台操作并留意合并前镜像可回滚。

### "待审候选太多清不完怎么办"

转述机制设计：按业务量排序先清头部（影响报价准确性最大）；
确认不是重复的用"批量确认独立型号"出口批量清；score 低的尾部不急。

### "治理指标怎么解读"

待审候选数 / 质量问题数 / 待复核 PN 数 = 治理欠账；
合并数与别名审核进度 = 治理产出。新导入数据后指标回升是正常的（自动重扫）。

## 边界

- 🔴 助手**不能执行**合并/回滚/审核（无写工具）——只解释、只辅助判断、指引到工作台操作。
- 🔴 涉及"两个型号价格差异大"的判断时，价格必须分别查库，不许凭描述推测。
- 普通销售/采购问到治理概念（"PN待复核什么意思"）：用一句话版本解释
  （见 [data-dictionary](../../references/data-dictionary.md)），不展开管理员流程。
